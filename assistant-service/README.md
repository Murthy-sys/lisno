# Lisno private Python assistant

This stateless service plans reads for private Ask Lisno and Project Messages. The Node backend owns authentication, database access, project scope, permissions, exact customer prices, source freshness and publication. Python never connects to the database. All model facts and amounts are reconstructed in Node; Python returns allowed tool requests or request-local references. Model prose is discarded before returning verified facts. Greetings, thanks and short direct business intents have a deterministic path, including mixed greetings and questions.

Only the independently installed Ollama artifact may run inference. There are no cloud SDKs, fallback providers, embedding APIs, remote model selectors, training packages or automatic pulls. An unavailable runtime yields a sanitized 503. The Mac has no runtime role, tunnel, model installation or background process.

## Contract and local verification

The authoritative contract is `../backend/src/contracts/assistant-step.ts`; tests consume `../contracts/assistant-step-fixtures.json`. One authenticated `POST /internal/v1/assistant/step` makes at most one inference call. Node limits the entire generation to four attempts, three tool rounds and six tools. Node/Python request and response bodies are each limited to 32 KiB. The model response envelope (including Ollama metadata) is separately limited to 64 KiB. Before any model request, the complete serialized model input must fit both 32 KiB and a conservative UTF-8-byte token bound within the 16,384-token context, reserving 2,048 output tokens and 512 template tokens. Oversized context fails closed without trimming required messages/results. The service permits two active requests, no waiting queue, and a maximum 19-second step deadline within the supplied remaining generation time. Disconnects/timeouts cancel upstream work. Only Node performs retries and durable usage accounting. Missing model token counts return null, never fabricated usage.

Lightweight tests use fake transports with real network access denied:

```sh
python3.11 -m venv /tmp/lisno-assistant-tests
/tmp/lisno-assistant-tests/bin/pip install -r requirements.lock
/tmp/lisno-assistant-tests/bin/pip install -e '.[test]'
/tmp/lisno-assistant-tests/bin/python -m pytest -m 'not model'
```

These commands install web/test libraries only. Runtime direct and transitive versions are pinned in `requirements.lock` and used by the container build; direct dependencies also have exact package constraints. Starlette is pinned explicitly to avoid retaining an older installed transitive runtime. Do not install Ollama, download model weights, run inference, build containers or run the real-model harness on this Mac. Default tests cannot load a model.

## Independent-host setup

Deployment and artifact downloads are separate authorized operations. Choose a controlled Linux host and validate actual memory/GPU capacity before production. No model is selected by default. Pin the approved model's exact local tag and `sha256:` digest; record its license, quantization, provenance, runtime image digest and Python image digest. Pin image values with immutable `@sha256:` references. Model quality and speed remain unverified until independent-host evaluation.

1. In an isolated setup phase, obtain the approved images, Python wheels and model files on that host. No application data participates. Build the service image using `Dockerfile` with a verified immutable `PYTHON_IMAGE` build argument, and store its immutable digest. Review the resolved dependency manifest. There is no model download in the image or serving entrypoint.
2. Provision `ASSISTANT_SERVICE_TOKEN` from a server secret store. It must match Node's value and contain 32 to 512 non-whitespace ASCII characters. Never put it in client bundles, logs, model requests or a committed `.env` file. Set `ASSISTANT_MODEL_NAME`, `ASSISTANT_MODEL_DIGEST`, and `OLLAMA_NO_CLOUD=1` in both service/runtime environments.
3. Use `deployment/compose.yaml` as a starting template, not a completed production deployment. It mounts the preinstalled model directory read-only, disables cloud features, denies container Internet egress with an internal network, and shares the model's loopback namespace with the assistant. The Ollama API is never published. All requests check that the installed model digest matches; inference also checks afterward. The model directory/tag must remain immutable while serving. Stop/drain before replacing an artifact.
4. Put a trusted TLS reverse proxy on the independent host in front of loopback port 8080. Permit inbound requests only from the deployed Lisno backend over the private network, with an ingress body limit of 32 KiB and an upstream timeout above 20 seconds. Expose only the step endpoint and health routes. Disable access/body/header logging and external tracing. Do not expose the service or Ollama to a browser/public network. Cross-host transport requires HTTPS with certificate verification; no plaintext cross-host exception exists.
5. Configure Node's `ASSISTANT_SERVICE_URL` to the private HTTPS origin and `ASSISTANT_SERVICE_TOKEN` to the same secret. Set `ASK_LISNO_ENABLED` and `PROJECT_CHAT_AI_ENABLED` independently only after rollout validation. Node appends `/internal/v1/assistant/step`. No Gemini configuration selects a fallback.
6. Enforce host/container default-deny egress, allowing only backend-to-assistant and assistant-to-local-model traffic. The service accepts a fixed IP endpoint: loopback HTTP or RFC1918/ULA HTTPS with valid certificates. It rejects DNS/external destinations, URL credentials/paths/query strings, redirects and environment proxies. The deployment template uses loopback HTTP exclusively. Verify both chat surfaces function with Internet access blocked after setup, including model absence/failure, and record destination-only firewall evidence. Never collect question bodies, tokens or customer data in diagnostics.

`/health/live` proves the web process is alive, without inference. Authenticated `/health/ready` checks the pinned local artifact and returns no model identity or secret. A failed readiness check does not prevent deterministic greetings; the deployment may keep routing direct paths while marking model-dependent operation unavailable. Structured diagnostics contain only the opaque request ID, selected route, elapsed time, active/queued counts, safe outcome code, token counts and a short artifact digest. No question, fact, header, identity, secret or upstream error is logged. No tracing exporter is installed, and the image explicitly disables OpenTelemetry export. One Uvicorn worker is intentional: service concurrency limits are process-local. Scale only with corresponding global Node admission and runtime resource limits. A supervisor provides restart and a 25-second graceful shutdown; accepted work is bounded to 19 seconds. GPU/device access is intentionally not guessed in the template and must be configured/validated for the chosen host.

## Rollout and rollback

Disable both assistant feature flags and drain/fence old Gemini workers before changing the provider. Deploy Node and all four consumers with the new disclosure marker and protected published-price parser. Existing unclassified answers remain stored but cannot replay structured old prices. Enable private and shared paths only after independent-host validation; check identity revocation, legacy responses, transactional publication and all viewer roles. Rollback means disabling the assistant or deploying another verified self-hosted-compatible release. Never roll back to a cloud provider or Configuration price disclosure. Ordinary project messages remain available during assistant downtime.

## Evaluation

`evaluation/corpus.py` contains 136 synthetic prompts across both surfaces, including asymmetric project fixtures, privacy probes and missing data. `evaluation/run.py` checks exact expected tool sets and synthetic fact/report references, plus permitted clarification outcomes, without an AI judge. It measures at least 30 warm latency samples per direct/model/complex class at concurrency 1 and 2. It requires explicit independent-host confirmation and refuses Darwin. Output contains case IDs, outcomes, latency aggregates, actual known token counts, unknown-usage steps and supplied hardware/artifact metadata, never question bodies or authentication tokens. Cold p50/p95 can be supplied through `--cold-samples-file` containing `{ "modelDigest": "sha256:...", "samplesMs": [...] }` with at least 30 independently measured samples after controlled runtime unload/restarts. The harness does not mutate the model runtime, and reports cold measurements as pending when absent. Shared automatic wait time is reported separately as configured, not measured. This is a planner-decision/reference regression corpus, not a claim of general conversational quality; review failures and expand it with human-authored cases before production. Do not infer quality or speed from mock tests. The remote target is at least 95% correct answer-or-clarification decisions and zero critical tested disclosure/finance failures. Full public-endpoint access/race testing belongs to the backend verification lane, because Python cannot authorize users or inspect prices.

Current privacy projections deliberately omit room/item labels and raw materials/scope descriptions. A named room's completion or an item-specific price therefore receives clarification; material/scope descriptions are unavailable through those facts. The assistant can return aggregate verified work states/schedules and an explicitly requested customer estimate breakdown. New work/additions require a separate team quote, and never reuse the whole existing estimate as a guessed addition price. These limits are explicit until richer client-safe, lineage-preserving sources are approved.
