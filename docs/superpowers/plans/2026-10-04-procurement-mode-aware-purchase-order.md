# Mode-aware procurement purchase order task plan

Date: 2026-10-04

Source of truth: [approved specification](../specs/2026-10-04-procurement-mode-aware-purchase-order-design.md)

## Outcome and fixed boundaries

The original T0–T8 work implements specification AC1–AC10 on the existing project purchase order request path. The approved mode-selection amendment adds AC11–AC14: a two-stage PMC/Execution selector and a read-only backend preview of the chosen main line's configured calculation before saving. The existing request remains one project decision that atomically produces separate vendor POs on Super Admin approval. T0–T15 below are historical context. The approved observed-content recovery specification adds AC15–AC18; T16–T22 are the tasks proposed for this amendment.

**Configuration is read-only throughout.** No implementation task may edit `frontend/src/features/ai-estimator-knowledge/` or Configuration-owned backend screens, routes, services, domain calculators, validation, models, schemas, records or collections. Procurement-owned code can read saved revisions/sections/price/tax/UOM data and call the existing calculators. If a required value cannot be resolved, the buyer sees a blocker or the specification's reasoned historical/manual exception. No worker may “fix” a calculation by changing Configuration.

The approved estimate review round supplies scope and stable lineage. Configuration's pinned saved revision supplies mode inputs. The procurement child supplies vendor, explicit ordered quantity, agreed before-tax rate, GST and allocation. Selling margin never becomes a payable vendor PO rate. The prepared mode decision is versioned within Procurement; submitted request revisions remain immutable. Existing approved POs, estimate approvals, finance baseline and individual-order amendment path remain unchanged.

## Contract checkpoint before writers

After plan approval and the execution-mode choice, the primary agent records `git status --short` and each target's existing diff or untracked content before assigning ownership. The specification is currently an untracked approved document; preserve it and all unrelated work. Freeze these cross-layer contracts before parallel implementation:

1. **Identity and hierarchy:** project + estimate ID/version/review-round ID + immutable approved source line key; room, main basket, sub basket and main line IDs are join keys. Include/exclude and zero-value states are explicit. The preparation response adds a hierarchy without breaking existing section/item fields. One source-line mode decision maps to zero or more current procurement children.
2. **Mode decision:** a procurement-owned record keyed by project, approved round and source key, with expected version, idempotency receipt, selector (`pmc`, `execution/sub_vendor`, `execution/in_house`), confirmed canonical quantity, optional supported discount/margin basis, pinned revision identity, actor/time and audit. A null/clear selection is a versioned decision, not a Configuration write. Decide the exact `POST /procurement/projects/:projectId/purchase-order-mode-decisions` body and response once here; a pending request freezes edits.
3. **Calculation result:** per-source-line option/readiness codes and a server projection of saved inputs, applicable low-quantity/slab/wastage rules, cost, margin, selling/floor, and source digest/formula version. Per-child price/tax reference has vendor, UOM, mode/specification, effective date/version and before-tax unit amount. Configured benchmark and vendor payable quote are separate named objects; no fallback to a newer line revision or copied signed vendor balance.
4. **Request mutation:** quote and submit reference expected preparation/decision versions and explicit per-child GST, delivery/scope/terms and any manual exception reason. Quote and submit revalidate the approved source, configuration/price lineage, full eligible child set, allocations and existing commitments in a transaction. The immutable request revision stores internal mode snapshots; vendor PO reads remain vendor-specific and contain only payable commercial lines.
5. **Authorization and compatibility:** use project-scoped Procurement read/manage and existing Super Admin decision checks. New operation is entered in `route-operations.ts`, routes, OpenAPI and route tests. Existing request/revision records read with nullable new fields, never reconstructed as if their mode was known. Neither Clients nor vendors receive internal benchmarks or another vendor's prices.

The primary agent owns this contract, shared app/authorization wiring, central OpenAPI integration, query invalidation reconciliation and final diff. A contract change discovered by a writer is sent to the primary agent before another slice assumes it.

## Mode-selection amendment: contract and dependency plan

The prior Mode A choice authorized T0–T8 only. After this amended plan is approved, obtain a fresh execution-mode choice before any T9–T15 product edit. The relevant mode service, purchase tree, request panel, shared API, route registry, and tests already contain uncommitted approved work. T9 records their exact starting content and assigns each dirty or untracked target to one owner; no writer may replace those earlier changes. No Configuration-owned file or persisted revision is a target.

### Contract to freeze at T9

1. **UI mapping:** first-stage `PMC` or `Execution`; second-stage `Sub-vendor` or `In-house` only for Execution. Keep the stored leaf selector (`pmc`, `sub_vendor`, `in_house`) and one decision per approved source-line key. The preparation response adds per-leaf availability and issue text for the pinned saved revision's scopes and established legacy compatibility. A disabled choice explains the missing scope or invalid settings; current Configuration and display names never supply a fallback.
2. **Read-only preview API:** use `POST /procurement/projects/:projectId/purchase-order-mode-previews` with project-scoped `procurement.purchase_orders.manage` authorization. Body contains the expected approved estimate ID/version/review-round ID, source-line key, expected decision version, leaf mode, canonical quantity, discount basis points and In-house margin basis. Response identifies the approved source, pinned revision/digest, decision version and UOM, and returns either named issues or a calculated preview. No idempotency key, decision/audit write, quote or external order is created by preview. The route must be registered in the route-operation registry and OpenAPI inventory.
3. **Calculation breakdown:** extend only the procurement preview projection with per-scope saved base rate, quantity, rounded base subtotal, low-quantity limit, impact basis points/applied state, adjusted unit rate and amount, margin/discount/floor and result. PMC and Sub-vendor have one scope; In-house has independently rounded labor and material scopes and a reconciled sum. Existing Configuration calculator functions and rounding stages are reused, not reimplemented. Keep `mode.preview` on a saved decision and a transient draft preview distinctly identified.
4. **Freshness:** preview reads the same approved source and pinned revision as save. A source or decision-version mismatch fails explicitly. The browser query key includes project, source identity, decision version and all draft inputs; it aborts or ignores previous replies. Changing any input invalidates the displayed draft preview. The existing save operation independently re-resolves and CAS-checks the decision, then refreshes preparation; the quote remains blocked while a draft differs from the saved decision.
5. **Finance separation:** `quantity × mode base rate` is an internal configured cost stage. The vendor child's agreed before-tax price, explicit order quantity and GST remain the only payable PO source. No calculation preview or mode switch copies internal cost, selling total or signed Sub-vendor balance into a vendor PO line. The existing deliberate, uniquely matched configured *vendor price* apply action is unchanged.

## Observed-content recovery amendment: contract and dependency plan

The approved specification permits an explicit, audited Procurement decision to calculate from the **current content of the same pinned revision** when its recorded activation digest disagrees. The basis is labeled unverified against activation. This is a narrow new path; strict blocking remains the default. No original activation payload is available to reconstruct, so no task may mark those values activation-verified, auto-replace the activation digest, trust timestamps alone, use a newer revision, or change Configuration. The four reported lines also have no supplier procurement children; a mode decision does not create one.

T16 captures the existing dirty/untracked target content before any writer starts and freezes the exact optional fields. A fresh execution-mode choice is required after this plan is approved. Use the existing project-scoped Procurement manage and Super Admin approval operations; do not expand role permissions or create a new Configuration endpoint.

### Contract to freeze at T16

1. **Integrity projection:** for an active/superseded pinned revision with eight intact sections but a full-digest mismatch, expose optional `integrity: { status: "mismatch", activatedDigest, observedDigest, candidateAvailability }`. Normal `mode.options` stays empty and state stays blocked until a buyer opts in. Missing sections, changed approved identity/UOM, invalid settings and drafts do not enter this recovery. Do not add unconditional `null` fields to normal decisions or preparation digests; that would stale existing pending requests.
2. **Buyer preview/save:** extend the existing read-only preview and decision-save bodies with optional `expectedObservedDigest` and an explicit recovery acknowledgment/reason on save. Existing estimate-source, source-line, decision-version and idempotency guards still apply. Preview re-reads the exact saved sections; save re-reads them in its transaction and requires a reason of at least ten characters. Normal verified saves retain their current request/response behavior.
3. **Decision lineage:** the optional procurement-owned `integrityBasis` records `observed_unverified`, recorded activation digest, observed digest, buyer reason, actor and time. `revisionDigest` continues to store the activation digest. The selected mode, quantity, calculated inputs/result and this basis enter preparation's hash and the immutable internal request snapshot only for recovered decisions. A changed observed digest, activation digest, revision identity/version, source, UOM or selected mode invalidates the decision and blocks quote, submit and approval until a new acknowledged decision is saved.
4. **Approval and payable money:** Super Admin review identifies recovered lines and shows the frozen buyer reason, saved calculation and actual vendor payable lines. Approval requires its own acknowledgment reason in the existing decision/audit path, independently of any budget override. Approved estimate baseline and vendor child quantity/rate/GST remain the financial authority for payable PO amounts. Vendors and Clients never receive the internal recovery basis or mode rates.
5. **No-child copy and compatibility:** show `No vendor purchase item added yet` separately from configuration integrity. Adding a supplier child remains the established explicit action. Historical decisions/requests and normal verified-mode preparations retain their prior serialized digest shape; optional recovery fields are absent when unused. No migration, backfill, Configuration write, order mutation or external dispatch occurs during this implementation.
