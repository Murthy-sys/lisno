## Outcome and boundary

Estimator/Sales sees the saved, applicable Recommendation & Exclusions relationships for Main Lines included in the active room. The screen explains the configured reason and lets the estimator explicitly include an eligible related Main Line in that same room. Whole-Sub-Basket advice lists children for individual review. Mapping uses stable Configuration IDs and the exact catalogue revision; the read is bounded and restricted to Estimator/Sales catalogue permission. Advice itself never changes estimate totals, saved lines, or approval history.

The user approved this plan and selected Mode A for local implementation. No migration, dependency, seed, production write, commit, push, or deployment is in scope.

## Baseline and contract to settle before writers

- At plan creation, `git status --short` shows only the untracked approved specification. Before any implementation writer starts, recapture the dirty-path set and relevant per-target diffs; preserve unrelated edits and assign any newly dirty target explicitly.
- `KnowledgeBudgetAlterationBuilder.tsx` writes structured rules and free-text guidance. `GET /estimation/catalogue` chooses eligible source revisions and projects the hierarchy; `LeadEstimateWorkspace.tsx` and `ConfiguredEstimateBuilder.tsx` own the room-scoped configured-line state. The new read must use those current source and eligibility rules, not a separate revision or label-matching policy.
- Freeze the estimator projection before parallel writes: a maximum of 50 distinct source Main-Line IDs per request; one restricted result for each requested ID; chosen source revision ID/version; normalized actionable rule ID, requirement, target kind and stable parent/target IDs, reason, and availability/completion state; active free-text guidance ID/name/reason. Unavailable or unauthorized IDs return generic non-disclosing results. The endpoint returns no Configuration section body, private costs, vendor data, or unavailable target names.
- Use the catalogue's chosen revision for Active and ready Draft/Inactive items. Only active `added/add` rules with `must` or `can` and valid Main-Line or whole-Sub-Basket targets are actionable. Normalize legacy missing `targetKind` to Main Line. Use batched section/target reads with the existing revision/section index; no per-rule database fetch.
- The frontend compares returned source revision identity with its loaded catalogue, resolves display names from eligible catalogue IDs, and disables selection on mismatch until refresh. Query keys include sorted source IDs and revisions; chunk sets larger than 50. The backend owns permission and target eligibility; the UI never interprets a failed request as an empty recommendation set.
- The current configured-line update remains the sole path for explicit selection, including Main Basket selection and existing quantity/rate/paise validation. No new estimate-save, approval, or finance contract is planned. If implementation reveals a necessary shared-contract change, the primary agent reconciles it with the approved specification before dependent owners proceed.
