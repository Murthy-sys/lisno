# Vendor induction and activation task plan

Date: 2026-09-28  
Status: Approved task plan; Mode A implementation completed locally, final verification recorded in handoff  
Source: [approved vendor induction design](../specs/2026-09-28-vendor-induction-activation-design.md)

## Outcome and boundaries

Implement the approved Overview/Induction vendor detail, staff-authored questionnaires with safe Excel preview, one-time vendor answers and staff approval, and backend-enforced activation across web, mobile, vendor selection, suggestions, and allocations. The same derived state must drive detail, directory counts/filter, and new-work eligibility. Preserve stored lifecycle, old allocations, and the existing KPI scoring/token flows.

The current dirty-path baseline is the new approved specification only. Before any implementation writer starts, record `git status --short` and relevant target diffs again. Preserve unrelated changes; no worker may revert another worker's edits. No deployment, production mail, live data rewrite, seed, commit, or push is in this plan.

## Frozen cross-layer contract before writers

The primary agent owns the shared contract and must publish exact wire shapes to every writer before independent edits:

- `effectiveStatus`: `active | under_review | inactive | archived`, distinct from stored lifecycle `status`. Gate detail includes approved induction submission/version, current self and Procurement KPI presence, `profileComplete`, and physical verification. Zero is a completed KPI score.
- Versioned question and option IDs; supported answer types and bounded constraints; a single prior-question condition; immutable published/request snapshots; answer value unions; staff review and request states. Use vendor ID as lineage key, never name or question number.
- Protected endpoints and permission codes `procurement.vendor_induction.read/manage/request/review`; public inspect/submit DTOs containing only the five approved basic vendor fields and the request's question snapshot. Exact error and CAS/idempotency semantics are frozen before API/UI parallel work.
- Workbook contract for template and legacy preview, parser issue shape with row/column, question limits, and normalized draft JSON. The backend validates normalized questions and answers independently of the client parser.
- Query invalidation/event contract after induction, KPI, profile/verification, lifecycle, and new-work mutations. Older clients retain the lifecycle `status` field/filter; new staff Status controls use `effectiveStatus`.

## Rollout evidence and boundaries

The derived rule requires no historical record rewrite. Before any separately authorized live rollout, produce a **read-only** count of existing vendors that would become Under Review, the number of projects/items with those vendors already allocated, and eligible-list query timing. Check indexes/query plans and prepare a reversible release sequence; do not run a production migration or send vendor email in this task. A real uploaded workbook is still needed to verify formatting that is absent from the pasted table; the implementation must nevertheless handle the approved template and legacy column preview safely.
