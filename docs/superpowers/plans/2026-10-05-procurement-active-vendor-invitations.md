# Simple vendor invitations and ranked bid responses: task plan

Source of truth: [approved specification](../specs/2026-10-05-procurement-active-vendor-invitations-design.md), revised 2026-10-06. This plan replaces the former send-time BOQ-fields task. The approved customer estimate's pre-GST line amount is vendor-visible; Configuration/project base cost remains internal.

## Baseline and contract

- Preserve the dirty worktree and inspect each target diff before editing. Tender files are currently untracked. Earlier work already added eligible-vendor selection, approved-quote snapshots, average bid calculation, priority rank, and the compact enquiry layout; review and reuse it rather than rebuilding it.
- Backend remains authoritative for the complete included approved-line set, description, quantity, UOM, quote, preparation digest, eligibility, and financial calculations. The first Send saves the derived BOQ and dispatches selected vendors. No scope/date/location input or second click occurs at enquiry.
- New BOQ revisions may omit scope/date/location; historical revisions retain existing values. These terms become required, digest-bound fields of the award proposal before it enters approval. Issued orders read only approved proposal terms. Material vendor-facing scope changes require a BOQ revision and rebid.
- Email remains the existing preflighted delivery path. WhatsApp uses manual, ready-to-send sharing as approved. Use a separate short-lived hashed access token for a WhatsApp share, tied to a delivered vendor invitation/revision; do not replace or revoke the email token when preparing it. The authenticated share-intent endpoint returns an ephemeral wa.me URL and records not_sent. Public inspect/submit must accept either valid channel token for the same vendor/revision, enforce one complete bid, and revoke/consume access correctly on submission, revision, expiry, or resend. Do not store raw tokens or claim WhatsApp delivery.
- Keep authorization route registry, frontend API types, OpenAPI, cache invalidation, idempotency, CAS/version checks, and existing email failure semantics aligned with every changed route/contract. No new dependency is expected.

## Acceptance and limits

- Trace AC1-7 in the approved specification to focused evidence. Use asymmetric approved/internal amounts and unequal vendor bids so wrong source, units, and averages cannot pass. Test a historical BOQ with existing work-order fields and a new BOQ without them.
- Verify a successful email does not imply WhatsApp delivery, WhatsApp preparation does not invalidate email, and submission through either channel cannot create two bids. Preserve disabled-mail no-write behavior. Stub all outbound messages; do not send real email or WhatsApp.
- Do not seed, backfill, run a production migration, deploy, commit, or push. Required tests/builds may create ignored temporary output; report unrun checks and remaining risks.
