# Main Basket vendor selection and unnecessary expansion removal: task plan

Source of truth: [approved specification, clarified by the user during implementation](../specs/2026-10-06-main-basket-vendor-selection-design.md). This plan covers both user requests: select all eligible vendors for a Main Basket after bids exist, and remove the three unnecessary expansions, including **Prior BOQ revisions**. Preserve the bid details and work-order actions.

## Baseline and contract to preserve

- The repository is dirty. The tender service, route, model, domain, frontend enquiry/comparison, API, CSS, and focused tests are currently untracked; `backend/src/domain/route-operations.ts` and `backend/src/openapi.ts` are modified. Before any writer starts, capture the dirty-path set and inspect the complete contents or relevant diff of each target. Do not replace, reformat, stage, or revert unrelated work.
- Candidate membership uses stable Main Basket ID and backend activation/KPI/contact readiness. The picker may display eligibility independently of BOQ or invitation state, but only the backend decides whether a request may be sent. A frozen BOQ includes every approved included line and retains its source IDs, quantity, UOM, and approved quote.
- The current sent revision, existing vendor links, submitted bids, counteroffer history, and award records are immutable history. A first invitation to a new vendor attaches to that revision; failed/expired/stalled delivery uses resend semantics; a submitted bid uses a reasoned counteroffer. An active sent/pending invitation is a no-op with an explicit result. Vendor-facing scope drift requires an explicit new revision. Award pending/issued states must not acquire new bids outside their established withdrawal/revision path.
- Mail preflight precedes invitation/token/audit writes. Outbound delivery is stubbed in verification. The public vendor link remains scoped by vendor, revision, expiry, and hashed token. No production mutation, seed, migration execution, real mail/WhatsApp, deployment, commit, or push is part of this task.

## API and UI contract checkpoint

The primary agent settles and records the exact DTO before parallel writers begin. The expected design is one authenticated, project-scoped batch action beneath the enquiry for a sent revision, with `expectedVersion`, current BOQ revision identity/digest, `idempotencyKey`, selected stable vendor IDs **or** a server-resolved `all_eligible` selection, and a required reason whenever any selected vendor has already bid. A basket-wide select-all must include eligible vendors beyond the current page without a silent cap; large selections need a bounded, observable delivery path. Return a result per vendor: first invite, resend, counteroffer, already invited/no-op, or delivery failure/pending, plus the current enquiry version. Revalidate every vendor and current revision at commit time. Keep initial draft dispatch compatible. Use a durable batch idempotency record if the existing invitation/enquiry records cannot safely replay a mixed or all-no-op request; never persist raw tokens.

The frontend treats vendor eligibility, invitation state, and BOQ dispatch readiness as separate facts. It maintains explicit selections across search/pages and a basket-wide select-all state. The sent-BOQ action previews how each selected vendor will be handled and requests a counteroffer reason when needed; actual backend results replace the preview after submission. The existing **Comparison** step continues to show the full vendor bid details and work-order actions. Remove the two disclosures beneath that detail and the separate **Prior BOQ revisions** disclosure.

## Parallel boundaries

- T1 backend and T2 frontend may run in parallel only after T0 fixes the API/DTO contract; they own disjoint paths. The primary owns cross-layer interpretation and sends any contract change to both owners immediately.
- T2 and T3 share `ProcurementBasketEnquiry.tsx`, API types, CSS, and workspace tests. Keep them with the same frontend owner, sequentially. No second frontend writer on those paths.
- Route-operation/OpenAPI/test fixture files belong to T1 during backend writes. The primary reviews, but does not edit them concurrently. Integrity review and final verification wait until all writers finish.
- If execution Mode B is selected, the primary performs T1, T2, T3, T4, and T5 inline in this dependency order. This plan does not itself authorize either implementation mode.
