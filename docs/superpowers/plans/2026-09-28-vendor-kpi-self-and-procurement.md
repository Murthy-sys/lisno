## API/data and security checkpoints for execution

1. Backend canonical operations: protected vendor-ID read, Procurement assessment save, and request/resend, with independent `procurement.vendor_kpi.read`, `.rate`, `.request` grants only to Procurement and the sole active Super Admin. Public inspect/submit accepts a raw token only in a POST body, never as ambient login. The route-operation registry, OpenAPI, and both client mirrors must agree.
2. Current score is projected from immutable revisions keyed by stable vendor ID, source, and rubric version/type. Backend derives `averageScoreBps`; no client calculates an authoritative score. Missing Procurement assessment means no official score even when self scores exist. Directory overview average uses only current official scores and an explicit eligible count/absence state, not fabricated zeroes.
3. Token issuance preflights mail. Disabled/unavailable mail writes nothing. Persist only token hash and request metadata; public inspect requires delivered, current, unexpired token. Failed send invalidates the token. Resend supersedes prior generation; cooldown/idempotency prevents duplicate mail. Submission consumes the token and writes the self assessment in one transaction; exact retry returns the same receipt without a second assessment.
4. Use vendor profile email as the sole recipient. Archive, email change, type change, expiry, and completed self assessment revoke eligibility. No raw token, recipient private details, or scores appear in logs/analytics/audit metadata beyond safe IDs and outcomes. Client fragment vault clears the URL immediately; public responses contain a strict minimal projection.
5. Staff assessment writes use expected current revision/version and actor identity. Concurrent edits return conflict with reload, preserving both history and audit. Update every affected vendor detail/list/overview/suggestion query. Keep private client caches partitioned by user/environment and clear on permission loss.
6. Deploy order, if separately authorized later: backend/model/index/API first, then web and mobile. Rollback hides new entry points and disables new writes while retaining assessment history. No existing-record rewrite is needed.
