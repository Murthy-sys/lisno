## Delivery boundary

Apply the approved compact typography, spacing, faded interior header, and content-driven widths to `/admin/projects`, `/client`, and `/admin/purchase-orders`. Keep the present grid/list, search/filter, client review, and both approval workflows. The three route slices are independent once the shared visual and data invariants below are agreed. No backend or API change, new business value, new dependency, or project-level purchase-order editor redesign is planned.

The worktree already contains Lead workspace TSX, test, CSS, specification, and plan edits from the prior task. Before any writer starts, capture `git status --short` and per-target diffs; preserve those Lead files and all other unrelated work. The new specification is also untracked. Do not stage, commit, push, deploy, seed, or mutate production.

## Shared contract for all writers

- Visual direction: compact but readable type and spacing; warm surface, restrained forest/sage palette, existing interior image with a soft directional fade; no harsh gradient, drop shadow, pure-white expanse, new decorative icon, hover animation, or skeleton loading UI. Image failure must leave copy and actions readable.
- Keep current authorized API data and stable IDs. Do not add derived financial values, fake counts, unsupported controls, or new permission rules. Approved Sales Manager estimate copy uses its existing approved baseline helper. Client approved-plan count remains client-visible-only. Purchase-order amounts retain their paise formatting, before-GST budget labels, submitted revision, decision reasons, version, and idempotency checks.
- Desktop data widths are chosen from real content inside the sidebar, with enough room for identity, descriptive text, amount, and actions. Intermediate/mobile layouts use explicit labels and a safe reading order. No page-level horizontal overflow or lost action at 200% zoom.
- Route-specific CSS may override legacy selectors. Shared `admin-home.css`, `access-administration.css`, `role-themes.css`, `purchaseOrders.css`, and application shell files remain read-only unless the primary agent assigns a narrowly scoped change after reviewing its impact. The project-level purchase-order editor must not inherit approval-only styling.

## Parallel ownership and integration

- In **Mode A**, T1, T2, and T3 can run concurrently after T0 because their source and test files do not overlap. Every writer is told that other agents share the worktree and must preserve their edits. The primary agent owns product interpretation, the shared contract, the approved documents, CSS-boundary decisions, and final reconciliation. An integrity reviewer follows the completed source changes; a verification runner checks the integrated worktree after writers stop. Tests run during concurrent edits are provisional.
- In **Mode B**, the primary agent completes T0–T5 inline and performs the equivalent integrity and verification review sequentially without implementation subagents.
- If a slice genuinely needs a shared file, the owner reports the exact selector or contract need before editing it. The primary agent assigns one writer and verifies nearby consumers. No two writers modify the same file.

- Synthetic rendered checks covered Sales Manager grid/list and Super Admin variant, Client dashboard, both approval queues and details, empty/error/permission states, desktop/intermediate/mobile widths, and a 720 CSS-pixel reflow check representing 200% zoom at 1440px. The three main routes had no document overflow, unexpected fixture request, or render error. Automated accessibility scans reported zero violations; the shared PageHeader/sidebar produced two indeterminate checks on the Sales and approvals routes.
- Actual browser zoom was not exercised. The adjacent project purchase-order panel was smoke-checked without overflow, but its synthetic fixture lacks two endpoints, so its populated appearance was not verified. The shared purchase-order stylesheet and editor source were unchanged.
