# Configuration-driven Main Line values across Estimation and Procurement

Date: 2026-10-05  
Status: Implemented; focused verification passed, with an adjacent existing tender approval-queue test failure

## Goal and standing product rule

Configuration is the source of truth for **every Configuration-owned value of a Main Line** wherever that Main Line is used. Saving a change must refresh current views and calculations for that same stable `mainLineId` across projects and workflows, without a manual “use updated source” step. This includes names, UOM and precision, mode rates and rules, low-quantity settings, recommendations and other configured sections wherever a current consumer uses them. User-entered project quantities and selling rates remain separate inputs. A project-only Procurement base-rate override, when present, wins for that project's line and never changes Configuration. The rule is recorded in repository operating guidance.

## Latest Main Line-wide correction (2026-10-05)

The user's latest instruction, “if anything updated in configuration that should get updated in every for that main line,” supersedes the previously approved active-revision-only behavior. For **current internal views**, use the latest saved draft revision for the same Main Line when one exists, otherwise its saved active revision. A save becomes visible without waiting for activation. If that draft is incomplete, show the specific missing/invalid value rather than falling back to another item or an old price. Activation remains the gate for sending newly priced vendor work. A valid configured value must flow to every live consumer of that Main Line, including an editable saved estimate draft, its catalogue/recommendations, Procurement Main Basket and its internal calculation, and any other current read projection that consumes that Configuration field. Resolve all joins by stable Main Line ID, not names.

Immutable approved estimate/customer amounts, approved review records/PDFs, already sent vendor BOQs, bids and issued orders remain historical snapshots. A current project screen may display live Configuration-derived internal values beside that history; a changed calculation invalidates draft/sent BOQ preparation so dispatch uses the existing revision flow. This distinction is about historical records, not an exemption for current Main Line views.

## Scope and behavior

1. Resolve every current configured consumer by stable `mainLineId`, never the displayed name. The latest saved draft takes precedence over active Configuration for current internal reads, including an active item's newly saved draft. If no draft exists, use its active saved revision. Do not require a copied estimate revision version/status to match before using a valid current configured value. An archived or deleted Main Line has no current source and must show a specific unavailable state.
2. Refresh Configuration-owned fields for the same Main Line in current Configuration screens, estimation catalogues/recommendations, editable estimate drafts, and Procurement/project projections that consume them. A saved estimate draft must rebase its configured identity, labels, UOM, source revision and configured default values on current Configuration when read and before its next save; it retains explicit user-entered quantity, classification and selling-rate decisions. Remove a manual “Use updated source” step for ordinary same-ID updates. If an UOM or precision change makes an entered quantity invalid or ambiguous, show a concise correction state; never silently convert it.
3. Keep approved estimate identity, selected lines, customer amount, approval history and published artifacts immutable. In current project views, recompute internal Configuration-derived values from the latest saved revision. Require valid item/UOM identity and scale before calculating; a changed UOM that cannot be safely reconciled remains unavailable with one useful issue. Never combine values from another item or a name match.
4. Explicitly Standard baskets use Sub-vendor automatically. Base amount comes from latest saved Configuration unless this project's approved source line has a project-only override. Total uses the canonical integer-paise calculator and current saved low-quantity rule at or below its limit. A Configuration change to limit/impact updates the total even with an override. Special and historical baskets retain their explicit mode-choice workflow but recalculate configured values for the selected mode from the same Main Line's latest saved Configuration. No revision/provenance message appears for a calculable Standard line.
5. Invalidate or refetch every affected current query family after a Main Line section, lifecycle, relationship or relevant master save, including estimation catalogue, recommendations and basket list/detail. Current views opened in another session refetch on return/focus. The backend resolves latest saved Configuration on each read; client invalidation alone is insufficient. A changed internal calculation updates the private BOQ preparation digest; draft/sent BOQs need the existing revise-and-resend flow. A draft-only current revision may show internal costs, but new vendor dispatch waits for activation. Pending awards and issued orders remain locked/history.
6. The project override remains scoped to its project and approved line. Clearing it returns to the then-current Configuration Base amount. Only Super Admin may change shared Configuration pricing through Configuration permissions; Procurement's project rate edit does not grant that permission. Internal costs must not enter the approved customer estimate, vendor-facing BOQ, vendor bid, or payable purchase-order amount.

## Risks and controls

- **Historical approval drift:** Recalculate only internal Procurement cost; preserve the approved estimate and use the changing preparation digest to prevent stale vendor work.
- **Draft safety:** A newly saved draft is the current internal source, even for an active item; incomplete or invalid values are explicit rather than silently falling back. Vendor dispatch remains blocked until the selected revision is activated and the BOQ is refreshed.
- **Cross-project or wrong-item pricing:** Resolve by stable Configuration and approved-source IDs; retain project override scoping and permission checks.
- **Invalid arithmetic:** Reuse the server's integer-paise mode calculator and inclusive low-quantity threshold. Do not calculate a price in React.

## Acceptance criteria

1. Saving a valid change to any consumed Configuration field for one Main Line updates that Main Line's current Estimation and Procurement/project views across at least two projects on read or refetch. An active item's new draft values appear immediately in current internal views; another Main Line, including one with the same name, does not change.
2. Reopening and saving an editable estimate draft uses current Configuration-owned Main Line fields without a manual rebase action, while its explicit quantity, classification and selling-rate inputs remain intact. A UOM/precision conflict asks for correction rather than silently changing entered quantities. Approved estimate history and published PDFs retain their prior values.
3. Standard Painting shows the latest saved Sub-vendor Base amount and low-quantity-adjusted Total; a project-only override remains effective until cleared, while updated configured limit/impact still applies. Special keeps its selected mode and refreshes that mode's configured calculation. Draft values can be displayed internally, but a new BOQ cannot be sent from an unactivated draft.
4. Missing item, incompatible UOM or invalid/incomplete mode settings show a specific issue; no another-item or old-revision fallback. A changed calculation invalidates stale BOQ preparation, preserves sent/awarded/issued history, and does not expose internal amounts to vendor-facing payloads.
5. Focused backend replica-set and frontend rendered tests, authorization/finance checks, typechecks/builds and repository diff hygiene verify all affected consumers without changing unrelated work.

## Assumption and open decision

“Everywhere for that Main Line” means every **current** screen or calculation that consumes its configured data. It does not mutate immutable approval history or already issued external artifacts. “Updated” means visible after saving a draft, even before activation, while activation remains required for new vendor dispatch. This expands the earlier approved lifecycle interpretation and is the material choice in this amendment.
