# Mode-aware purchase order preparation from the approved estimate

Date: 2026-10-04  
Status: approved base, mode-selection/live-calculation, and observed-content recovery amendments; Mode A implementation authorized

## Goal

Give Procurement a complete, expandable view of the approved estimate while preparing the project purchase order. At each configured main line, show the modes, cost inputs, margins, price references, quantity rules, and calculated results saved in Configuration. Procurement must see the financial effect of a chosen mode and the actual vendor order amount before sending one project request to Super Admin. The backend must calculate and preserve the values used in the decision.

The supplied `reference_docs/lisno-v104 (1) (1).html` was opened locally and inspected after selecting Karan, Procurement Head. Its project packages, BOQ rows, vendor enquiry, bid comparison, and awarded work-order sections are interaction and information-hierarchy references. It is a standalone prototype, so its demo data, formulas, role enforcement, and work-order actions are not application requirements or financial authority.

## Original baseline and current evidence

The following bullets record the baseline that led to the first approved implementation. They are historical context; the current purchase-order code and remaining gap are described immediately below.

- `frontend/src/features/procurement/ProcurementProjectPage.tsx` presents approved estimate items, editable procurement child items, and purchase orders as separate sections. `EstimateProcurementItems.tsx` displays the approved line hierarchy but filters out nonpositive estimate amounts. The project purchase order request panel shows only existing child rows grouped by broad section, without main-line expansion or mode selection.
- `backend/src/services/project-purchase-order-preparation.service.ts` reads the approved estimate source, creates broad sections, and fills them from active `ProjectProcurementItem` rows. An estimated main line with no procurement child is absent from the order detail. The preparation digest covers the source and child fields but has no chosen mode or configuration pricing snapshot.
- `frontend/src/features/procurement/ProjectPurchaseOrderRequestPanel.tsx` inserts 18% GST for every row, calculates a provisional total in the browser, and sends all current unordered child rows. The backend quote and submission calculate the authoritative PO lines in paise from each child row's explicit planned quantity, unit price, and requested GST rate.
- The approved estimate review snapshot retains stable room, main basket, sub basket, main line, revision, UOM, quantity, and approved selling amount fields (`backend/src/models/Estimate.ts`; `backend/src/services/estimate-client-review.service.ts`). The procurement source projection in `backend/src/services/procurement.service.ts` currently drops revision/version and UOM ID/precision. These must be carried through from the approved round; current labels must never be used as join keys.
- Configuration stores line-scoped mode calculation settings in the `advanced` section of a specific `AiEstimatorKnowledgeRevision`; its price/tax versions and quantity-margin section are separate. `backend/src/domain/ai-estimator-knowledge-configuration-context.ts` validates scoped settings. `backend/src/domain/ai-estimator-knowledge-mode-calculation.ts` contains the PMC, Sub-Vendor, and In-house formulas. Active/superseded revisions carry a content digest; draft revisions can change.
- The approved project-order contract in `docs/superpowers/specs/2026-10-01-procurement-purchase-order-vendor-client-completion-design.md` requires an explicit planned order quantity for each procurement child. Approved estimate quantity is a reference, never an automatic ordered quantity. One internal project request becomes separate vendor POs on Super Admin approval. Existing immutable requests, orders, approvals, allocations, and commitments remain authoritative.

### Current behavior and correction requested after the first implementation

- The current `PurchaseOrderEstimateTree.tsx` uses one flat selector with `PMC`, `Sub-Vendor`, and `In-house`, then displays `mode.preview` only after `Save mode decision` refetches preparation. Those calculators multiply the saved base rate by the confirmed quantity, apply the saved low-quantity impact at or below its limit, and then apply each mode's established margin and discount stages. The present service accepts an in-memory proposal during decision saving, but exposes no read-only proposal preview operation.
- Configuration stores separate scoped calculations for `pmc`, `sub_vendor`, `in_house_labor`, and `in_house_material`; its Modes interface groups the latter three under Execution. The purchase screen must expose that same hierarchy using each approved main line's saved, valid options. A currently active revision or a similarly named line cannot replace the approved line's pinned configuration.

### Observed digest mismatch in the saved project

- The reported Purchase screen shows four approved estimate lines. A read-only check of the local project data found an active pinned revision and saved mode sections for each line, but recomputing each revision's eight-section content digest disagrees with its recorded activation digest. The Configuration screen can display those current sections while Procurement refuses to use them. This is a content-integrity mismatch, not absent mode configuration.
- The section timestamps are all before their recorded activation time. That cannot prove the current financial fields equal the activated fields: a direct collection update can alter a mode rate without advancing `updatedAt`, as the new Procurement regression demonstrates. The activation audit holds the digest, not an immutable copy of the original section payload, so the historical values cannot be reconstructed from the current record. The cause of the local divergence is unproven. A timestamp-only or silent digest replacement would make an unverified rate appear activated.
- `No purchase item prepared under this main line` is a separate state: those lines have no `ProjectProcurementItem` supplier child. Selecting a configuration mode must not auto-create a vendor order item. The buyer still adds a child with explicit supplier, order quantity, agreed rate and GST when purchasing is intended.

## Observed-content recovery amendment

### Recommendation and alternatives

**Recommended: explicit Procurement review of current saved content.** Keep the recorded activation digest and label the current sections `Unverified saved values`. For the exact approved source line and pinned active or superseded revision, let the buyer inspect and preview valid PMC/Execution settings from the current sections, then enter a reason and explicitly confirm their use. This creates a procurement-owned, versioned exception; it does not claim the activated values have been recovered. The existing Super Admin order approval must show and explicitly acknowledge this exception.

The strict-block alternative requires new trustworthy activation evidence or a newly approved Configuration revision and cannot use the visible modes in the present project. The existing manual exception can order a supplier child with explicit commercial terms but produces no selected configured-mode calculation. Neither satisfies the requested purchase calculation. Silent re-hashing, timestamp trust, or borrowing the latest active revision is not acceptable.

### Source, financial and state contract

- On an active/superseded digest mismatch, return a distinct optional `integrity` state with the recorded activation digest and recomputed observed digest, plus candidate current mode availability for review. Keep normal mode `options` empty and `state` blocked until a buyer explicitly opts in; this preserves existing manual-exception eligibility. Do not return `ready` or enable quote/send merely because a mode is visible. Draft-revision and missing/invalid section rules remain unchanged. Show a concise line warning and the current calculation inputs without exposing raw digests in the normal buyer UI.
- A read-only preview for this case requires the approved estimate source identity, source-line key, expected decision version and observed digest. The server re-reads the exact pinned revision and validates its eight sections, UOM, selected mode, saved rate/margin/low-quantity rule and arithmetic. Label the result as a preview of **current unverified saved values**. It writes no Configuration or Procurement state.
- Saving a recovered mode requires the same expected source, decision CAS/idempotency and exact observed digest, plus an explicit buyer acknowledgment and a reason of at least ten characters. The server revalidates within the transaction. Add a nullable procurement-owned `integrityBasis` to the mode decision containing `kind: observed_unverified`, recorded activation digest, observed digest, reason, actor and time. Keep `revisionDigest` as the original recorded activation digest; never overwrite it with the observed digest. Normal verified decisions remain unchanged. A buyer can clear or replace the decision only through the existing versioned path; pending requests remain immutable.
- A recovered decision is usable only while the approved estimate source, pinned revision identity/version, activation digest, observed content digest, eight-section identity, UOM, selected mode and calculation all still match. Preparation, quote, submission and Super Admin approval independently revalidate these conditions. Any drift blocks ordering with a named stale-content conflict and requires a fresh review; no automatic reacknowledgment. Put the basis and calculated inputs/results into the preparation digest and immutable internal request snapshot. Existing order quantity, supplier rate/GST, approved estimate baseline and budget cap remain authoritative and separate from mode cost/selling.
- Super Admin sees the `Unverified saved values` provenance, buyer reason and frozen calculation beside vendor payable amounts. Approval of a request containing any recovered decision requires a distinct Super Admin acknowledgment reason, recorded with the approval audit even if no budget override is needed. Changes requested/rejected decisions retain the existing workflow. Vendors and Clients receive no internal mode rates or integrity details.
- If the current content is missing, invalid, changes during review, or no longer matches the acknowledged digest, keep the strict blocker and existing reasoned manual exception. Recovery fields are optional and omitted on ordinary decisions and snapshots, so existing pending-request preparation digests do not change. Historical decisions/requests remain readable. No Configuration record, approved estimate, existing request or vendor PO is rewritten; no data migration/backfill is part of this amendment. Rollback disables new recovery entry while preserving already frozen historical evidence for reading.

## Mode-selection and live-calculation amendment

### Buyer workflow and source matching

For each eligible approved **main line**, show `PMC` and `Execution` as the first choice. Choosing `Execution` reveals `Sub-vendor` and `In-house` as a second choice. Show an unavailable choice with a short reason when that exact pinned revision does not have a valid saved scope; never borrow another mode's rate, margin, UOM, or another line's settings. Map the two-stage UI to the existing persisted selectors `pmc`, `sub_vendor`, and `in_house`; one saved decision still belongs to one approved source-line key and can cover several procurement children. Basket and sub-basket headers remain grouping, not calculation identities. Existing historical manual-exception behavior stays separate from configured choices.

Suggest the approved main-line quantity in the calculation field when it is valid for the pinned UOM, but require the buyer to confirm and save the mode decision. A buyer may enter another valid quantity at that UOM's saved precision. Changing the top-level choice clears an incompatible Execution source in the *draft*; changing the Execution source or quantity recalculates only the draft. Neither action changes Configuration, an approved estimate, a procurement child, or an order. Clearly distinguish `Preview` from `Saved` values and keep quote/send unavailable until the current decision is saved and backend preparation is refreshed.

### Visible calculation contract

As soon as the selected leaf mode and quantity are valid, show a backend-calculated, read-only preview within that main-line expansion. Show the saved base rate and UOM, confirmed quantity, rounded base subtotal (`quantity × base rate`), low-quantity threshold, saved impact percent, whether impact applies, adjusted unit rate and adjusted cost, followed by the selected mode's configured margin, discount/floor and final internal selling or charge. At a quantity **equal** to the low-quantity limit, impact applies. An omitted impact retains Configuration's existing 10% compatibility default; an explicit zero remains zero. Preserve the existing calculator's order and half-up rounding stages: impact adjusts the unit rate before quantity multiplication, so it must not be reapplied to the rounded base subtotal. Quantity slabs and wastage suggestions remain separately labeled and do not become a hard minimum or an automatic order quantity.

For In-house, show labor and material base rates, low-quantity impacts and rounded results **separately**, then their summed result; do not use a single shared base rate. For PMC and Sub-vendor, show their respective configured margin and discount bases. A signed Sub-vendor balance is internal analysis, never a payable vendor PO amount. The approved estimate amount, the configured mode result, and the actual supplier quote remain separately named and reconciled. A mode base rate or calculated selling amount does not silently replace a child's agreed vendor unit price. The existing deliberate `Use configured rate` action may use only a uniquely matched vendor price version, not the mode base rate.

### Recommended implementation and alternatives

Add a **read-only procurement preview operation** that accepts project, approved estimate ID/version/review round, source-line key, expected decision version, and a proposed leaf mode, quantity, discount and In-house margin basis. It resolves the same pinned revision and calls the same domain adapter as saving a decision, within a consistent read snapshot; it returns named calculation stages, applied rules, source/version/digest and issues, without persisting a decision or writing Configuration. Register the protected operation and OpenAPI contract. The frontend cancels or ignores out-of-order previews and clears a preview whenever the source, choice or inputs change. Saving remains the existing versioned, audited operation and independently revalidates all inputs; a preview is never authority for a quote.

Keeping the current save-then-refresh interaction would preserve fewer API surfaces but does not let a buyer assess a mode or quantity before committing. Duplicating the calculator in the browser would give instant numbers but risks different rounding, stale Configuration and conflicting financial totals. The read-only backend preview is the recommended contract.

### Failure, compatibility and scope

Missing or invalid pinned settings, stale approved source, conflicting mode decision version, invalid UOM precision and unsafe arithmetic return specific line-level messages and no provisional amount. Retain the last **saved** calculation for reference, clearly marked stale when applicable; never leave an earlier draft preview attached to a newly selected choice. Preview reads must respect the existing project-scoped Procurement authorization and must not expose internal rates to Clients, vendors or unrelated roles. Keep existing saved flat mode keys, immutable request snapshots, vendor PO amounts, and historical records compatible; this amendment requires no migration or Configuration edit. Changes are confined to procurement-owned UI/API/projection code and tests. No external order is sent by previewing or saving a mode.

## Scope and decisions

### Recommended product model

Extend the existing project purchase order preparation, quote, submission, and Super Admin review path. The approved estimate supplies scope and identity; its saved configuration revision supplies mode settings; a selected vendor's valid price version is a reference for a proposed purchasing rate; the procurement child supplies the actual vendor, planned order quantity, agreed unit price, and allocation. Backend quotes reconcile the two financial views. One chosen mode belongs to an approved estimate **source line**, even when that line has several procurement children. Group headings are main baskets and sub baskets; Configuration does not have a separate basket-wide mode calculation that can safely be applied to every child.

Save the working source-line mode decision as an internal, versioned project/approved-round/source-line record so a multi-line preparation survives reload and concurrent editing. It records selector, confirmed calculation quantity, any permitted margin basis/discount, actor/time, and source revision identity. The request revision freezes the exact resolved settings, formula version, input quantity, calculation output, applicable price/tax version identities, vendor payable figures, and any documented variance. The decision record is preparation state, while the approved request revision and vendor POs remain immutable financial history.

### Alternatives considered

1. **Recommended: versioned line decisions plus backend quotes.** It supports resumable work, stale-source detection, a reviewable calculation trail, and one authoritative request total. It adds a small persistence/API surface.
2. **Submission-only mode choices.** It is a smaller data change but loses preparation on reload, complicates concurrent Procurement users, and weakens the explanation of how a reviewed amount was reached.
3. **Derive a vendor PO price directly from the configured selling price.** This would turn Lisno's margin into a vendor payable amount, potentially overstate commitments, and fail for In-house work and signed Sub-Vendor balances. It is unsuitable for the existing finance contract.

### Included behavior

- The main project request page shows all approved review-round estimate rows as an expandable tree: room → main basket → sub basket where present → main line. Stable IDs and the approved round determine grouping and order. Each row says included/excluded, approved amount, UOM/quantity, mode readiness, procurement child count, and ordering state. Approved included rows with zero amount and excluded rows remain visible for completeness, with no automatic PO line. An empty selected basket or a legacy row gets a clear reference state where the snapshot contains enough identity; the interface must not invent a main line.
- For an included, positive configured main line, Procurement can choose only a mode actually configured and valid in the pinned revision: PMC, Execution/Sub-Vendor, or Execution/In-house. The panel shows a concise mode summary first and expands to calculation details, relevant vendor child items, and blockers. A group-level bulk choice may be offered only when every targeted main line independently supports that mode; it must write separate line decisions with individual validation.
- Every approved source line remains visible even if it has no procurement child. Such a line says `No purchase item prepared` and contributes zero to the proposed PO. The summary counts these lines so they cannot disappear silently. Submission continues to include every eligible current procurement child, matching the established request contract; merely viewing an estimate line does not create an order or silently copy its quantity.
- A configured line with child items in the request needs a valid line mode decision and calculation, or a documented manual exception when historical configuration is unavailable. An In-house selection explains that internal labor/material cost does not itself create a vendor PO. Any external material or execution child still needs its own vendor commercial terms and explicit quantity.
- The PO review presents approved customer estimate amount, configured cost/price analysis, actual vendor order net, GST, gross, allocation, and variance as separately labeled figures. Super Admin sees the same frozen explanation and reason for a material difference before deciding. The existing approved estimate budget override and tax-inclusive child allocation controls still apply to the **actual PO amounts**.

### Outside this change

The prototype's enquiry messaging, bid collection/comparison, WhatsApp, payment tracker, and work-order document flow; automatic supplier selection; changes to the client-approved estimate; rewriting existing approved POs; and production migration/deployment are outside this change. The individual vendor-order route remains available for existing orders and explicit later amendments.

### Configuration is read-only

This change must not modify Configuration screens, settings, validation, calculation formulas, routes, services, models, collections, saved revisions, mode definitions, price/tax versions, UOMs, or basket data. In particular, no changes are planned in `frontend/src/features/ai-estimator-knowledge/` or Configuration-owned backend modules. Procurement reads the existing saved values and calls the existing domain calculators through procurement-owned code. New mode decisions and snapshots belong only to procurement records. A missing read capability or an unresolvable saved value becomes a procurement-side blocker or documented manual exception; it is not repaired by writing to Configuration.

## Source and configuration lineage

1. Use the approved client review round and approved design plan as the procurement gate. Preserve `estimateId`, version, review-round ID, source line key, room ID/name, basket/sub basket/main line IDs and approved labels, inclusion, approved quantity/UOM, and approved amount. The tree is a read projection of that immutable round. Names are display only.
2. Resolve configuration by that approved line's `mainLineId` and `revisionId`, including `sourceRevisionVersion` when present. For active/superseded revisions, verify the content digest and saved section identity. A mismatch remains a blocker unless the buyer follows the explicit observed-content recovery above for that same pinned revision; the resulting calculation is labeled unverified. A later active revision must not replace the pinned one. A draft that changed after estimate approval, an absent revision, an ambiguous mode scope, a missing UOM, or invalid settings gives a named blocker. No fallback to a different revision or name matching is allowed.
3. Mode availability comes from saved canonical selectors and scoped settings in that revision, with explicit legacy compatibility when the existing context resolver recognizes legacy fields. PMC, Sub-Vendor, and In-house values cannot inherit from one another. The line's saved UOM precision governs the calculation quantity. A price entry's vendor, UOM, specification and mode scope must match its child before it can be proposed as that child's rate.
4. Resolve a unique effective saved vendor price version and tax version at the proposed order date when one exists on the pinned revision. Show version, effective window, tax treatment, and the before-tax unit amount. Multiple matches, expiry, inactive/missing tax, or vendor/UOM mismatch are explicit unresolved states. The operator may use a validated manual agreed rate and tax with a required reason; no ambiguous rate is silently selected. A configured reference price is never substituted for the agreed vendor price without a deliberate `Use configured rate` action and confirmation.
5. If a historical approved line lacks configuration lineage or its draft settings no longer match the approved version, keep the line visible. A reasoned manual exception may permit its existing procurement child to proceed with explicit vendor terms and Super Admin visibility. The exception does not claim that a configured calculation succeeded, does not create settings, and never mutates the approved estimate. A missing line identity or contradictory estimate/child lineage remains a hard conflict rather than an exception.

## Calculation and money contract

All money is integer paise, percentages are integer basis points, quantities are canonical decimals validated to the saved UOM scale, and each existing calculator's documented half-up stages remain authoritative. The backend owns mode calculations, quote totals, validation, and persistence. The frontend formats server results and may perform only a consistency check.

| Source | What Procurement sees | Effect on payable PO |
| --- | --- | --- |
| Approved estimate | Customer-approved quantity, UOM, selling amount, and remaining pre-GST budget | Reference and existing approval cap; does not set order quantity or unit price. |
| Mode settings | Base cost, low-quantity limit, applied impact, adjusted cost, configured margin, calculated selling/floor or charge, and formula version | Cost/price benchmark and variance explanation; selling margin does not become vendor payable. |
| Quantity-margin and pricing sections | Applicable quantity slab or gap status, wastage-derived procurement quantity suggestion where configured, uniquely effective vendor price and tax treatment | A suggestion only until operator confirms a child quantity/rate/tax. A slab lower bound is a pricing boundary, not an invented supplier MOQ. |
| Procurement child and PO quote | Vendor, UOM, explicit planned order quantity, agreed pre-tax unit price, GST, net, GST amount, gross, allocation | Sole source of vendor payable PO lines and commitments after the backend validates it. |

- The operator confirms a calculation quantity at the main-line level. The approved estimate quantity is shown beside it as reference. A sum of child order quantities can be proposed only when every child shares a compatible saved UOM; mixed UOMs require an explicit line calculation quantity. Neither suggested calculation quantity nor a wastage/procurement quantity automatically sets a child's ordered quantity.
- `lowQuantityLimit` activates the saved impact **at and below** the boundary, including equality. An omitted impact uses the existing 1,000-bps compatibility default; an explicit zero stays zero. Quantity slabs use their existing lower-inclusive/upper-exclusive and gap rules. A minimum slab quantity or low-quantity limit is not a hard order minimum. If a future or existing explicit supplier minimum exists on the matched price source, validate it separately and identify that source.
- PMC and Sub-Vendor use the existing adjusted-cost, gross-margin division, and their different discount bases. PMC's discount reduces its charge while preserving adjusted cost. Sub-Vendor's `finalVendorChargesPaise` is a signed remainder and can be negative; it is never copied into a PO line. In-house rounds labor and material independently, respects each minimum gross-margin floor and the combined discount cap, then sums components. Do not apply a quantity slab adjustment again to a mode `baseRatePaise` unless the existing domain calculator defines that composition explicitly.
- Configured selling totals and customer estimate totals are before GST unless explicitly labeled otherwise. A unique vendor price version with inclusive tax must be normalized to its stored before-tax amount before use as a suggested PO unit price. The actual PO GST rate is explicit per child, checked against a matching tax source where available, and never silently defaults to 18%. The backend applies the established PO line rounding once to `quantityMilliUnits × unitPricePaise ÷ 1000`, then the line GST rate; sums of rounded lines form vendor, section, and project totals.
- A line with multiple procurement children gets one configured line benchmark, not one full benchmark per child. Actual child nets and taxes aggregate under that source key; each child's allocation cap is checked independently against its tax-inclusive actual amount. A material configured-cost/actual-cost variance is visible with a reason required by the internal review policy; the exact threshold, if any, must be a named policy value and must never alter the PO arithmetic.

## State, failure handling, and compatibility

`approved estimate + approved design → derived preparation → saved mode decisions → backend quote → immutable pending request revision → Super Admin decision → separate approved vendor POs` is the proposed path. A rejected request stays historical. Changes requested lead to a new immutable revision. Concurrent Procurement edits use compare-and-swap; quote/submit fail with a named conflict when a source, configuration, price, tax, quantity, allocation or prior order changed. Transaction rollback prevents partial requests or vendor POs.

Existing approved requests and vendor POs remain readable with their historical amounts. New fields are additive and nullable for historical records; no retroactive mode calculation is presented as historical truth. No existing approved estimate, finance baseline, vendor allocation, or purchase order is rewritten. New indexes or schema changes require a dry run, backup/rollback and conflict report before any separately authorized live migration. This specification does not authorize seeding, backfill, deployment, publishing, or production mutation.

## Risks and mitigations

| Risk | Required control |
| --- | --- |
| Current Configuration differs from the approved line's saved revision | Pin by stable revision/version/digest; fail or use a visible reasoned historical exception. |
| An active revision's current sections do not match its activation digest | Never infer unchanged prices from timestamps or silently replace the digest. An explicit, reasoned Procurement decision may use the current pinned content only under an observed-digest guard, with unverified provenance frozen for Super Admin review. |
| Selling margin mistaken for vendor cost | Label benchmark versus vendor payable and keep actual PO net tied to explicit child rate/quantity. |
| Same names across rooms/baskets or multiple children under one line | Join by approved source key and stable IDs; aggregate without multiplying the line benchmark. |
| Quantity or tax inferred without authority | Require explicit child quantity and GST; show saved price/tax and wastage only as resolvable suggestions. |
| Concurrent edits or approval race | Re-fetch, compare versions/digests, serialize within transactions, preserve idempotency and immutable revisions. |
| Internal price disclosure | Separate internal request snapshot from vendor/client projections and test role-specific access. |
| Large estimate performance | Batch source/config reads and keep expansion rendering bounded. |
| An unsaved preview is mistaken for a saved financial decision | Label draft and saved states separately; invalidate previews on every source/input change and require the existing versioned save before quote. |
| A configured calculation is mistaken for a supplier payable rate | Keep mode cost/selling beside, but distinct from, the actual vendor child rate and backend quote; never copy the mode base rate to the PO. |

## Assumptions and open decisions

- **Assumption for approval:** “all estimated items” means all rows in the approved review-round snapshot should be visible. Excluded and zero-value rows are reference-only until a separately approved scope change or explicit existing amendment path makes them orderable.
- **Assumption for approval:** “minimum quantity” refers to the saved low-quantity impact limit and quantity-pricing slab boundaries now present in Configuration. Neither is an implicit supplier minimum order quantity. A separately stored supplier MOQ, if discovered in the matched price source during implementation, will be shown and validated as its own rule.
- **Assumption for approval:** Configured mode costs and margins are internal analysis. The actual vendor PO remains based on the supplier's confirmed quantity, rate, and GST; a uniquely matched configured vendor price can be applied only by an explicit user action. This preserves existing finance commitments and makes the selected mode consequential through calculation, variance review, and audit.
- **Assumption for this amendment:** “Selected items” means the approved main-line rows in the Purchase orders hierarchy. One mode and calculation quantity apply per source main line, while any linked vendor purchase items retain individual order quantities and commercial terms. The first-stage Execution choice is a UI grouping; the stored decision remains the existing `sub_vendor` or `in_house` key.
