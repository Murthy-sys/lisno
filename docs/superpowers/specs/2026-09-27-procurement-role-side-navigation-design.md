# Procurement dashboard and shared vendor screen

Date: 2026-09-27  
Status: Proposed for approval  
Classification: High-risk authorization and vendor workflow change across frontend and backend.

## Goal

For Super Admin and Procurement users, the web side navigation must show an expandable **Procurement** parent with two children: **Dashboard** and **Vendors**, matching the user's supplied reference. For Procurement users, Dashboard shows the existing project procurement workspace and its project budget/spend information, as pictured. Super Admin's Procurement Dashboard is separate from its existing global Dashboard. Vendors opens one shared vendor directory and Add vendor experience for both roles, so later vendor UI changes appear without maintaining a second copy. The user confirmed that Procurement staff should have **all current Super Admin Procurement actions**, including edit, archive, inline basket creation, private document and photo operations, and historical allocation correction. Those actions require backend authorization, not only a visible tab.

## Current behavior and evidence

- The original missing-tab report was clarified: the Procurement role already has a flat **Procurement** side-nav item. `frontend/src/app/routeRegistry.ts` links it to `/procurement`; `frontend/src/app/router.tsx` renders `ProcurementWorkspace`, the project list shown in the reference image. Its cards already display selected estimate value, recorded spend, and remaining selected value. `Sidebar.tsx` renders flat links only; the narrow-screen drawer reuses it. The existing navigation tests passed 68/68 and focused procurement router tests passed 8/8 in the initial investigation. The needed change is a nested menu, a separate Vendors route, and authorization.
- Super Admin's flat `/admin/procurement` link renders `ProcurementVendorDirectory` through `ProcurementManagementPage.tsx`. An Admin/Sales Manager gets project vendor suggestions from that route. The page currently rejects the `procurement` role, while the directory gates itself on `ai_estimator_knowledge.configuration.*` permissions. The current vendor page contains a vendor overview with backend-supplied total, active, and under-review counts; its Average KPI is explicitly unavailable.
- The shared directory/editor uses `/admin/ai-estimator-knowledge/vendors` for vendor list, full detail, create, update, archive, private certificate/photo, and historical allocation review/correction. It also reads Main Basket/Sub Basket catalogs and can create those classifications inline. The full detail includes private identity, address, banking, and document data; the directory list uses a safer summary projection.
- The backend route-operation registry and `AiEstimatorKnowledgeActorGuard` currently restrict these operations to the sole active Super Admin. Procurement has `procurement.vendors.read/create` for the separate `/procurement/vendors` minimal picker and name-only quick-add, plus `procurement.workspace.read` for project work. These do not authorize the full vendor profile. The prior vendor-profile specification explicitly kept Procurement away from private profile data; this request deliberately changes that decision.
- The existing `/home` role landing also renders `ProcurementWorkspace`, and `/procurement/projects/:projectId` hosts project work. The full vendor directory and the name-only project picker use the same stored vendor IDs and collection.
- Initial worktree inspection was clean. This specification is the only file created for the current request; no product code or live data has been changed.

## Required behavior and scope

1. For `super_admin` and `procurement` only, replace the flat Procurement link with one expandable Procurement parent containing exactly **Dashboard** and **Vendors**, in that order. Clicking the parent toggles the submenu; each child navigates to a distinct route. Keep the group expanded while either child or a nested project route is active. Desktop sidebar and responsive drawer must agree. The menu is keyboard operable, has an accessible expanded state, clear child focus/active states, and closes the drawer after child navigation. Existing Admin/Sales Manager project-suggestions navigation remains flat and unchanged.
2. Match the supplied navigation reference: use the existing light rail and typography; make the expanded Procurement parent a dark olive full-width row with its cart icon and upward chevron; indent the two children beneath it; show the active Dashboard/Vendors row on a pale olive surface with a slim green indicator at its left; use muted text/icons for inactive children. Keep the established focus treatment and adequate contrast. Do not add decorative animation or a new icon library. The same hierarchy must fit the narrow-screen drawer.
3. Use `/procurement` for the Procurement-role Dashboard and preserve its existing `ProcurementWorkspace` heading and project cards, including estimate version, project identity, Design-approved status, selected budget, recorded spend, and remaining selected value. This is the screenshot's main content. The same workspace remains accessible from `/home` and nested project routes. Do not replace it with vendor-count cards.
4. Use `/admin/procurement` for a Super Admin Procurement Dashboard, separate from `/admin/dashboard`. Initially show available backend-derived procurement vendor counts (total, active, under review); do not fabricate the unavailable Average KPI, finance totals, or project metrics. This is an initial metrics view for the Super Admin role while future procurement metrics can be added from defined backend sources. The Admin/Sales Manager branch of `/admin/procurement` continues to show project vendor suggestions.
5. **Vendors** uses `/admin/procurement/vendors` for Super Admin and `/procurement/vendors` for Procurement. Both render the same existing `ProcurementVendorDirectory` component and data, including its vendor overview, search, filters, pagination, detail panel, and Add vendor. Preserve the current Super Admin Vendor screen's content rather than splitting or recreating it. Vendor actions and future additions use the same shared component for both roles.
6. Give Procurement users every operation currently reachable from the Super Admin Vendors screen: read full vendor detail and private photo/MSME certificate; create full vendor profiles; update profile, verification, status, photo, and certificate; archive vendors; create Main Baskets and Sub Baskets inline; and view/record missing historical allocation baselines. The existing server-side validation, versions, idempotency, audit, upload cleanup, vendor allocation cap, and transaction behavior remain authoritative.
7. Keep role-specific project procurement available on `/home` and its existing project-detail URLs. The project-workspace data and name-only `/procurement/vendors` API picker/quick-add contracts remain compatible. Do not replace stored vendor identities or duplicate the vendor registry.
8. Preserve Super Admin's existing vendor-management capabilities and Admin/Sales Manager's project-suggestions screen. Other roles, inactive accounts, stale-role sessions, and missing permission snapshots remain denied. Future vendor UI changes should be made in the shared directory/editor; new backend operations still need explicit scoped authorization and API registration.

Out of scope: granting Procurement the general Configuration tool, item/price/tax/quality-control administration, unrelated Super Admin routes, finance ledger editing, native mobile screen changes, new vendor models, migrations/backfills, deployment, production mutations, or speculative future Procurement submenu items. This request targets the web screen the user compared with Super Admin.

## Recommended authorization and API approach

Reuse the existing vendor and classification endpoints and their services, but authorize them by **operation-specific Procurement capabilities**. Do not add `ai_estimator_knowledge.configuration.*` to the Procurement role and do not broaden the generic knowledge actor guard for all master types. Introduce a vendor-scope active-actor guard that accepts the sole active Super Admin or an active Procurement actor, coordinating writes inside the existing transactions. Apply it only when the requested master type is `vendors`, to the specific basket/sub-basket list and inline-create operations used by this screen, and to the vendor photo, certificate, and allocation-baseline services. Other knowledge operations keep the sole-Super-Admin guard.

| Capability | Operations exposed to Procurement and Super Admin |
| --- | --- |
| Vendor directory read | Vendor list/detail; private vendor photo and certificate reads; upload policy; Main Basket/Sub Basket list for selection; historical allocation list. |
| Vendor create | Full-profile `POST /admin/ai-estimator-knowledge/vendors`; stage a certificate for a new vendor. |
| Vendor update | Full-profile PATCH, status/address-verification edit, photo replace/remove, and certificate stage for an existing vendor. |
| Vendor archive | Vendor archive with existing reason, reference, and version checks. |
| Classification create | Only the Main Basket and Sub Basket create endpoints used inline in the vendor editor. |
| Historical allocation correction | The existing baseline completion endpoint, with its reason, integer-paise, version, vendor-allocation, idempotency, and audit rules. |

Define distinct permission codes for these capabilities in the canonical backend/frontend authorization contracts and grant them to `procurement`; Super Admin continues to have all codes. Re-map only the listed backend route operations to these permissions. Retain the existing configuration permissions and service guard on all other AI-estimator knowledge operations. The new Vendors frontend routes require vendor-directory read; the existing `/procurement` Dashboard keeps `procurement.workspace.read`. `/admin/procurement` remains the Admin/Super Admin shared URL, so its outer route guard must continue to admit Admin for project suggestions; the role-specific Super Admin Dashboard branch additionally requires vendor-directory read before loading metrics. `/procurement/projects/:projectId` and `/home` retain their project-workspace permissions. In the shared component, derive each action from its corresponding capability so a reduced or stale snapshot cannot show a button that its API denies. The backend route operation and stored actor check remain decisive. Keep OpenAPI and route-operation inventory synchronized.

Extend the registry-derived navigation model with a permission-filtered group rather than hard-coding two role-specific menus. Parent visibility requires at least one permitted child. The active child is announced on its route, and the parent reflects active descendants. The Procurement Dashboard child remains active on `/procurement/projects/:projectId`; the group starts expanded on any Procurement child or nested project route and retains an intentional user toggle on other routes. Existing role navigation remains flat. `/admin/procurement` and `/procurement` are the respective Procurement Dashboard routes; the old Super Admin vendor URL remains a valid landing route but now shows Dashboard, with Vendors one child away. Update safe return-path handling to accept both new Vendors routes without broadening other role returns.

This approach keeps one vendor model, one validation path, and one editor. A separate copied directory or broad Configuration grant would increase drift or expose unrelated administration. If a generic knowledge route cannot be narrowed safely by master type, add a vendor-specific API alias that calls the same domain service and checks the same capability; never weaken the generic guard globally.

## Data, compatibility, failures, and side effects

- Existing vendor IDs, profile shapes, basket/sub-basket arrays, project references, cached query keys, and minimal picker projections remain unchanged. A vendor added by Procurement appears in the Super Admin directory and existing project vendor selectors; a Super Admin change appears in Procurement after normal query invalidation/refetch.
- The Procurement-role Dashboard keeps its existing project procurement query and backend-derived budget/spend figures; the Super Admin Procurement Dashboard uses the existing vendor-directory overview response as its initial source of truth. Loading, empty, and error states identify unavailable data rather than showing invented zeroes. The Vendors screen retains its directory and overview data contracts.
- The full-detail response contains sensitive personal and banking fields. Return it only from explicitly authorized detail routes with `private, no-store`; keep list/overview projections free of those fields. Document and photo bytes remain behind authenticated streaming endpoints with opaque storage references and established size/type checks. Do not place private fields in audit events, optimistic list caches, error messages, or test output.
- Preserve one active Super Admin identity invariant. A Procurement mutation validates its stored active role in the same coordinated transaction without impersonating Super Admin. Role revocation and stale sessions fail closed. All writes preserve actor identity, version/CAS checks, deduplication, audit, idempotency, compensating file cleanup, and Mongo replica-set transaction semantics.
- Missing catalogs block invalid vendor saves; a failed list, detail, upload, archive, or baseline request shows the existing retry/conflict state. Permission loss produces a denied state without exposing cached private detail. No UI-generated substitute data is allowed.
- Backend/frontend deployment must be coordinated: the frontend should not expose the shared directory until its scoped backend operations are available. No data migration is needed. Rollback can restore the prior route/permission mapping without changing vendor records, but any new Procurement-created records remain valid shared vendors.

## Verification and remaining risk

Use distinct Super Admin, Procurement, Admin, and unauthenticated identities in authorization tests, including stale-role and inactive Procurement cases. Assert allowed vendor-specific operations and denied item/tax/quality-control operations, including direct API calls. Exercise safe list versus private detail/doc responses. Test menu toggle and child activation with mouse, Enter, Space, and keyboard focus in desktop and narrow drawer layouts. Verify the pictured project workspace values and the Super Admin's vendor Dashboard counts, including unavailable states without fabricated values. Test lost-response retries, competing versions, duplicate vendor names, failed uploads and cleanup, invalid basket parent IDs, archived vendors, and allocation races using a Mongo replica set where relevant. Run focused frontend/backend suites first, then contract and build checks, and visually confirm Dashboard, Vendors, and Add vendor interactions in both roles at desktop and narrow widths.

The main risk is accidental access to unrelated Configuration data or exposing sensitive vendor detail through a broad guard, route mapping, cache, or log. Other risks are broken deep links when the Super Admin vendor page moves and regression in the existing Procurement project workspace while the sidebar structure changes. The route map, permission matrix, shared-component approach, and cross-role checks above address those risks.
