# Main Line Budgeting Simplification Design

**Status:** Approved
**Date:** 2026-09-02
**Scope:** Configuration → Main Basket → Main Line → Mode → current Pricing/Price versions workflow
**Presentation superseded:** User-facing Pricing/Price versions terminology and the technical price-entry form described by the existing AI Estimator Knowledge specifications. Internal `pricing`, `priceEntries`, and immutable price-version contracts remain authoritative.

**Revision:** Budgeting now no longer exposes Tax as a choice. New and updated
budgets use the system-owned, exclusive GST 18% policy. GST is added to the Unit
budget; for example, a ₹100.00 Unit budget produces ₹18.00 GST and a ₹118.00
total. Existing immutable historical prices retain their original Tax lineage and
amounts.

## Decision summary

Replace the technical **Pricing / Price versions** experience with a task-oriented
**Budgeting** experience for the Super Admin:

- the visible section name becomes **Budgeting**;
- the visible list name becomes **Budgets**;
- **Add Price version** becomes **Set budget**;
- **Replace price version** becomes **Update budget**;
- each budget is a compact expansion panel instead of one permanently expanded
  technical record;
- only Vendor, Unit of measure, Unit budget before GST, Starts on, and optional
  Ends on remain user-editable;
- the Tax selector, Add tax action, Tax prerequisite warnings, and Tax-catalog
  loading dependency are removed from Budgeting; and
- command, lineage, tax-version, tax-treatment, lifecycle-status, and legacy Mode
  fields are owned and resolved by the backend and never become UI inputs.

**GST is a fixed backend policy, not a form choice.** New and updated budgets
always use the canonical system-owned `GST 18%` rule and immutable version at
1,800 basis points with `exclusive` treatment. The preferred `set_budget`
request contains no Tax field. The backend verifies and persists the canonical
Tax lineage, derives GST and the total in paise, and fails closed if that policy
is unavailable or invalid.

**Price operation is required by the persistence protocol but is not a business
choice.** A new backend-owned `set_budget` command will accept only business
inputs. The backend decides whether to create a new immutable version or retain
an unchanged `reference`; legacy `append` remains compatibility-only and is not
generated by the new UI.

**Mode is not needed in this Budgeting form.** The current field is a legacy
reusable `modeId`, not the fixed PMC/Execution choice used by the Main Line Mode
configuration. The current estimator intentionally uses the same unscoped price
for PMC, Execution, Sub-Vendor, and In-house requests. New budgets therefore
remain shared and submit `modeId: null`. Existing legacy mode-scoped records are
preserved without exposing or silently changing their stored scope.

Separate PMC and Execution budgets would require a new immutable price
`modeKind` contract, resolution precedence, indexes, compatibility rules, and
possibly an `executionSource` dimension. That is deliberately not introduced by
this simplification.

## Goal

Allow an authorized Super Admin to set the estimator's unit budget using familiar
commercial inputs without seeing storage/versioning mechanics or being able to
select an invalid command state.

The completed experience must:

1. explain what the budget controls;
2. keep the form compact until a budget is selected or created;
3. have the backend generate and resolve every technical identity, fixed-GST,
   lifecycle, and persistence field;
4. preserve immutable financial history, auditability, and optimistic
   concurrency;
5. keep server-derived tax totals and estimator results authoritative; and
6. prevent a newly written set of budgets from being ambiguous to the estimator.

## Current behavior and evidence

### The UI exposes the wire protocol

The current row in
[`KnowledgeSectionEditor.tsx`](../../../frontend/src/features/ai-estimator-knowledge/KnowledgeSectionEditor.tsx)
shows all of the following together:

- Price operation;
- Price entry ID;
- Vendor;
- UOM;
- Mode;
- Tax rule;
- Tax version;
- Input amount;
- Tax treatment;
- effective dates; and
- Version status.

A new row initially contains only `operation: "append"`, a generated
`priceEntryId`, and `specificationId: null`. As a result, the screen presents
internal identifiers and an incomplete protocol object before the user has made
a business decision.

### Price operation is internal state

The strict pricing command union in
[`backend/src/contracts/ai-estimator-knowledge.ts`](../../../backend/src/contracts/ai-estimator-knowledge.ts)
has two purposes:

- `append` asks the backend to create and audit a new immutable price version;
- `reference` retains an existing version without creating a duplicate.

The item service materializes an append command, derives base/tax/total amounts,
writes the immutable version and audit in one transaction, and stores a compact
reference in the section. Allowing a Super Admin to select `reference` on a new
row is therefore misleading and can only create an unusable row.

### IDs are lineage, not form inputs

`priceEntryId` groups successive immutable versions. `priceVersionId` identifies
one exact stored version. Both are needed for history, cloning, CAS-safe updates,
context lineage, and audit, but neither helps the user set a budget.

### Tax is fixed and is not a Budgeting choice

The current preferred Budgeting request still requires `taxRuleId`, and the UI
still blocks on the Tax catalog, renders a Tax dropdown, and offers Add tax.
That contradicts the confirmed business rule that estimator budgets always use
one exclusive GST rate of 18%.

The repository already defines canonical stable identities for `GST 18%` in the
AI Estimator Knowledge bootstrap manifest:

- Tax rule: `knowledge-tax-bootstrap-gst-18`;
- Tax version: `knowledge-tax-version-bootstrap-gst-18-v1`;
- rate: `1,800` basis points;
- treatment: `exclusive`; and
- effective window: from `2026-08-28T00:00:00.000Z`, with no end date.

For every new or updated budget, the backend must require that:

- the canonical Tax rule is present and active;
- the canonical Tax version belongs to that rule, is active, and exactly matches
  the fixed rate and treatment;
- the Tax version covers the complete price effective interval;
- the command treatment exactly matches the Tax version treatment; and
- base, tax, and total paise are derived on the server.

The user supplies no Tax choice. The backend binds those canonical identities and
amounts. Looking up Tax by a mutable label/code, choosing the first Tax, trusting
a client-supplied Tax ID, or calculating GST in the browser is prohibited.

### Version status is a system decision for this workflow

Only active, currently effective price versions participate in estimator
resolution. **Set budget** is an explicit instruction to create an active budget.
Draft copies that require review remain identifiable through their existing
`reviewRequired` data and must be presented as **Needs review**, not as a raw
status selector.

### The displayed Mode field is obsolete

The Main Line configuration owns exactly two fixed Mode choices—PMC and
Execution—using canonical `modeKind`. Execution may separately distinguish
Sub-Vendor and In-house configuration.

The price form instead writes `modeId`, which references the legacy reusable
Mode collection. Immutable price versions do not currently store `modeKind`.
For a context request containing canonical `modeKind`, the resolver deliberately
selects only `modeId: null` price versions. Existing integration coverage proves
that PMC, Execution, Sub-Vendor, and In-house share that same unscoped price.

Therefore, replacing the current Mode options with PMC and Execution labels would
write false identity and must not be done.

### Price versions are still the estimator source

The new priced Quantity slab displays `Quantity × Unit rate`, but it is not yet
the runtime estimator price source. Immutable price versions must remain behind
the Budgeting facade until a separately approved estimator-source change is made.

### Existing ambiguity across Vendors

Vendor is stored in the immutable price scope, but context requests have no Vendor
selector and effective-price resolution does not filter by Vendor. Two retained
active budgets for different Vendors but the same UOM and overlapping dates can
therefore be accepted by the current scope check and later produce
`NO_UNIQUE_EFFECTIVE_PRICE`.

The simplified workflow must not create new ambiguity. When a save contains a
new or updated budget, the resulting retained active set must have at most one
effective budget per revision, UOM, legacy Mode scope, and time window,
regardless of Vendor. Reference-only compatibility saves must not rewrite
or newly reject untouched historical data.

## Product requirements

### 1. Terminology

Use business language throughout the Main Line workspace:

| Current visible wording | New visible wording |
| --- | --- |
| Pricing | Budgeting |
| Price versions | Budgets |
| Add Price version | Set budget |
| Replace price version | Update budget |
| Input amount (rupees) | Unit budget (₹, before GST) |
| Effective from | Starts on |
| Effective to | Ends on (optional) |
| No price versions configured. | No budgets set. |

The internal section key remains `pricing`; the internal array remains
`priceEntries`; the Mongo collection and audit entity remain price versions.
Technical identifiers, API enums, and historical documents are not renamed.

Main Line Overview, conflict review, validation summaries, save-error messages,
and accessibility labels must use **Budgeting/Budget** consistently when they are
visible to a Super Admin.

### 2. Information hierarchy

Within the consolidated Mode workspace, keep the established order of
Specifications, Priority, Vendors, and the pricing-backed content. Replace the
last content block with:

```text
Budgeting                                      [Set budget]
Set the unit budget used by the estimator. Complete the details, then Save Mode.

▸ ₹120.00 per sq ft · Acme Vendor · Starts 2 Sep 2026
▾ New budget
   Vendor                 Unit of measure
   Unit budget (₹, before GST)
   Starts on              Schedule options
   GST is fixed at 18% and is added when you save.
```

Do not restore the removed standalone Pricing tab or add another workspace tab.

### 3. Budget expansion panels

Use a dedicated Budget builder rather than changing the shared generic repeater
for every section.

- Saved budgets load collapsed.
- A newly created budget opens automatically.
- Selecting **Update budget** opens that budget in editable form.
- At most one budget panel is expanded at a time.
- The panel trigger is the readable summary, not a raw ID or version number.
- A valid summary uses Unit budget, UOM, Vendor, and Starts on.
- When data is incomplete, use **New budget** or **Budget needs attention**.
- Remove the up/down controls because price-entry order has no estimator meaning.
- Keep a clearly named **Remove budget from this Draft** action. Removing a
  reference from a Draft does not delete immutable historical records.
- **Set budget** changes the local Mode draft only. Helper copy must make clear
  that **Save Mode** persists it.

### 4. Visible editable fields

Show these controls in this order:

1. **Vendor** — required active Vendor master; retain the existing permitted
   Add vendor action.
2. **Unit of measure** — required active UOM master; retain the permitted Add
   Unit action.
3. **Unit budget (₹, before GST)** — required non-negative rupee amount with at
   most two decimal places.
4. **Starts on** — required; a new budget defaults to the current local date and
   time but remains editable.
5. **Schedule options** — a secondary disclosure containing **Ends on
   (optional)**. It is collapsed when there is no end date and expanded when an
   end date exists or has an error.

Always use **Unit budget (₹, before GST)** with the helper **GST is fixed at 18%
and is added when you save.** The UI does not infer or persist GST. After save,
the collapsed detail shows only the server-returned Amount before GST, GST, and
Total including GST.

### 5. Fields removed from the UI

The following must not be visible, focusable, or user-editable in Budgeting:

- Price operation;
- Price entry ID;
- Price version ID;
- Tax rule and Tax selector;
- Add tax, Retry Tax, and missing-Tax controls or warnings;
- Tax version;
- Tax treatment as a control;
- Version status;
- Version number;
- Mode; and
- reorder controls.

These removals apply to the editor and to its user-facing conflict-review
projection. Overview must use business summaries rather than exposing the same
technical metadata under another heading.

### 6. Backend-owned Budget command and mapping

Extend the Pricing section command union with a business-facing
`set_budget` command. The UI creates this command from visible fields but does
not supply persistence, lifecycle, or Tax-version mechanics.

```json
{
  "operation": "set_budget",
  "sourcePriceVersionId": null,
  "vendorId": "knowledge-vendor-id",
  "uomId": "knowledge-uom-id",
  "inputAmountPaise": 12000,
  "effectiveFrom": "2026-09-02T10:00:00.000Z",
  "effectiveTo": null
}
```

`sourcePriceVersionId` is omitted/null for a new budget and is an opaque hidden
reference for an explicit Update budget action. It is never displayed or entered
by the Super Admin.

The backend maps `set_budget` to the established immutable price model inside
the existing section-update transaction.

`taxRuleId`, `taxVersionId`, treatment, rate, and calculated amounts are not
accepted on `set_budget`.

#### New budget

The client sends only Vendor, UOM, amount before GST, and effective dates. The
backend:

- generates the opaque `priceEntryId` and `priceVersionId`;
- internally materializes the operation as a new immutable append;
- sets `specificationId: null`;
- sets `modeId: null` because canonical PMC/Execution share the budget;
- binds the canonical GST 18% rule/version stable IDs after verifying the exact
  system policy and complete effective interval;
- assigns `treatment: "exclusive"` and `rateBps: 1800` from backend policy;
- sets `status: "active"`;
- derives base, tax, and total paise; and
- stores the resulting section entry as the existing compact `reference`.

#### Unchanged saved budget

The UI retains the server-returned reference internally. The backend:

- validates that the reference belongs to the same Main Line and revision;
- retains the same `priceEntryId` and `priceVersionId`; and
- creates no new price version or price-version-created audit event.

#### Updated saved budget

The UI sends `set_budget` with the hidden `sourcePriceVersionId` and the edited
business inputs. The backend:

- requires the source version to be one of the references retained by the
  previously read Pricing section;
- resolves and retains its existing `priceEntryId`;
- generates the next immutable `priceVersionId` and version number;
- binds canonical fixed-GST linkage and all other hidden fields again;
- when the source is a historical inclusive budget, initializes the editable
  before-GST amount from its authoritative `baseAmountPaise`, never its inclusive
  `inputAmountPaise`;
- treats the explicit Update action as active/reviewed;
- writes the new version and audit atomically; and
- leaves every prior immutable version unchanged.

If the source has a non-null historical `modeId`, the backend preserves that
scope during update. It never accepts a client-supplied replacement Mode or
silently converts the source to PMC, Execution, or shared scope. If the source
scope cannot be validated safely, the transaction fails and the UI keeps the
record readable with an actionable historical-scope message.

#### Legacy command compatibility

Existing `reference` requests remain accepted unchanged. Compatibility
`append` remains non-UI and is accepted only when its supplied Tax rule, version,
rate, and treatment resolve to the canonical fixed GST 18% policy. It must not
remain a bypass for writing a new noncanonical tax price. Historical versions
using other rates or inclusive treatment remain readable and immutable.

### 7. Backend fixed-GST policy and provisioning

The backend uses the canonical stable identities and values already defined by
the bootstrap manifest. It must not silently create or modify this system policy
during Save Mode. A financial edit must not become an implicit data-provisioning
operation.

Before frontend cutover, a separate targeted GST provision operation must:

- support dry-run and explicit write modes with the same backup, target,
  approval-key, conflict-reporting, idempotency, and audit protections used by
  canonical Priority provisioning;
- insert or accept only the exact canonical rule/version identities and exact
  1,800-BPS exclusive, active, open-ended values;
- report any conflicting identity, value, audit, or effective-window data and
  never overwrite it;
- be safe on a populated knowledge database and not invoke the whole-database
  bootstrap, which rejects unrelated governed records; and
- produce a verification report before Budgeting is exposed without Tax UI.

Execution of that provision against any real target is not authorized by this
specification approval and requires a separate exact-target approval.

For every `set_budget`, the backend reads and validates the canonical policy in
the same transaction as the budget write. It requires that the canonical Tax
version:

- has active status;
- has `rateBps: 1800` and `treatment: "exclusive"`;
- belongs to the canonical system Tax rule;
- starts on or before the budget Starts on value; and
- ends after or at the budget Ends on boundary, or is open-ended when the budget
  is open-ended.

The backend writes the canonical rule/version IDs and treatment to the immutable
PriceVersion and derives the monetary breakdown in the same transaction. The
client neither chooses Tax nor calculates authoritative base, GST, or total.

If the canonical policy is absent, altered, inactive, mismatched, or does not
cover the complete interval, reject atomically with
`FIXED_GST_POLICY_UNAVAILABLE`. The UI retains all entered business values,
expands the affected budget, focuses its panel/validation summary, and shows:

**Budgeting is temporarily unavailable because GST could not be applied. Try
again later.**

The canonical version currently begins on `2026-08-28T00:00:00.000Z`; backdated
budgets before that instant fail closed. Changing that immutable effective date
or introducing a GST rollover requires a separately approved policy/version and
compatibility design.

### 8. Resolvable-budget invariant

For any Pricing-section save containing `set_budget` or a compatibility append,
the backend validates the resulting retained active price set, including
existing references and every proposed new immutable version.

- For a given `revisionId`, `uomId`, legacy `modeId` scope, and instant in time,
  at most one retained active budget may apply.
- Vendor and price-entry identity do not make two simultaneous
  candidates resolvable because the context request does not select them.
- Non-overlapping periods and different UOMs remain supported.
- An ordinary save containing only unchanged references remains compatible even
  if historical data already contains an ambiguity.
- A new/update conflict is rejected atomically using the existing
  `EFFECTIVE_WINDOW_OVERLAP` error contract, mapped in the UI to:

  **Another budget for this unit already covers these dates.**

The existing transaction, section CAS, aggregate CAS, and dependency coordination
must protect this check against concurrent writes.

### 9. Readable saved budget summary

A collapsed budget may display only business-facing information:

- Vendor name;
- UOM name;
- Unit budget before GST, sourced from authoritative `baseAmountPaise`;
- Starts on and Ends on when present;
- server-derived GST and Total including GST after save; and
- **Needs review** when `reviewRequired` is true or the effective version is not
  usable.

Do not show operation, internal IDs, version numbers, Tax rule/version,
treatment, raw status, or raw legacy Mode IDs. Historical records retain their
server-returned money breakdown; the UI labels the amount **GST**, not **GST
(18%)**, because an untouched historical record may use another immutable rate.

## UX states

### Loading

- Show **Loading Budgeting…** while required section data is unavailable.
- Disable Set budget until the Pricing section and Vendor/UOM catalogs needed to
  create a valid row have loaded.
- Loading one prerequisite must not manufacture an empty budget.
- Tax-catalog loading, staleness, emptiness, or failure never blocks Budgeting or
  Save Mode and produces no Budgeting status message.

### Empty

- Show **No budgets set.**
- Keep **Set budget** available when prerequisites are ready and the actor can
  edit.

### Missing prerequisites

- Identify Vendor or UOM specifically.
- Offer Add vendor or Add Unit only when permitted.
- Do not expose a technical missing-ID or missing-version message.

### Validation

- Open the affected budget and Schedule options when relevant.
- Focus the first invalid visible control after announcing a concise validation
  summary.
- Map a fixed-GST policy failure to the budget panel/validation summary rather
  than a nonexistent Tax field or technical identifier.

### Saving and success

- Disable Set, Update, Remove, panel fields, and disclosure switching that could
  mutate state while Save Mode is pending.
- Keep values visible.
- Preserve the existing single Save Mode transaction ordering and section/Main
  Line CAS behavior.
- Rebase all saved rows from the authoritative returned section envelope.
- Announce **Mode saved** once; do not add a second competing success message.

### Error and conflict

- Preserve the complete local form after a server error.
- Use **Budgeting could not be saved** for section-specific failure copy.
- For CAS conflict, use **Budgeting changed elsewhere**, retain local work, and
  keep the existing review/discard resolution.
- Conflict review shows only the visible business values and server-derived
  totals; hidden fields and IDs remain excluded.

### Stale data

- Keep last successful data visible.
- Show **Showing saved budgets. Latest updates could not be loaded.** with Retry.
- If resolved saved details are unavailable, show **Saved budget details are
  unavailable. Retry before updating this budget.** and disable Update.

### Read-only and permission states

- Active, inactive, superseded, or archived revisions show collapsed summaries
  that remain expandable for reading.
- Omit Set budget, Update budget, Remove, Add vendor, and Add Unit actions.
- A permission loss during save retains the draft and shows **You no longer have
  permission to update this Draft.**
- Backend authorization remains authoritative.

## Accessibility and responsive behavior

- Each budget trigger is a real button with `aria-expanded` and `aria-controls`.
- Each expanded body is a labelled region.
- Enter and Space toggle the disclosure.
- Set budget focuses the new panel and then its Vendor control when available;
  otherwise it focuses the panel trigger so recovery actions remain reachable.
- Update budget applies the same focus rule.
- Validation opens the correct disclosures before moving focus.
- Remove controls include enough context—Vendor and UOM where available—to be
  distinguishable.
- State is expressed with text, not color alone.
- Preserve visible focus and at least 44 × 44 px touch targets.
- Respect reduced motion; no decorative animation is required.
- At wide widths, use at most two bounded form columns.
- At 768 px and below, use one column.
- At 480 px and below, Set budget and disclosure triggers span the available
  width, summaries wrap, and the screen has no horizontal scrolling.

Rendered verification must cover 1440×900, 1024×768, 768×1024, 390×844, and
320-pixel widths.

## Data, API, and calculation contract

### Ownership boundary

| UI provides | Backend owns |
| --- | --- |
| Selected Vendor ID | Active Vendor lookup and archive-race validation |
| Selected UOM ID | Active UOM lookup and quantity/unit linkage |
| Unit budget before GST in validated rupees/paise | Canonical GST 18% rule/version, exclusive treatment, base, GST, total, rounding, and overflow checks |
| Starts on / optional Ends on | Effective-window coverage and overlap enforcement |
| Hidden source reference only when updating | `priceEntryId`, new `priceVersionId`, version number, immutable lineage, and legacy Mode preservation |
| Set, Update, or Remove intent | Append/reference mapping, active status, transaction, CAS, and audit |

The frontend may resolve IDs to names for display, but it never uses labels as
join keys and never manufactures a financial, lifecycle, or lineage value.

### Mapping and interlink invariants

- Vendor, UOM, canonical Tax rule/version, Main Line, revision, price entry, and
  price version relationships continue to use stable IDs.
- The backend validates every newly introduced reference as active inside the
  transaction and coordinates against concurrent archive/update activity.
- A saved budget remains scoped to exactly one Main Line revision and one
  `priceEntryId` history chain.
- `sourcePriceVersionId` can update only a version currently retained by the
  same editable revision; cross-Main-Line, cross-revision, stale, or removed
  sources fail closed without disclosure.
- The backend-selected canonical Tax version must belong to the fixed Tax rule,
  exactly match 1,800 BPS/exclusive treatment, and cover the entire budget
  interval.
- The immutable price version stores the exact Vendor, UOM, Tax, money,
  effective-window, actor, and version lineage used by context resolution.
- Section CAS, aggregate CAS, audit records, and context lineage remain linked to
  the same transaction outcome; no partial interlink is persisted.
- After save, every Pricing/Budgeting and Overview query affected by the returned
  authoritative section/aggregate version is updated or invalidated together.

### API extension and unchanged stored shape

The Pricing section request contract adds `set_budget` to the existing
price-entry command union. Its request fields are limited to:

- optional hidden `sourcePriceVersionId` for an update;
- `vendorId`;
- `uomId`;
- `inputAmountPaise`;
- `effectiveFrom`; and
- `effectiveTo`.

The backend rejects unknown fields on `set_budget`; a client cannot set
`priceEntryId`, `priceVersionId`, `specificationId`, `modeId`, `taxVersionId`,
`taxRuleId`, `treatment`, rate, status, version number, calculated amounts, actor
metadata, or audit metadata through this command.

OpenAPI documents `set_budget` as the preferred Budgeting write contract and
marks legacy `append` as compatibility-only. Successful section responses remain
the current enriched reference shape, so saved rows continue to carry immutable
lineage without exposing it in the UI.

The following remain unchanged:

- `pricing` section key and `priceEntries` property;
- persisted reference entries;
- immutable PriceVersion schema and collection;
- integer-paise money storage;
- Tax version relationships;
- server-derived base/tax/total amounts;
- formula version and context lineage;
- section and aggregate CAS;
- audit event types; and
- route authorization operations.

No database schema migration, historical backfill, or response-shape rename is
required. A targeted, guarded canonical GST provision is a rollout prerequisite;
its implementation may be delivered, but executing its write mode against a
real database is a separately authorized operation.

### Targeted backend validation

The save service will resolve every `set_budget` relationship and strengthen
new-version effective-window validation to match what the current context
resolver can uniquely select. This changes request validation and rejection
behavior for newly created or updated budgets but does not rewrite stored data
or change successful response shapes.

### Financial invariants

- Money stays non-negative safe-integer paise internally.
- Rupee parsing accepts at most two decimal places.
- Fixed GST remains exactly 1,800 integer basis points with exclusive treatment.
- The protected canonical immutable Tax version supplies the persisted lineage.
- For a fixed-GST budget, `baseAmountPaise = inputAmountPaise`, GST uses the
  existing server half-up basis-point calculation, and total equals base plus
  GST.
- The backend alone derives base, tax, and total.
- Existing half-up rounding and overflow checks remain unchanged.
- Quantity-slab estimates do not override the effective budget.
- Budget values must not be manufactured by Overview or conflict-review clients.

## Permissions and audit

- Reading Budgeting continues to require the established configuration-read
  operation.
- Editing and Save Mode continue to require the established
  configuration-update operation and sole-active-Super-Admin guard.
- Revision activation continues to use its separate lifecycle permission.
- Context resolution keeps its existing read operation.
- Every created immutable budget version and section update remains in the same
  Mongo transaction with its existing audit events.
- The targeted GST provision has its own explicit operator authorization,
  deterministic audit records, dry-run, conflict reporting, and rollback
  instructions; Save Mode never performs that provision implicitly.
- A fixed-policy mismatch, overlap, CAS conflict, audit failure, or authorization
  failure writes neither a partial price version nor a partial section update.

## Compatibility and rollback

- Existing Active and superseded revisions remain immutable.
- Existing reference commands continue to read without migration.
- Existing mode-neutral prices remain the canonical source for PMC and Execution.
- Existing non-null legacy `modeId` values remain stored and are never mapped to
  PMC/Execution by label.
- Existing reference clients remain compatible. Legacy append is accepted only
  for the exact canonical fixed-GST rule/version and remains compatibility-only;
  this prevents it from bypassing the fixed policy.
- Reference-only saves remain compatible with untouched historical ambiguity.
- The UI and preferred command path can be rolled back without a data rollback;
  every successful `set_budget` write produces the existing canonical stored
  version/reference shape.
- The strengthened new-version validation can be rolled back independently; no
  stored values require reversal.
- No deployment, schema migration, historical rewrite, provision execution, or
  production write is included.

## Scope

### In scope

- Main Line user-facing Pricing → Budgeting terminology.
- Dedicated Budget builder and expansion panels.
- Set, update, remove, empty, read-only, loading, error, stale, and conflict
  states.
- Backend-owned generation of price-entry/version identity and append/reference
  mapping.
- A preferred `set_budget` request command containing business inputs only.
- Backend binding of protected canonical GST 18% lineage, treatment, status,
  scope, version, and amount derivation.
- Removal of Tax selection, Tax catalog state, and Tax configuration actions from
  Budgeting.
- A targeted guarded provision operation for the fixed GST policy, without
  executing it against any database.
- Removal of the obsolete Mode control from new budgets.
- Preservation of historical legacy Mode scope.
- Business-only Overview and conflict projections.
- Append-time ambiguity prevention aligned with context resolution.
- Focused financial, interaction, accessibility, responsive, compatibility, and
  concurrency regression coverage.

### Non-goals

- Renaming backend `pricing`, `priceEntries`, models, collections, or audit types.
- Making Quantity slab rates the estimator price source.
- Different budgets for PMC and Execution.
- Different Execution budgets for Sub-Vendor and In-house.
- Adding Vendor as an estimator-context selector.
- Removing immutable price history or price/tax lineage.
- Changing the existing GST formula, margin formulas, money units, or rounding.
- Redesigning reusable Vendor, UOM, or Tax administration.
- Removing the reusable Taxes administration area outside Budgeting.
- Changing permissions.
- Migrating, backfilling, seeding, deploying, committing, or pushing.

## Options considered

### 1. Backend-owned fixed GST policy with one shared budget scope — selected

- Removes every requested technical control.
- Matches current PMC/Execution context behavior.
- Removes a redundant Tax decision and its broken empty-catalog prerequisite.
- Lets the server generate IDs and bind the protected canonical GST 18%, status,
  scope, immutable version, and audit relationships.
- Keeps the proven stored reference, immutable-history, CAS, and audit contracts.
- Adds one preferred request-command shape but requires no data migration.
- Backend validation prevents new unresolvable overlaps.

### 2. Keep Tax selectable but auto-select the first/only option

- Has a smaller contract change.
- Still depends on mutable catalog state, fails when no Tax exists, and could
  silently select a different future record.
- Rejected because labels/order are not identity and the business rule is fixed.

### 3. Calculate fixed GST without immutable Tax lineage

- Avoids provisioning canonical reference data.
- Breaks the required Tax rule/version interlink and weakens historical audit
  evidence.
- Rejected because hidden backend ownership must preserve, not remove, lineage.

### 4. Frontend facade over legacy append/reference commands

- Could hide fields visually while the client still generates IDs, chooses the
  Tax version/treatment, sets status/scope, and submits `append`.
- Has a smaller API diff but leaves business-critical mapping in the client.
- Rejected because the user explicitly requires hidden technical fields and data
  interlinks to be backend-owned.

### 5. Canonical Mode-scoped budgets with PMC/Execution panels

- Would allow genuinely different budgets for each fixed Mode.
- Requires adding canonical `modeKind` (and potentially `executionSource`) to
  immutable prices, changing scope keys/indexes and context precedence, and
  defining fallback/migration behavior for shared and legacy `modeId` records.
- Rejected for this simplification because the current estimator intentionally
  shares the price and the request prioritizes minimum user complexity.

## Risks and mitigations

### Fixed GST policy is missing or altered

Mitigation: deliver a targeted dry-run-first provision operation, protect the
canonical identities from generic mutation/archive, exact-verify the rule and
version inside every budget transaction, and fail atomically with plain-language
panel feedback. Never choose a Tax by label or order.

### Provisioning mutates the wrong database or overwrites data

Mitigation: require exact target fingerprint, backup confirmation, approval key
and digest, dry-run evidence, idempotency, deterministic audit, conflict-only
behavior, and separate authorization before write mode. Never auto-provision in
Save Mode.

### Updating an inclusive historical price increases its before-GST amount

Mitigation: initialize an Update draft from authoritative `baseAmountPaise`.
Never reuse an inclusive historical `inputAmountPaise`, which represents its
tax-inclusive total. Prior immutable history remains unchanged.

### “Set budget” appears to save immediately

Mitigation: explain that Save Mode persists the change, retain the existing dirty
indicator, and keep one success announcement.

### Historical legacy Mode scope is lost

Mitigation: preserve the stored `modeId` during replacement, never infer a fixed
Mode from a label, and block an unsafe update with recovery copy.

### Multiple Vendor budgets make context unresolvable

Mitigation: enforce one retained effective budget per UOM/legacy Mode/time window
for every save containing `set_budget` or a compatibility append, regardless of
Vendor.

### Hidden-field validation exposes technical wording

Mitigation: map errors to Budget, Starts on, Ends on, or a plain-language panel
notice; keep raw IDs out of visible conflict and error projections.

### Expansion panels hide errors

Mitigation: auto-expand the affected budget and Schedule options, then focus the
first invalid visible control.

## Acceptance criteria

1. Every Main Line user-facing occurrence of the relevant Pricing section is
   labelled **Budgeting**, while the internal key remains `pricing`.
2. The visible list is **Budgets** and its primary action is exactly **Set
   budget**.
3. Price operation, price entry/version IDs, every Tax selector/configuration/
   warning/retry action, Tax rule/version/treatment, Version status/number, Mode,
   and reorder controls are absent from the Budgeting editor and focus order.
4. The new UI sends only the business fields defined by `set_budget`; it never
   generates or submits price-entry/version IDs, any Tax field, treatment, rate,
   status, specification scope, Mode scope, version number, or calculated amount.
5. The backend generates every new ID and mapping and retains append/reference
   semantics internally: unchanged references create no new version, while
   Set/Update creates exactly one immutable version.
6. Updating resolves the source reference on the backend, retains the same
   `priceEntryId`, advances immutable version history, and does not modify prior
   versions.
7. The backend assigns `specificationId: null`, `modeId: null`, active budget
   status, and the canonical GST 18% rule/version without accepting those fields
   from `set_budget`.
8. A safe legacy replacement preserves a non-null historical `modeId`; it is
   never silently converted to PMC, Execution, or shared scope.
9. Vendor, UOM, Unit budget before GST, and Starts on are required; Ends on is
   optional. Tax is neither required nor accepted from the client.
10. The backend exact-verifies the protected canonical Tax rule/version as active,
    1,800 BPS, exclusive, related by stable ID, and covering the complete budget
    interval before writing.
11. The UI explains **GST is fixed at 18% and is added when you save.** Any Amount
    before GST, GST, and Total including GST displayed after save comes only from
    the authoritative response.
12. The server remains authoritative for integer-paise base, GST, total, half-up
    rounding, overflow, effective-window, and canonical Tax-reference validation.
13. A save containing a new/update budget cannot leave two retained active
   budgets for the same UOM/legacy Mode scope with overlapping effective windows,
    even when Vendors differ.
14. Existing reference-only payloads and immutable historical versions remain
    readable without migration or rewrite, including other rates and inclusive
    treatment.
15. Saved budgets are collapsed business summaries; new/updated/invalid budgets
   open automatically, and at most one primary budget is expanded.
16. Set budget changes only the local draft until Save Mode succeeds.
17. Removing a budget removes its reference from the Draft but never deletes
   immutable history.
18. Overview and conflict review say Budgeting/Budget and omit technical fields
    and raw IDs; saved details omit Tax identity and use authoritative Amount
    before GST, GST, and Total including GST.
19. Tax-catalog loading, failure, staleness, or emptiness cannot disable Set
    budget, block Save Mode, or render any Budgeting warning/action.
20. Keyboard users can create, expand, update, validate, and remove a budget with
   correct focus restoration and disclosure semantics.
21. The layout remains usable without horizontal scrolling at 1440, 1024, 768,
   390, and 320 pixel widths.
22. A fixed-policy failure uses `FIXED_GST_POLICY_UNAVAILABLE`, preserves all
    local business values, writes nothing partially, opens the affected panel,
    and never directs the user to a Tax control.
23. Updating a historical inclusive budget initializes the editable before-GST
    amount from its saved `baseAmountPaise`; it does not reuse the inclusive
    `inputAmountPaise` or alter the prior version.
24. A targeted guarded GST provision operation can dry-run, conflict-report,
    idempotently establish the exact canonical rule/version and audit records,
    and provide rollback instructions; no real-target write is performed without
    separate authorization.
25. Canonical GST rule/version identities and availability cannot be changed or
    archived through generic reusable-Tax mutation paths.
26. Compatibility append cannot create a new noncanonical Tax price; reference
    compatibility and immutable historical reads remain intact.
27. Existing Specifications, Priority, Vendors, Quantity slabs, Save/Discard,
   activation, estimator context, CAS, audit, permissions, and financial
   calculations have no regression.

## Assumptions and resolved decisions

- **Resolved:** Price operation remains internal and is removed from the UI.
- **Resolved:** Mode is removed because the two fixed Modes currently share one
  authoritative budget; the old `modeId` dropdown must not impersonate
  `modeKind`.
- **Resolved:** Set/Update budget means active status.
- **Resolved:** new budgets start now and have no end date unless changed.
- **Resolved:** the Unit budget is the before-GST amount. The backend always
  applies the protected canonical `GST 18%` rule/version using exclusive
  treatment, so ₹100.00 becomes ₹18.00 GST and ₹118.00 total.
- **Resolved:** Budgeting sends no Tax field and shows no Tax selector,
  configuration button, prerequisite warning, retry action, or catalog state.
- **Resolved:** before accepting a write, the backend verifies the exact
  canonical IDs, 1,800 BPS rate, exclusive treatment, active state, ownership,
  and effective-window coverage; labels and collection order are never used as
  policy identity.
- **Resolved:** the canonical policy is established only by a targeted,
  guarded, dry-run-first provision operation. Save Mode never creates or repairs
  Tax configuration as a side effect, and running provision write mode against
  any real target requires separate authorization.
- **Resolved:** untouched historical prices keep their original Tax lineage and
  calculations. Updating an inclusive historical price starts from authoritative
  `baseAmountPaise`; if that value is unavailable, Update is disabled rather
  than inferred.
- **Resolved:** the current canonical GST version starts on 28 August 2026, so a
  new or updated budget beginning earlier fails closed unless a separately
  designed canonical historical version is provisioned.
- **Resolved:** Overview and conflict review use the same simplified terminology.
- **Resolved:** existing immutable data is preserved with no migration.
- **Open decisions:** none required for this bounded implementation. Approving
  this specification approves the fixed-exclusive-GST, shared, mode-neutral
  Budgeting model. It does not authorize provision execution against a real
  database. A later request for different PMC/Execution amounts or a backdated
  GST policy will require its own contract.
