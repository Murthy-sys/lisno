## Goal

Simplify Project Initiation and correct recommendation deselection, limited to the five requested changes. Existing assignment, project creation, estimate pricing, approval, and procurement workflows remain intact.

## Current behavior and evidence

- `frontend/src/features/admin/AdminProjectInitiationDialog.tsx` renders Location, Minimum budget, and Maximum budget and requires all three before submitting. Property type is currently free text. Next action date uses the browser's native `datetime-local` control.
- `backend/src/routes/admin-projects.ts` also requires location and both budgets. `admin-project.service.ts` copies location into project location, client address, and lead location. The Project and Lead Mongoose schemas require location, and Project also requires client address. Hiding fields alone would leave submission blocked or fail persistence.
- Lead budgets already support `null`. Removing the inputs must not manufacture zero budgets or substitute a city/project name for an unknown address.
- `LeadEstimateWorkspace.tsx` defines the property-type options used during main-line selection: **1BHK, 2BHK, 2.5BHK, 3BHK, 3.5BHK, 4BHK, Villa, Penthouse, Studio, Duplex**. Initiation should share this source rather than duplicate it.
- Recommendation-origin tracking and cascade deselection already exist in `configuredEstimate.ts`, `LeadEstimateWorkspace.tsx`, and the estimate persistence contract. Existing tests cover direct removal, basket removal, and saved origin. The reported remaining failure needs reproduction against the current recommendation-modal path; the existing dependency mechanism should be corrected rather than replaced.

## Scope and requirements

### 1. Remove budget and location inputs

- Remove Minimum budget, Maximum budget, and Location from the initiation form, local validation, and the payload generated by this form.
- Keep **Project city**, client details, project name, next action, date/time, and the existing Sales/Sales Manager assignment behavior.
- Make the three removed inputs optional in the initiation API. Continue accepting valid values from existing callers and validate any supplied budget range.
- Store absent budgets as `null`; represent absent location/address consistently as empty strings within the existing string response contracts. Permit this absence through persistence without placeholder addresses. Retain mandatory location validation on other creation endpoints that currently require it.
- Do not erase values on existing projects/leads or run a migration.

### 2. Property-type dropdown

- Replace the free-text input with a required, keyboard-accessible dropdown.
- Extract the existing ten options into one shared constant consumed by initiation and estimate configuration, preserving their values and order.
- Start with “Select property type”; do not select a property type on the user's behalf. Preserve legacy stored property-type values outside the new initiation form.

### 3. Next action date picker

- Provide a scoped, styled calendar control for initiation with a clearly labeled time input, preserving the current requirement to collect both date and time and convert the local selection to the existing ISO timestamp API field.
- Selecting a calendar date closes the calendar. Clicking outside, pressing Escape, or toggling its trigger also closes it reliably; Escape closes the calendar before the parent initiation panel. Restore focus appropriately.
- Support keyboard operation, a visible selected date, month navigation, invalid/required states, narrow screens, and panel scrolling.
- Use the established neutral/green design tokens and a short opacity/vertical transition (approximately 160–200 ms). Respect reduced motion, interrupted closing/reopening, and unmount cleanup. Do not add global date-picker styling or a new animation dependency.
- Other date inputs elsewhere in the application retain their current behavior.

### 4. Remove dependent recommendation selections

- Reproduce the exact flow: select POP false ceiling, accept the recommended false ceiling painting through the recommendation modal, then deselect POP false ceiling.
- Deselect the recommendation-added painting immediately. It must disappear from the selected-items view and stop contributing to counts, totals, Summary, Proposal, and the submitted/saved scope. Its catalogue definition and editable draft values are retained.
- Apply the existing room-scoped origin rule to the current modal addition path, source checkbox removal, and removal of the source Main Basket. Follow recommendation chains until no orphaned recommendation selection remains.
- Retain a target required by another still-selected recorded source, and retain independently/manual-selected items and selections in other rooms. Preserve this behavior through save/reload and catalogue refresh.
- Preserve existing recommendation-modal dismissal behavior. Existing historical lines without recorded recommendation origin are not silently reclassified or removed.

## Constraints and non-goals

- No unrelated styling, procurement changes, approval changes, role/permission expansion, pricing changes, new dependencies, migration, deployment, or production mutation.
- Existing worktree changes must be inspected and preserved before edits. Modify only the affected initiation contracts, persistence accommodation, shared property list, scoped picker, recommendation path, and relevant tests.
- Preserve transaction boundaries, audit events, stable IDs, estimate version checks, and integer-paise calculations.

## Acceptance and verification

1. Initiation shows none of the three removed fields and succeeds without them for both existing assignment modes. API/service and Mongo persistence checks prove absence is supported, supplied legacy values remain valid, and ordinary creation endpoints retain their required-field validation.
2. Initiation and main-line selection show the identical ten property types from a single source. Dropdown labels, required validation, and keyboard operation work.
3. A chosen next-action date closes the calendar; outside click, Escape, trigger toggle, and repeated reopen work without closing the parent or trapping focus. Time survives date changes and the submitted timestamp represents the chosen local date/time.
4. The user's POP/painting example passes in a rendered interaction test and browser verification. Coverage also protects another room, a shared target, a manually selected target, chained dependencies, and save/reload.
5. Desktop and mobile rendering, focus behavior, and reduced motion are verified. Run focused tests, affected workspace typechecks/builds, and `git diff --check`; broaden testing only for demonstrated shared-contract risks.

## Risks and assumptions

- Removing a required persisted address affects more than form rendering; compatible storage and endpoint validation must be verified together. No fabricated fallback is acceptable.
- The precise remaining recommendation defect is unconfirmed. Reproduce it before changing the existing cascade logic; add the regression at the failing interaction boundary.
- “Disabled” for a removed recommendation means no longer selected or included in the estimate, not deleting or globally preventing independent selection of a configured Main Line.
- “Remove location” refers to the Location field shown in the screenshot. Project city remains available for vendor matching.
- No open product decision blocks this specification. The next repository stage is the separate task plan after specification approval.
