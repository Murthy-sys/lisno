# Mode Quick Summary fields and tab-based progress

## Goal

Show the complete saved Mode configuration in Configuration → Quick Summary, including the unit price, low-quantity threshold, impact percentage, margins, scope, description, component fields, and Specifications. Make the Configuration progress bar reflect completed **registered workspace tabs**, so saving all currently visible tabs shows 100% on web and mobile and future tabs join the calculation when added.

## Current behavior and evidence

- `shared/knowledge/knowledgeSavedSummary.ts` now projects saved `baseRatePaise`, `lowQuantityLimit`, `impactBps`, and margins for all four calculation scopes from Advanced, using the saved Overview UOM where available. Web and mobile show those four rows.
- The current Mode projection now shows four calculation rows, but intentionally omits saved `modeDescription`, `modeConfigurations` (PMC, Sub-Vendor, In-house scope and component fields), and `pricing.specifications`/`pricing.brands`. `useKnowledgeSavedSummary.ts` fetches Overview, Advanced, and Recommendations but does not fetch Pricing. The web and mobile Quick Summaries therefore cannot show everything saved under Mode. The latest user clarification requires every saved Mode detail in Quick Review, while keeping the summary tied to saved values.
- The currently registered workspace tabs are Overview, Mode, Recommendation & Exclusions, and Quality Parameter (`shared/knowledge/knowledgeWorkspaceSections.ts`). Mode contains two backend sections, `advanced` and `pricing`; Quality is a shared Main Basket checklist. The tab registry also maps visible tabs to their backend sections.
- The preceding approved implementation changed backend completeness to count registered workspace tabs and reprojects older stored revision percentages on read. Web and mobile now display that backend percentage with a registry-derived configured-tab count. This progress behavior remains in scope for regression protection, but the latest clarification requires additional Quick Summary content.
- Relevant source files are already dirty from the preceding approved Mode margin change; `backend/src/services/ai-estimator-knowledge-item.service.ts` and its service test are dirty from separate vendor-induction work. Preserve those edits and work within the affected functions.

## Proposed behavior

### Quick Summary

1. For each configured Mode calculation scope (PMC, Execution → Sub-Vendor, In-house Labor, In-house Material), show the saved **unit price**, **low-quantity threshold**, **impact %**, and its saved margin. Unit price means the entered `baseRatePaise` per Overview UOM; it is not a simulated selling price. Format integer paise exactly as INR and basis points with up to two decimal places. Preserve the saved decimal quantity string. Show `0` and `0%` when saved.
2. Read only confirmed, identity-matched saved Overview, Advanced, and Pricing section envelopes already authorized for the item and revision. Typing, unsaved drafts, simulator output, internal IDs, opaque references, raw JSON, historical compatibility fields hidden by the editor, and budget price-reference internals must not appear as saved details. If the UOM name is unavailable, show the saved price without inventing a unit. Invalid or incomplete calculation scopes keep `Not configured` rather than displaying partial numbers. A failed/denied Pricing read must not hide independently available Advanced details; provide its own loading/error/retry state.
3. The Mode Quick Summary must include every user-editable value actually saved in the Mode tab, grouped by PMC and Execution → Sub-Vendor/In-house: the saved shared description when present; the four complete calculation scopes and margins; every persisted Inclusion/Exclusion with its selected state; custom configuration component label, type, options, and saved answer; and saved Specifications and Brands (item/Brand names and descriptions, and each Specification's Brand association). Resolve names through saved IDs and authorized catalogs; missing names use a safe unavailable label. Do not fabricate generated descriptions or starter-list selections that were not saved. Keep distinct legacy or unresolved configurations visible under a clear “Needs review” label without guessing their source.
4. Keep the four calculation rows fully readable in the compact Mode preview on web and mobile. Present the other saved Mode content in an ordered, expandable detail area within Quick Summary, with visible counts or labels indicating that more saved details are available. Do not silently cap the detail list; allow long user text to wrap or expand. Empty saved fields may be omitted, while explicit `0`, `false`, and saved unselected scope choices remain visible. Preserve keyboard and screen-reader access and the existing product styling. After a successful save or query refresh, both clients show the newly confirmed values; failed saves and local typing leave Quick Summary at the last saved values.

### Progress

5. Derive the denominator from the first-level Configuration tab registry for the item, not from a hardcoded number. Each registered tab contributes one equal share: `completed registered tabs / registered tabs × 100`, rounded to an integer. Today there are four tabs, so 0/4 = 0%, 1/4 = 25%, 3/4 = 75%, and 4/4 = 100%. If a fifth tab is registered later, 4/5 = 80% until it is configured. Show the live count beside the percentage, for example “3 of 4 tabs configured.” Permission-based read-only state does not change the denominator; a future item-type-specific tab enters only when registered for that item type.
6. Derive completion from **saved, backend-evaluated section states**, not local drafts or a nonempty payload test in the clients. Overview is complete when its section is `complete`. Mode is complete when **at least one** of its visible content sections, `advanced` or `pricing`, is `complete`. Recommendation & Exclusions is complete when its section is `complete`. Quality Parameter is complete when the current shared Main Basket Quality checklist is configured. A visible tab in `not_configured`, `needs_attention`, or `not_applicable` state is incomplete. Hidden `quantity-margin`, `scope`, and `execution` sections never affect the registered-tab percentage.
7. Make the backend authoritative for `completeness.percentage` on new writes and current reads. The backend tab-to-section mapping must stay synchronized with the shared workspace tab registry through a contract test, since backend TypeScript does not import files outside its `src` root. Registering a future tab with its saved section mapping changes the denominator without editing a numeric total. Recompute the displayed percentage from stored section states on reads of older records, including revision-history presentation, without rewriting persisted revisions or running a migration. Refresh the current item percentage when basket Quality changes. Keep the existing `completeness.sections`, findings, blockers, activation rules, and revision content digests intact. Align web/mobile index-card counts and progress text with the same registered-tab rule.

## Options and decision

- **Recommended: shared saved-content projection plus the existing backend-owned registered-tab percentage.** Extend the shared Mode projection for both clients and load the existing saved Pricing envelope; preserve the backend as the progress source of truth. Existing records are displayed on read without a data write. Future tabs require a saved-section mapping as part of their registration.
- **Client-only percentage:** faster locally, but API, list cards, web, and mobile could disagree and old revision responses would still say 83%. This does not meet the consistency requirement.

The stated “content under tab” rule is interpreted as **any complete saved Mode content** (`advanced` or `pricing`) making the Mode tab complete. Pricing and calculation completeness remain separately available in backend findings and activation checks. The four currently registered tabs count for both main and temporary items; future tabs join according to their item-type registration.

## Contract, risks, and acceptance criteria

The existing API shape stays unchanged: `completeness.percentage` remains a registered-tab metric; `completeness.sections` continues to expose backend section states. The expanded Mode summary reads the existing Pricing section endpoint under the same item/revision authorization. There is no new endpoint, field, dependency, seed, or data migration. Percentage changes must never clear blockers or alter immutable approval/revision data. Main risks are stale persisted percentages, Quality changing independently, Mode containing two backend sections, future registry drift, long saved Mode content, incorrect ID joins, and a failed Pricing read masking Advanced data.

- **AC1:** After saving distinct PMC, Sub-Vendor, Labor, and Material settings, web and mobile Quick Summary show each scope's exact saved INR unit price, low-quantity threshold, impact %, and margin; zero and fractional values remain correct. The same summary exposes every saved Mode description, scope choice, component field, Specification, and Brand described above, including long text and explicit unselected/false values. Unsaved edits and simulator output do not appear; save/refresh updates do.
- **AC2:** Missing/invalid values, unavailable UOM/Brand names, legacy configurations, and independent Advanced/Pricing load failures are handled without invented values or leaked IDs/private fields. All requested fields are readable at narrow widths and by screen readers, with expandable access to the full saved content.
- **AC3:** With the four current tabs configured and hidden `quantity-margin` empty, the current item shows 4 of 4 and 100%. With one current tab unconfigured, it shows 3 of 4 and 75%; cover 0/4 and 1/4 too. Mode with only `advanced` or only `pricing` complete counts once. A test-registered fifth tab changes 4/5 to 80% and 5/5 to 100% without changing a numeric denominator constant.
- **AC4:** Main and temporary items, web and mobile status, index cards, current shared Quality changes, and older stored revisions use the same registered-tab percentage/count presentation. Reads do not mutate persisted records. A contract test fails if the backend mapping and shared tab registry diverge.
- **AC5:** Backend `sections`, blockers/warnings, activation checks, versioning, and content digests remain unchanged. Focused domain/service, shared projection, web/mobile rendered interaction/accessibility tests, typechecks/builds, and `git diff --check` pass. Preserve the unrelated dirty vendor work.

## Open decisions

The latest clarification resolves the saved-versus-typed question: Quick Summary shows **saved** Mode content only. Approval of this revision confirms that all user-editable saved Mode tab values, including Specifications and Brands, belong in Quick Summary; budget price-reference internals and hidden typed compatibility fields stay out of the presentation.
