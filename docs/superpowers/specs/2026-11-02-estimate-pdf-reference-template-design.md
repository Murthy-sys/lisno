## Evidence and current behavior

- The reference contains 12 portrait A4 pages, 594.96 × 841.92 points, generated by Chromium. All 12 pages have been rendered and visually inspected.
- It uses warm off-white pages, deep indigo ink/panels, muted gold accents, fine rules, large condensed headings, and six embedded interior photographs. The cover and closing page use full-bleed imagery and branded panels.
- Embedded fonts are subset Futura BT Book, Medium, and Light Condensed, plus Helvetica for certain glyphs. Those Futura BT font files are not in the repository. The machine has a different Futura collection, which is not a production asset or an exact substitute.
- `backend/src/services/estimate-pdf.service.ts` currently uses PDFKit with Helvetica, a small logo/red header rule, faint rotated watermark, five-column item tables, totals, and four short terms. It supports `standard` and `compact_client_delivery` profiles.
- The same generator supplies staff PDF export (`backend/src/routes/estimates.ts`), client publication (`estimate-publication.service.ts`), and visibility-filtered client renditions (`client-quotation-rendition.service.ts`).
- Publication records store immutable estimate snapshots and original PDF bytes. Staff revision downloads read those bytes. Client rendition caching additionally depends on Configuration visibility and a policy version.
- `EstimatePdfInput` currently lacks proposal date/validity, canonical project reference, prepared-by attribution, payment stages, and versioned proposal terms. The current snapshot validators also allowlist known fields; adding metadata requires synchronized validation and consumers.
- Included lines carry quantities, saved rates/amounts, specifications/notes, dimensions, and stable room/basket IDs. `included: false` means an unselected estimate line; it does not mean client-supplied work.
- Monetary source values are integer paise for configured lines and totals. GST and approved totals already have established calculation and lineage rules.
- Static build packaging currently copies only the logo. New photo/font/template assets need explicit production packaging and compiled-output verification.

### Financial and scope safeguards

- Actual estimate amounts, saved component amounts, UOM, quantities, dimensions, and tax values remain authoritative. Never alter an approved amount to reproduce the sample's price.
- The example's special-discount amount and agreed price are not reusable defaults. Do not add a discount field or invent a discount calculation in this task.
- Keep explicit GST and total-payable disclosure using existing source totals, even though the sample's price panel has no separate GST row. Use the same visual panel with the applicable source rows.
- Payment-stage amounts use the document's actual payable total in paise. Calculate deterministically; round stages with an explicit integer rule and assign any final remainder to the last stage so all stages sum exactly to payable total. They are proposal amounts, not new receivable/ledger records.
- Group rows by saved stable room IDs and basket IDs, preserving saved ordering. Do not join by presentation names. Legacy lines without stable room IDs remain in a clearly named ungrouped section, retaining their original room text.
- Client-visible scope and area summaries must be based only on the authorized client projection. Never disclose hidden names, counts, descriptions, materials, or a fabricated balancing line to reconcile filtered rows with the unchanged approved total.
- No unselected line is automatically labeled BY YOU. Show client-arranged budgets, zero-cost INCLUDED indicators, and supplier-responsibility labels only when source data explicitly supports that meaning. Unsupported optional blocks are omitted, not populated from the example.
- Default exclusions apply only unless explicitly included in the detailed estimate. Phrase that precedence visibly so defaults cannot contradict selected work. Do not infer a project-specific exclusion from the sample's client's choices.

In scope:

- Reusable proposal renderer, reusable reference imagery/brand assets, and versioned commercial defaults.

- Staff generation and future client-publication/rendition integration, static-asset packaging, regression tests, and rendered synthetic proposal previews.
- New-template support for both current call profiles without globally shrinking all text; the reference layout becomes the presentation standard for newly generated proposal documents.

Out of scope:

- New discount/negotiation, payment collection, client-supplied line editing, signature capture, or contract-management workflows.
- Changes to estimate calculations, Configuration prices, authorization, source selection, client visibility, approvals, or email retry semantics.
- Replacement of already published PDFs, retrospective commercial-term changes, data backfills/migrations, customer mail, deployment, commits, or pushes.
- Recreating the reference customer's estimate as an actual project in the database.

## Recommended implementation approach

**Recommended:** extend the existing server-side PDFKit generation with separated proposal sections, pagination/measurement helpers, and versioned packaged assets/defaults. This retains the existing service boundary, avoids a Chromium deployment dependency, and supports precise A4 placement and stable saved artifacts.

**Alternative:** a print-HTML/Chromium template could approximate the reference's original rendering engine and use CSS typography/layout. It adds a browser runtime, packaging/resource limits, and a second rendering infrastructure; the missing original HTML/fonts still need reconstruction. Do not introduce this runtime unless implementation evidence shows PDFKit cannot achieve the required result and the decision is reconciled in the task plan.

A visual proof of the cover, detail table, payment schedule, and closing page must precede declaring full visual fidelity. Do not rebuild the unrelated web UI to produce the document.

- Exact typography cannot currently be guaranteed from subset fonts alone; the final preview must disclose any substitution.
- The full proposal is materially longer than today's PDF. Use reusable compressed images, avoid duplicate embedding, and verify generation time, page count, file size, and email/storage limits on long documents.
- Generic exclusions/material promises can conflict with configured project scope. Explicit saved scope/specifications take precedence and must be presented clearly.
- Snapshot metadata changes can affect source-digest/CAS validation and client projection allowlists. Test existing and newly published rounds, not just the renderer in isolation.
