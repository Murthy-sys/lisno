# Independently hosted Python assistant for Ask Lisno and Project Messages

Date: 2026-10-15
Status: Approved, together with the separate task plan. The user selected parallel execution (A); implementation, integrity review and focused local checks are finished. Broader integration and independent-host model verification remain pending; exact evidence and limitations are recorded in the task plan.
Classification: Substantial, with authorization, privacy, and financial-data integrity risks.

## Goal and confirmed decisions

Replace Gemini for both private Ask Lisno and the Project Messages AI assistant with one Lisno-owned Python service using a self-hosted open-weight model and verified live database queries. Preserve natural conversation, improve the reliability of business answers, and measure response speed against explicit targets.

Confirmed by the user:

- The new chatbot service must be developed in Python.
- An existing open-weight model running on an independently controlled server is acceptable.
- The same assistant must be usable in Project Messages as well as private Ask Lisno.
- Neither chat feature may use a cloud AI API. This includes Gemini, any other managed inference service, cloud-hosted Ollama models, hidden AI helper calls, and fallback providers. Model inference runs on the independently controlled server itself.
- Production hosting can be chosen later.
- The later instruction that the chatbot must not depend on or impact this Mac supersedes the earlier suggestion to run development inference here. Do not download model weights, install a model runtime, train, run inference, start an AI daemon, or run model benchmarks on this Mac. Code editing and lightweight tests with fake model responses are the only local development activities proposed.
- Sensitive information must not be disclosed. The user clarified that a Client may know their own project details and project prices, but not configured prices or other internal Lisno information. Interpret allowed prices as customer-facing prices already published to that Client or present in their approved estimate. Configuration rates, internal calculations, and unpublished price previews are excluded. Enforce this in backend data selection and output controls, not merely model instructions.

“Own chatbot” means Lisno owns the application, retrieval rules, prompts, deployment, and evaluations, using an existing model's weights. Training a foundation model from scratch is outside this scope. Matching every Gemini capability or being faster on unspecified hardware is not a claim this specification makes.

## Scope and product behavior

The replacement covers private Ask Lisno and Project Messages AI on web and mobile. Both use the same independent Python service and the same restriction against configured prices/internal Lisno information. AI estimation and OCR remain outside this task; this change must not be described as removing cloud AI from unrelated repository features.

Supported business questions cover owned projects, client-visible project status/progress, recorded schedules, project scope/materials already shared with the Client, and their published or approved customer-facing estimate prices. Answer only fields supplied by authorized sources and permitted by the sensitive-data policy below. Unpublished additions require a quote from the project team; do not calculate an answer from Configuration or expose the internal catalogue, pricing modes, margin rules, or recommendations. A price originally derived from Configuration is visible only if it is now part of the immutable estimate already shared with that Client; no live Configuration value is exposed or substituted.

Users can ask in natural language, use short follow-ups, switch to another owned project, and receive clarification for ambiguous project names or missing quantities/rooms. A greeting followed by a business question must answer the business question. An unsupported question should explain the limitation or point to the project team without claiming to contact anyone.

Preserve the approved mobile reference design, launcher, quick actions, sources, checked-at information, Retry behavior, and disabled private-chat attachment/photo controls. Add only the necessary published-project-price rendering and result-contract support to existing web/mobile answer components. In Project Messages retain the Lisno AI participant, existing request/retry/refresh controls, and restricted-price state. No public streaming contract or wider chat redesign is required. English is the initial evaluated language; other languages require their own evaluation before promising equivalent quality.

Preserve the current Client-initiated Project Messages assistant workflow and existing staff viewing permissions. This request does not create new staff assistant-trigger rights or an internal-information assistant. Private chats remain private and never feed shared-thread history. A shared-thread answer is locked to that thread's project, even if the Client owns other projects or asks to switch projects.

Non-goals: arbitrary database exploration, unrestricted MongoDB queries, global Configuration/catalogue browsing, hypothetical addition pricing, internal Lisno reporting, new user roles, assistant business writes/approvals, document ingestion, attachment analysis, vector search, training on customer records, persistent private-chat storage, production provisioning, and production cutover.

## Architecture and alternatives

Selected approach: a separate Python 3.11+ service in `assistant-service/`, using FastAPI, strict Pydantic contracts, an asynchronous HTTP transport, and a replaceable local-model adapter. Initially use Ollama on the separate server for inference. The Python service owns question interpretation, deterministic conversational rules, model prompting, and candidate-answer generation. The existing Node backend owns authorization, database reads, business calculations, and final answer validation.

FastAPI documents deployment in application containers. Ollama documents CPU and GPU container deployments and schema-constrained JSON responses. These are supported integration mechanisms, not evidence of accuracy or latency for Lisno. See [FastAPI containers](https://fastapi.tiangolo.com/deployment/docker/), [Ollama containers](https://docs.ollama.com/docker), and [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs).

| Option | Decision and tradeoff |
| --- | --- |
| Python service, self-hosted model, existing authorized data tools | Selected by the user. Supports natural language while preserving current business truth. Requires independent compute and model evaluation. |
| Deterministic database bot without a language model | Useful for the direct-answer paths, but insufficient alone for the requested conversational flexibility. |
| Model with direct database credentials or generated database queries | Rejected. Duplicates authorization/business rules and allows incorrect or overbroad reads. Python retrieves database facts through the existing backend tools instead. |

Runtime data flow:

```text
Web/mobile -> deployed Lisno API -> independent Python assistant -> model runtime on AI server
                      |
                      +-> existing authorized services -> MongoDB
                      |
                      +-> validated answer -> web/mobile
```

No arrow depends on the user's Mac, a tunnel from it, local files on it, or a model process on it. The deployed Lisno API calls the independent assistant directly. Normal website/API operation must survive assistant downtime.

## Internal protocol and trust boundaries

Use a versioned, stateless internal step endpoint, proposed as `POST /internal/v1/assistant/step`. Node retains the request-local tool transcript and source maps, including any permitted customer-price report; Python never calls a privileged database endpoint on its own. The provider receives an authoritative surface discriminator (`private` or `project_messages`) and a server-controlled capability set. Model text and client payloads cannot change either value.

1. Node authenticates and admits the public request. Existing project-list responses remain direct and subject to the same display policy. Node supplies only the already scope-filtered and privacy-filtered messages and capabilities available for this request.
2. Python either applies a narrowly recognized deterministic intent or asks its configured model for a strictly typed next step.
3. Python returns either a tool-request batch or a candidate final answer. Node validates the entire batch before running any tool, then executes permitted tools using the existing scoped callbacks.
4. Node sends only explicitly allowlisted, non-sensitive tool-result fields into the next Python step. A field currently described as a public tool result is not automatically approved for this new boundary. Model output cannot set an actor, role, project scope, query filter, connection string, URL, or permission decision.
5. Node reconstructs the final result from request-local facts and any selected authorized project-estimate report, checks narrative and source references, and revalidates current identity, permissions, and source versions before returning the existing public response.

The internal request includes a protocol version, opaque request ID, surface, step index, remaining deadline, bounded filtered user messages, allowed tool names, and bounded server-produced tool results. Identifying references use request-local aliases where needed; Node retains any alias-to-record mapping and resolves it only within the current authorized scope. The response echoes the request ID/version/step and contains a discriminated `tools` or `final` result plus validated usage metadata. Unknown fields, mismatched IDs, duplicate call IDs, invalid enums, excess lengths, unknown tools, and invalid references are rejected. Tests share valid/invalid JSON fixtures between Python and TypeScript to detect contract drift.

Private Ask Lisno allows `resolve_project`, a privacy-restricted `client_profile`, `project_status`, `project_execution`, and a new bounded `project_estimate` read. Project Messages allows only the latter three project-scoped reads, bound to its existing run's project and Client; no profile, project discovery, or project-switching tool is available there. Status/execution projections must contain only client-visible fields. The estimate read reuses existing Client estimate publication/approval rules and preserves source/version lineage. Its model-visible output contains only a request-local report reference, safe field descriptors, and availability/state, never commercial amounts. Node owns report values and formatting. Tool arguments cannot supply a different project or arbitrary estimate ID. A choice between multiple eligible estimates must be authorized and unambiguous.

Do not advertise or execute `search_catalogue`, `recommendations`, or `preview_additions` in either chat surface. Reject those tool names even if the model invents them. Preserve their underlying non-chat business services for existing authorized application workflows; removing a chatbot capability does not alter Configuration or Procurement behavior.

The final candidate contains the existing answer kind, non-commercial fact IDs, an optional opaque project-estimate report reference, clarification codes, and bounded non-sensitive narrative. It never supplies authoritative facts, amounts, links, or freshness witnesses. Node rejects report references not created in that request and reconstructs the protected customer-price object from its own report map after model validation. Keep price formatting deterministic and outside the model prose channel; do not weaken the shared narrative validator to admit model-authored amounts. No price values or private price-derived claims may appear in generic facts, narrative, missing-input strings, or candidates.

Preserve existing public endpoints, private request shape, project choices, pagination, and checked-at time. Extend the answer/result contract additively with optional nullable `projectPricing`, strictly validated in backend, web, and mobile. It contains a fixed published-project-estimate policy, currency, publication/approval state, stable estimate/review/version references, bounded customer-visible line prices, and source subtotal/tax/total in integer paise. No internal cost/rate/margin/configuration metadata belongs in it. Missing data remains explicit; no guessed or default-zero values. Source links are server-generated permission-checked application paths.

Both surfaces use this protected field. Keep the old `commercial` field null and internal catalogue candidates empty for new answers. The Project Messages reader applies its existing commercial authorization decision to `projectPricing`, sets the existing `commercialAccess` state accordingly, and strips the entire object for unauthorized viewers. Private Ask Lisno returns it only to the authorized project Client. A missing field in older compatible responses means unavailable, never fallback to a Configuration price. Update public API documentation and client parsers/renderers together. Display “Published estimate” or “Approved estimate” with source/version, never the former “Approximate addition charges” presentation.

Protect Python with server-to-server authentication and a restricted network path. Require TLS for cross-host transport. Credentials belong only in server environment/secrets, never client bundles, prompts, or logs. No user JWT or database credential is sent to Python. The model endpoint stays private to the assistant host/network. Service and model destinations are fixed configuration, never user/model supplied; HTTP redirects are rejected. Test-only loopback transports are explicit exceptions for fake-service tests.

The disclosure restriction governs assistant-controlled retrieval, generation, and result presentation. Ordinary human-authored messages remain governed by existing chat permissions; this task does not introduce automatic moderation or rewriting of user messages.

- Preserve approved immutable baselines and leave other features' Configuration revision rules unchanged. Keep authorized monetary values in integer paise in the backend. Do not move finance formulas into Python or ask the model to calculate prices.
- For both chat surfaces, read project prices from the immutable customer publication/approval snapshot without joining live Configuration rates. Distinguish a published proposal from an approved contract. Reconcile an approved total with the canonical finance approval lineage; never replace it with a later draft or unapproved proposal. Missing/conflicting snapshots mean unavailable, never the zero-valued presentation fallback. Any legacy whole-rupee conversion must be explicit and exact at the boundary. Include only client-visible line prices, totals, and tax values already in that source, with stable estimate/review IDs retained for authorization and freshness checks.

- Python/model state is request-local only. No cross-user answer cache, model conversation reuse, background learning, or prompt/fact logging. Private requests create no shared messages, runs, notifications, emails, or attachments; existing admission/usage records remain allowed. ## Sensitive-data policy

These requirements apply to direct answers, model-assisted answers, errors, source links, debug output, telemetry, and deployment tooling alike:

- Never disclose credentials, access/session tokens, private storage references or signed URLs, bank/payment details, government identifiers, live configured rates, internal costs/margins/formulas, unpublished estimates, staff-only notes, vendor-confidential records/pricing, or another Client's data through chat. Existing application access elsewhere does not grant a chatbot exception. Requests to estimate, reverse-engineer, compare, or guess these internal values receive a neutral refusal without confirming the hidden value.
- Do not send those fields, phone numbers, email addresses, precise personal/site addresses, raw documents, or other confidential personal information to Python or the model. Keep all actual commercial amounts in the existing backend. Node may return only the project Client's permitted project details and already-published customer prices; shared-result readers additionally enforce the existing per-viewer commercial permission before returning prices.
- Create explicit typed projections for each tool result with denied-by-default fields. Do not serialize whole database records, existing fact bundles, source links, or raw free-text notes into the model request. Unknown/new source fields are excluded until classified and covered by tests.
- Apply privacy filtering to the latest message and every retained history entry before crossing the service boundary. Known identities/project references can be mapped to request-local aliases. Secret/PII detection supplements field allowlists; it is not proof that arbitrary free text is safe. If a request cannot be safely minimized, do not forward the raw text; use a neutral clarification or refusal without repeating the sensitive content.
- Restrict `client_profile` to non-sensitive help/navigation context for model use. Do not forward its currently available name/email/phone facts unchanged. Any permitted personal presentation, such as the existing local greeting, remains outside model context.
- Recheck the display policy in Node after answer reconstruction. References to a genuine source do not bypass field restrictions. Model instructions to reveal hidden fields, encode them, infer internal costs, or list other clients cannot expand the projection or display rules.
- Use only the independently hosted runtime. Disable cloud inference fallbacks, prompt tracing, external analytics/error-report bodies, and training/retention of client content. Restrict runtime network egress; downloading a pinned model artifact is a separate setup operation and must not include application data.
- Test with unique synthetic sensitive values inserted into each source, input/history, and failure path. Assert absence from the Node-to-Python payload, Python-to-model payload, logs, error bodies, and public response where prohibited. Include indirect disclosure and adversarial requests, not just literal keyword checks.

Confirmed display policy: show the Client their own authorized project information and published/approved customer prices. Hide configured prices and other internal Lisno information in both chat surfaces, including from otherwise-privileged staff through this assistant. If no permitted published price exists, state that it is unavailable and direct the Client to the project team; the model never claims it contacted anyone. Existing shared-thread routing remains server-owned. This restriction supersedes the earlier catalogue/recommendation/addition-preview chatbot capabilities.

## No cloud AI API dependency

Both private and Project Messages runtime paths must use the independently hosted model exclusively. Remove Gemini provider construction/selection from both chat paths, not just the default configuration. Do not read or forward cloud AI keys for them. No fallback, routing, moderation, embedding, reranking, translation, or evaluation helper may call a managed AI API for this functionality.

Configure Ollama with `OLLAMA_NO_CLOUD=1` on the independent server and permit only the pinned locally installed model artifact. Ollama documents this setting as disabling cloud features, including cloud models and web search. See [Ollama local-only configuration](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features). Reject cloud model selections and external inference destinations; unavailable/missing local weights must yield unavailability rather than automatic model pull or cloud inference.

The deployment must deny external runtime egress from the assistant/model services except explicitly required private service communication. The backend chat adapter has a fixed authenticated assistant destination and no redirect/fallback route. Package/model artifact download is an explicit setup operation on the independent host; it is separate from serving user questions and sends no application data. Normal unrelated application services retain their established networking.

Use fake transports and network-deny tests to prove neither chat path invokes Gemini or another AI provider, even when cloud keys are present elsewhere in the application environment. On the independent host, verify inference succeeds with external internet egress blocked after the pinned weights are installed. Use deterministic fixtures and human-reviewed expectations for evaluations; do not call a cloud model as a judge or create a new Gemini benchmark baseline.

Hosting may later be a separately owned machine or a rented server running the model itself. No managed cloud AI API is allowed in either case. The Mac remains outside the runtime.

## Speed, reliability, and model selection

Use direct verified answers for project lists and conservative, clearly recognized greetings/help/status intents. Ambiguous or mixed requests must go through clarification/model interpretation instead of an overbroad keyword match. Direct business answers still execute the same authorization and freshness checks.

Minimize model rounds, keep responses short, bound history, and keep the chosen model warm only on the AI server. Never drop the latest question, required context, or tool evidence to fit a prompt. No unvalidated token stream reaches the user. No cross-request caching of personalized database answers in this release.

Begin server evaluation with a quantized instruction model in the approximately 8B class; evaluate a larger alternative only if needed for quality and the host permits it. Qwen3-8B is one concrete candidate with an official Apache-2.0 model card and an Ollama Q4_K_M artifact listed at about 5.2 GB. Download size does not equal runtime memory, and this is a candidate, not a measured deployment recommendation. See [Qwen model card](https://huggingface.co/Qwen/Qwen3-8B) and [Ollama artifact](https://ollama.com/library/qwen3:8b). Pin the evaluated model digest, quantization, runtime version, context limit, and generation settings; do not silently follow a changing `latest` tag.

Proposed targets on the selected independent host, with a warm model and one active request: direct answers p95 at most 1 second; ordinary model-assisted questions median at most 5 seconds and p95 at most 12 seconds. Report complex multi-tool questions separately. For Project Messages measure generation after eligibility and report the preserved automatic two-minute wait separately; explicit requests do not inherit that automatic wait. These are evaluation targets pending host selection, not guarantees or observed results. Preserve the existing 90-second outer ceiling; bounded timeouts and cancellation must also apply inside Python and its model transport.

Retain existing request/concurrency/token protection and receipt settlement semantics; self-hosting removes Gemini's quota dependency, not finite capacity. Python also enforces a bounded concurrency/queue limit appropriate to its host. Exhaustion returns a sanitized busy response. Counters remain shared as currently implemented unless a later approved change explicitly separates them. Direct non-model paths do not incur model token charges. Usage is validated; absent usage retains conservative reservation rather than pretending zero consumption.

Retain the existing upper bounds of three tool rounds, six tools, four model attempts, 32 KiB request payload, and 2,048 output tokens. Apply bounded response reads and context-token limits as well. The new transport need not consume all allowed attempts; avoid retry amplification. Cancel outstanding generation on expiry/disconnect where supported, discard late output, release all slots, and never retry completed business reads blindly.

If Python or its model is unavailable, recognized direct paths may remain available where their required service is healthy; other requests return the established safe retry/unavailable state. Invalid output, unavailable facts, or changed authorization must never trigger a guessed answer. No automatic Gemini or external-model fallback. Do not show raw exception details, internal URLs, model traces, or secrets.

## Configuration, operations, and rollout

Use common Python service/model configuration with independent private Ask Lisno and Project Messages enablement. A Gemini or other cloud AI key is not required or consulted for either feature. Missing/invalid Python configuration disables generation safely, leaving ordinary chat/routing available. Do not offer a cloud-provider selection or implicit compatibility fallback. Keep the established shared-chat enablement semantics and leased workflow while replacing its generation provider.

Package the Python service and document a separate-server deployment with private model networking, resource limits, health/readiness endpoints, restart behavior, and secret configuration. Separate liveness from model readiness. Model downloads, model execution, container builds requiring substantial resources, and real inference evaluations run on the selected independent host/remote runner. Do not make this Mac an operational dependency or start background services here.

Logs/metrics include opaque request ID, selected route, model version, elapsed retrieval/inference/validation time, token counts, queue pressure, and sanitized failure category. Exclude prompts, facts, user identities, private URLs, and tokens. Health endpoints disclose only minimal operational state.

Add optional immutable project-price/disclosure-policy fields to the result schema and keep memory/Mongo adapters aligned; no destructive schema migration or historical backfill is required. Existing records without the new policy marker use the safe legacy read behavior. Document a coordinated rollout of result consumers, backend readers/writers, and the Python service. Drain/fence old in-flight Gemini chat workers before enabling the replacement, and reject publication of old/unclassified output under the new policy. A partially upgraded reader must not expose a protected object as generic facts.

Rollback disables affected AI entry points while preserving ordinary chat and the disclosure guard, or returns to a verified self-hosted-compatible release. It must not restore Gemini/cloud generation or legacy price disclosure. Production switching, infrastructure purchases, deployment, secret installation, and external communication require a separate explicit action/target authorization.

## Risks, assumptions, and remaining decisions

- Scope explicitly includes private Ask Lisno and Project Messages AI. Keep current Client-triggered behavior and existing staff result-viewing permissions; a new staff assistant workflow would require a separate scope decision.
- The confirmed sensitive-data boundary excludes Configuration prices and internal Lisno information from both chat surfaces. Published/approved customer prices use a protected field, never shared generic facts. Project Messages now requires persistence, result-reader, web, and mobile changes in addition to provider replacement.
- A separate server, credentials, operational owner, region, capacity, and spending limit are not yet selected. No purchase or deployment is authorized by approving the software specification.
- Model choice is provisional until quality and speed are measured on that server. Implementation can provide the tested service, adapter, fixtures, and deployment package before hosting is available; actual model quality, performance, and Mac-independent operation must remain explicitly unverified until the remote checks run.
- A self-hosted model can still hallucinate or choose the wrong tool. Deterministic sensitive facts, server reconstruction, validation, abstention, and adversarial evaluations reduce risk; they do not establish universal Gemini-level capability.
- Additional network hops and CPU-only inference may miss latency targets. Choose hardware/model using measured results; do not quietly relax correctness checks to achieve speed.
- Shared usage accounting, leases, publication transactions, result authorization, caches, and source helpers are regression-sensitive. Preserve their behavior while replacing both provider paths and introducing the protected project-price field; review the integrated result before final verification.

The next authorized stage after specification approval is a separate task-plan document. This specification does not authorize implementation, model installation, infrastructure provisioning, deployment, or production mutation.
