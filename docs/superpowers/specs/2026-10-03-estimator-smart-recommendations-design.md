# Estimator smart recommendations from configured Main Line relationships

Date: 2026-10-03  
Status: Slide-out and source-selection revision approved and verified locally in Mode A on 2026-10-03

## Goal

When Estimator/Sales includes a configured Main Line in a room, the estimator shows relevant, enabled recommendations saved in that Main Line's **Recommendation & Exclusions** tab. An actionable prompt names the related item or Sub-Basket, says whether it is required or optional, shows the configured **why** text, and lets the estimator deliberately select eligible related scope in the same room. For example, selecting POP / Gypsum → False Ceiling can suggest False Ceiling Painting, and selecting Functional Lights can suggest False Ceiling Functional Lights, only when those exact relationships are configured. Mapping uses stable IDs, never text similarity or hardcoded category names.

## Historical baseline before the original implementation

- `KnowledgeBudgetAlterationBuilder.tsx` authors structured `budgetAlterations` rules with `trigger`, `action`, `requirement`, `targetKind`, target Basket/Sub-Basket/Main-Line IDs, `reason`, and `active`. The target can be one Main Line or a whole Sub-Basket; an absent legacy `targetKind` means Main Line. The tab also has free-text `recommendations` rows, which have no target ID and cannot select a catalogue item.
- The web Estimator/Sales workflow is `LeadEstimateWorkspace.tsx` → `ConfiguredEstimateBuilder.tsx`. Inclusion is `ConfiguredLineDraft.included` for one `roomId` and `mainLineId`; `buildConfiguredLines` expands eligible catalogue lines by room. There is no recommendation read, prompt, or selection behavior in these files.
- `GET /estimation/catalogue` currently exposes a filtered, paginated hierarchy, item/revision identity, UOM, and a combined in-house base rate. `estimator-catalogue.service.ts` chooses an active item's active revision or an eligible Draft/Inactive item's appropriate revision, and batches the existing item/revision/section reads. It does **not** project recommendation rules. Estimator/Sales cannot safely read the full Configuration section APIs.
- Existing `ai-estimator-knowledge-context.service.ts` resolves active rule targets for the Configuration context, including legacy Main-Line and whole-Sub-Basket shapes, but that broader context is not an estimator-facing catalogue response. The September recommendation design explicitly deferred an estimator-facing acceptance screen.
- The initial worktree for this request is clean (`git status --short` returned no paths). Historical specifications describe prior intent; current code above is the implementation source of truth.

## Scope and product behavior

1. Add a contextual **Recommended for this room** area in the configured estimator's item-selection view. It appears for the active room when at least one included, currently available Main Line has applicable saved advice. Keep the originating Main Line, required/optional relationship, related target, and configured reason visible together. An inline count near a selected source may point to the area, but the area must be usable without opening Configuration.
2. Applicable actionable rules are from the exact source revision represented by the estimator catalogue: `active: true`, `trigger: "added"`, `action: "add"`, `requirement: "must" | "can"`, and a valid `main_line` or `sub_basket` target. Ignore disabled, removal, and source-removed rules for addition prompts. Active free-text `recommendations` rows may appear as separate named guidance with their reason, but they have no target ID and no Select action. Do not guess a target from their text, name, Basket label, or item type.
3. Resolve a Main-Line target by its stable `mainLineId` and declared parent IDs against the current eligible estimator catalogue. Resolve a whole-Sub-Basket target by its `basketId`/`subBasketId` and current eligible children. A target absent from the eligible catalogue or under a different parent shows a non-actionable availability/review state rather than a misleading Select button. An eligible temporary Main Line remains selectable. The estimator recommendation UI does not display **Must be completed**, Configuration completion warnings, or completion notes for that item or a whole-Sub-Basket child. Item-type labels such as **Temporary item** elsewhere in the estimator may remain.
4. **Select related item** explicitly includes an eligible target in the active room through the existing configured-line state and rate/quantity rules. If its Main Basket was not selected, the action also selects that Basket so the line remains visible. No other room's target is included. For a whole-Sub-Basket rule, show its current children for review and require an explicit action for each eligible child; never silently select the group or invent an unresolved child.
5. Show a Main-Line rule as selected when its target is included in the same room. Show a whole-Sub-Basket rule as selected when every current child is eligible and included in that room, regardless of internal Configuration completion state; an unavailable child still prevents a fully selected group. If two selected sources recommend the same target, show one target decision with both source names/reasons; `must` takes precedence over `can`. Deselecting a source removes its prompt, but does not remove a separately selected target or change its price. Selecting a target can reveal that target's own rules without automatic recursive additions.
6. Required additions are prominent and remain visible while missing. This first release is **advisory**: it does not auto-select targets or newly block draft save/estimate submission. The existing estimate save, totals, and client publication rules remain authoritative. A target selected from advice becomes an ordinary configured estimate line, with the same validation and financial treatment as manual selection.
7. Provide loading, empty, retryable error, stale-catalogue, unavailable-target, already-selected, and read-only estimate states. A failed recommendation read must not be presented as “no recommendations.” In read-only estimates, show current advice as information without selection controls. Keep the area accessible by keyboard and screen reader and usable at desktop and phone widths.

## Scope boundaries

- In scope: the web Estimator/Sales configured estimate builder, a restricted backend read projection, client data/query types, a short Configuration helper-text clarification that rule reasons are estimator-visible, focused tests, and API/authorization/OpenAPI inventory updates for the new read operation. The 2026-10-03 revision removes visible Configuration completion status from estimator recommendations only.
- Out of scope: AI or fuzzy inference from names; seeding the example relationships; changing Configuration rule fields or stored schemas; rewriting saved/approved estimate snapshots; automatic Estimate mutation; a persisted accept/dismiss decision; new pricing formulas; mandatory-rule submit enforcement; client-facing recommendation reasons; mobile estimator work (there is no mobile Estimator/Sales builder in the current app).
- No migration, dependency addition, production data write, deployment, commit, or push is expected.

## Recommended contract and efficient mapping

Use a bounded, batched, estimator-only read such as `GET /estimation/catalogue/recommendations` with a strictly validated set of selected source Main-Line IDs (at most 50 per request; the client may chunk larger sets). Query only selected sources and their chosen current revisions, then load their configured recommendation sections in one batch using the existing revision/section index. Return one restricted source result per requested ID with source revision ID/version and normalized rule summaries: rule ID, `must`/`can`, target kind and stable parent/target IDs, reason, and target availability/completion state. Return active free-text guidance as only its ID, name, and optional reason. The estimator resolves target display names from its already loaded eligible catalogue by ID. Do not return full Configuration payloads, vendor data, price internals, inactive rules, or unavailable target names. Generic unavailable results must not disclose an unauthorized ID's existence.

Register the new read in the canonical route-operation authorization registry and OpenAPI, using the existing `estimation.catalogue.read` permission plus the catalogue service's active-actor/role checks. No Configuration read permission is granted to Estimator/Sales. Match each recommendation section's `mainLineId` and `revisionId` to the chosen source revision. Normalize legacy absent `targetKind` as Main Line. Validate target parentage/status with batched reads; do not join on labels or issue a query per rule or selected row. Key and invalidate the client query by the sorted selected source identities and source revision versions; on a response/catalogue revision mismatch, disable Select and offer catalogue refresh.

The rejected simpler option is embedding every rule and up-to-4,000-character reason in every paginated catalogue line. That would ship recommendations for unselected items and make full-catalogue payload size grow with all configured rules. A per-line request is also unsuitable because it scales network and database reads with the number of selected lines. The bounded batch keeps the already filtered catalogue separate and sends only relevant relationship data.

## State, identity, authorization, and failure invariants

| Concern | Required behavior |
| --- | --- |
| Room scope | Evaluate only included source lines in the active room; a target selected in another room does not satisfy it. |
| Identity | Use `roomId`, source `mainLineId`/revision, rule ID, target kind, and target IDs. Names are presentation only; same-name records under different parents remain distinct. |
| Eligibility | Source revision and target availability must agree with the current estimator catalogue. Draft/Inactive ready sources use the same revision policy as the catalogue. Archived, missing, and wrong-parent targets cannot be selected from advice. Eligible temporary Main Lines remain selectable without displaying Configuration completion status in the estimator. A whole-Sub-Basket is selected when every current child is eligible and included in that room; unavailable children still prevent full selection. |
| Finance | Advice alone changes no line, rate, quantity, amount, GST, saved estimate, or approval. An explicit target selection follows existing integer-paise calculations and source-version checks. |
| Permission | Only an actor already allowed to read the estimator catalogue may call the restricted recommendation read. Backend checks remain authoritative. |
| Failure | Recommendation fetch errors retain the estimate draft and expose Retry; stale responses never auto-apply. Refreshing the catalogue/recommendations recomputes satisfaction without duplicating selected lines. |
| Logging | Safe diagnostics may record IDs, counts, result codes, and duration; do not log free-text reasons or private catalogue payloads. |

## Risks and controls

- Existing reason text was authored in Configuration. Treat it as estimator-visible copy in this projection, and update its Configuration helper text so future authors understand that audience. Return only the rule reason; do not expose other internal fields. An estimator-facing content review of existing reasons is an operational follow-up, not a data migration.
- A whole-Sub-Basket rule may include temporary or otherwise ineligible children. Surface unavailable children and require review; never claim the group is fully selected based on a partial eligible list. Configuration remains the place to see and manage its completion status.
- Rules can overlap or form cycles. Deduplicate by target stable ID within a room, retain every source/reason, and require an explicit user action for each addition so the UI cannot recursively add lines.
- Catalogue and rule revisions can change concurrently. Return source revision metadata, compare it to the loaded catalogue, and rely on existing estimate save version/source checks before persistence.

## Acceptance criteria

1. With a configured POP / Gypsum → False Ceiling source selected in one room, an enabled `added/add` rule to False Ceiling Painting appears with its saved reason and required/optional status. Selecting the recommendation includes the exact target only in that room, even if the Painting Main Basket was not selected. The same holds for a Functional Lights source recommending False Ceiling Functional Lights when configured.
2. No example relationship is hardcoded or inferred by name. Two identically named target Main Lines under different parents map to the configured stable ID. Legacy Main-Line rules without `targetKind` work.
3. A configured whole-Sub-Basket rule shows its current children and unavailable status; explicit selection includes only reviewed eligible children in the active room. Empty, archived, wrong-parent, and stale targets never become selectable. Eligible temporary children have no **Must be completed** or other Configuration completion label in the estimator. When every current child is eligible and selected in the active room, the group shows selected even if Configuration still tracks completion internally; unavailable children prevent full selection.
4. Disabled/removal/source-removed rules do not produce addition prompts. Active free-text advice appears without a fabricated selection action. A selected target is marked satisfied; duplicate sources consolidate without losing their reasons, with required taking precedence. Deselecting a source does not silently remove a target.
5. Suggestions change no estimate totals until the estimator explicitly selects a target. Selected targets use the existing source-version, quantity, rate, save, and integer-paise paths; saved/approved historical estimates are not rewritten.
6. Estimator/Sales can read only the restricted projection through its existing catalogue-read permission. Other roles and inactive actors are denied. No full Recommendation section, private cost/vendor data, or unavailable target names leak through the response.
7. The batched read is bounded, uses batched database access rather than N+1 queries, and handles more than 50 selected sources through bounded client requests. Permission, pagination/source version, duplicate names, two unequal rooms, and refresh/failure cases have focused backend/frontend tests.
8. Rendered desktop/phone checks cover selection, reason display, required/optional distinction, loading/error/retry, keyboard/accessibility, and read-only behavior. Estimator recommendations for eligible temporary targets and whole-Sub-Basket children contain no **Must be completed** or Configuration completion note in visible text, accessible names/descriptions, or tooltip text. Backend/frontend typechecks, focused tests, affected builds, route-operation/OpenAPI checks, `git diff --check`, and final dirty-path review are recorded.

## Proposed 2026-10-03 alert and modal revision

This revision supersedes the earlier always-expanded **Recommended for this room** presentation. The approved relationship mapping, selection, completion-status, and finance invariants above continue to apply.

### Goal and current evidence

After the estimator selects a source Main Line, its new recommendations should arrive as a clear, modern alert. The estimator can review the configured reason and select a related item from a modal. Selecting that item must perform the same room-scoped inclusion, basket reveal, source-version checks, and rate/quantity behavior that the current inline **Select related item** action performs.

The current local implementation derives room advice in `LeadEstimateWorkspace.tsx` from a batched recommendation query, renders the full **Recommended for this room** panel above the basket list in `ConfiguredEstimateBuilder.tsx`, and guards selection in `selectRecommendedLine`. `EstimatorRecommendations.tsx` already displays direct targets, whole-Sub-Basket children, guidance, selected status, unavailable status, and retry/refresh states. The shared `Dialog` component supplies a portal, focus management, Escape/backdrop close, background isolation, and return focus. The worktree contains the previously approved recommendation implementation and other uncommitted changes; these must be preserved.

### Recommended experience

1. Replace the always-expanded recommendation panel in the item-selection area with a compact, persistent alert for the active room whenever current advice exists. It shows a plain-language pending count, the strongest pending priority (**Required** before **Optional**), and a **Review recommendations** button. When all actionable targets are selected, it shows a reviewed state and still allows reopening the details. Guidance-only advice remains reviewable. It does not obstruct basket or rate editing.
2. When the estimator newly includes a source Main Line in the active room and the latest matching response contains a pending actionable recommendation, automatically open one recommendation dialog after the response is ready. Do not auto-open on initial draft restoration, room switch, catalogue refresh, query refetch, target selection inside the dialog, or every render. A dismissal is local to that source inclusion event; new source inclusions may open the dialog again. The alert always permits manual reopening. No persisted accept/dismiss record is added.
3. The dialog shows the active room, source name, configured reason, Required/Optional priority, target name and parent, and one **Select item** action per eligible unselected Main-Line target or eligible whole-Sub-Basket child. It shows selected targets as **Selected**, retains all reasons when sources overlap, and explains unavailable targets without a Select action. Free-text guidance is informational and has no Select action. It never shows **Must be completed** or Configuration completion notes in visible or accessible copy.
4. Each modal Select calls the existing `selectRecommendedLine` path. The target is included only in the active room, its Main Basket becomes visible, and the current quantity/rate validation and totals apply. The dialog stays open so the estimator can select several related items; it updates each item's selected state immediately. A clear **Done** control closes it and reveals the updated builder. Dismissing the dialog by Done, Escape, backdrop, or Close never selects or rejects anything.
5. The compact alert and dialog use the current Lisno typography and restrained colors, with crisp boundaries and no added decorative icon, drop shadow, gradient, or animation. Use the shared dialog/overlay behavior; provide a visible text Close or Done action, appropriate initial and return focus, a bounded scrolling body, and a mobile layout that fits 390 px without horizontal overflow. Because the advice is nonblocking, use a normal dialog rather than an urgent `alertdialog`; announce the alert summary accessibly without repeatedly interrupting the estimator.
6. Loading, error, forbidden, stale-catalogue, historical, unavailable, empty, and read-only states remain truthful. A failed or stale read must not open actionable advice or expose a Select control; retry/refresh stays available. Read-only estimates may open advice for review but cannot select. Selecting a target that becomes a new source may update current advice in the open dialog, but must not spawn another dialog or recursively select anything.

### Scope, invariants, and choices

- In scope: estimator alert/dialog presentation, its local open/dismiss trigger state, reuse of the existing guarded selection callback, scoped CSS, and focused interaction/accessibility tests. No change to recommendation matching, backend API/authorization, stored schemas, Configuration authoring, estimate save/approval, prices, or client-facing screens. No dependency, migration, production write, commit, push, or deployment is planned.
- Identity and eligibility remain based on active `roomId`, exact source revision, rule ID, and stable target IDs. A current response may drive the dialog only while it matches the loaded catalogue. Auto-open state is session-local UI state, not a new business workflow. Advice alone changes no estimate line or total.
- A persisted source without both saved item and revision version provenance is treated as historical advice, even when its revision ID still matches the current catalogue. It must not receive current actionable recommendations after a catalogue update.
- Recommended approach: one auto-open dialog for a newly selected source plus a persistent compact alert to reopen it. This makes fresh advice visible while retaining a way to review it after dismissal. A manual-only alert would be less interruptive but would not make the new recommendation as apparent when the source is selected. A permanently open modal would prevent normal estimate editing and is not suitable.
- Risks: asynchronous responses can arrive after a room/source change; auto-open must be tied to the initiating room and source event and cancelled if that context no longer matches. Repeated source and target changes must not produce a dialog loop. Multiple recommendations must remain individually selectable, including whole-Sub-Basket children. Focus must return to a meaningful control if the original source row disappears.

### Acceptance criteria for the alert and modal revision

1. In an editable room, selecting POP false ceiling with a configured Painting relationship produces a compact alert and opens one dialog when matching advice is ready. The dialog shows the source, reason, priority, target, and Select action. A second configured relationship, such as Functional Lights to False Ceiling Functional Lights, behaves from configuration rather than hardcoded names.
2. Selecting a direct target or one whole-Sub-Basket child in the dialog uses the existing inclusion path: only the active room changes, the target Basket becomes visible, missing rates remain subject to current validation, and totals change only through included priced lines. The dialog updates the selected state and remains usable for other choices; Done reveals the updated builder.
3. Closing without selecting changes no estimate state. Reopening from the alert shows current selected/pending advice. The dialog opens at most once for one source-inclusion event, does not auto-open during draft restore/refetch/room switch, and does not reopen because a target was selected from within it.
4. Duplicate sources retain their reasons and required precedence. Unavailable, stale, forbidden, failed, guidance-only, empty, and read-only cases present appropriate information without an invalid Select action. A whole-Sub-Basket still requires child-by-child selection and obeys the approved selected-state rule.
5. Desktop and 390 px rendered checks cover alert visibility, modal layout, focus entry/return, Escape and button dismissal, keyboard Select, accessible names, no **Must be completed** copy, no overflow, and no console/network errors. Focused frontend tests, typecheck, build, `git diff --check`, and final dirty-path review pass; backend checks are rerun only if a shared contract changes.

### Open decisions for approval

The proposed default is automatic opening only after a user newly includes a source with pending actionable advice; saved drafts and room switches show the alert without interrupting work. Approval accepts that trigger and the dialog staying open after each Select so multiple related items can be chosen.

## Proposed 2026-10-03 line-item slide-out and dismissal revision

This revision supersedes the alert-and-modal presentation and its rule that closing never changes estimate state. The configured relationship read, stable-ID matching, target eligibility, room-scoped selection, and rate/quantity calculations above remain the source of truth.

### Goal and current evidence

The estimator should see a short list of actual related line items in a slide-out panel. When a newly checked source Main Line opens that panel and the estimator closes it without selecting a related item, the initiating checkbox should return to unchecked. This prevents an accidental backdrop or Escape dismissal from leaving that source selected without any chosen related scope.

Today `LeadEstimateWorkspace.tsx` sets `ConfiguredLineDraft.included` to true as soon as the source checkbox is checked, then stores only a pending source event until advice is ready. Its auto-open effect clears those events when it opens the modal. `onCloseRecommendations` only closes the modal and clears pending events, so it cannot identify or undo the source inclusion. `EstimatorRecommendations.tsx` uses the shared centered `Dialog` and renders recommendation headings, Basket/Sub-Basket labels, reasons, group progress, child rows, guidance, and a Done footer. The screenshot shows this dense modal. The frontend already has a portal-based right `Drawer` with backdrop, Escape, focus management, scrolling, and responsive presentation; reuse it for the requested slide-out.

### Required interaction

1. Keep the compact in-page recommendation alert and its manual **Review recommendations** action. Replace the centered modal with one right-side contextual slide-out; at phone widths it uses the available viewport width. It has a visible Close action, a bounded scroll area, keyboard focus entry/return, Escape and backdrop dismissal, and reduced-motion behavior.
2. The primary list is one row per eligible recommended **individual line item**: its current catalogue name, a concise Required/Optional cue, and **Select item** or **Selected**. A whole-Sub-Basket rule is flattened into its eligible child Main Lines or temporary line items; do not repeat a Sub-Basket title, recommendation title, Basket path, count/progress paragraph, or separate child card. Deduplicate a target by stable target identity while retaining all source relationships. No item is selected merely by opening the slide-out.
3. Preserve the previously requested explanation of why an item is needed without the dense default layout: each row has a short, keyboard-accessible **Why?** disclosure containing its configured source name(s) and reason(s). Do not infer or manufacture explanation text. Loading, unavailable, historical, guidance-only, stale, forbidden, error/retry, and read-only states remain concise and truthful; no unavailable or free-text guidance entry gets a Select action. Do not display Configuration completion status.
4. Only an **automatic** slide-out created by newly checking source line(s) carries a cancellation context. Track each initiating line by room and stable line/source ID until that slide-out closes. For each initiating source, if no currently included, eligible recommended line item is linked to it when the slide-out closes, set only that source line's `included` flag back to false. This applies to Close, Done, backdrop, and Escape. If one linked item is selected, keep that source; one target may satisfy several sources. A failed Select callback does not count. The estimate total and selected count then follow the existing configured-line calculations.
5. Opening the slide-out manually from the alert has no cancellation context and closing it never unchecks existing lines. Already included lines restored from a saved estimate are not newly triggered by restoration. A room/tab change, explicit source uncheck, catalogue change, save hydration, or stale/failed recommendation response cancels an obsolete opening context without changing lines in another room. A source with no actionable advice does not auto-open or roll back. A compact status announcement explains any automatic uncheck, and focus returns to a surviving trigger checkbox or stable builder control if the alert disappears.
6. Selecting a recommended line uses the existing guarded `selectRecommendedLine` path and keeps the slide-out open for additional choices. The target is included only in the active room, its Basket becomes visible, and existing rates, quantities, totals, source versions, save validation, and authorization remain authoritative. No new backend enforcement, persistence record, API, migration, or dependency is required.

### Scope, assumptions, and risks

- **Interpretation:** “slider” means the existing right-side `Drawer`, not a carousel. “Show just main line item” means the default content is actual selectable target line names rather than recommendation/group headings; the Why disclosure retains the earlier requirement to explain the relationship. Eligible temporary line items remain possible targets because Configuration rules can point to them.
- **Dismissal rule:** “We should select something” means at least one linked eligible target for each newly checked source in that automatic opening. It does not turn Configuration `must`/`can` into a backend submit gate and does not undo previously selected, unrelated target lines. A selected target already present in the active room also satisfies its linked source.
- **Safety:** The worktree contains approved, uncommitted recommendation and recent header CSS changes in the same files. Preserve those diffs. Changes should be limited to estimator slide-out presentation, local source-inclusion lifecycle, scoped styling, and focused tests. No Configuration, backend, pricing, saved snapshot, approved estimate, or client-facing change is in scope.
- **Risk controls:** Multiple rapid source checks can share one automatic opening; evaluate cancellation per source and deduplicate by room/line identity. Do not use display names as join keys. A changed or failed recommendation response must not trigger rollback based on untrusted/stale advice. Avoid an auto-open loop after rollback or after a target is selected in the slide-out. Preserve keyboard focus and visible totals when the alert disappears.

### Acceptance criteria for this revision

1. Checking a source with current actionable advice opens one right-side slide-out. At desktop and 390 px the panel fits the viewport, keeps its Close action reachable, does not horizontally overflow, and is operable by pointer and keyboard.
2. The slide-out's default list shows each distinct eligible target line once, including whole-Sub-Basket children, with its name and Select/Selected state. Configured source/reason text is available through Why. Dense recommendation titles, Basket paths, child group progress, and Configuration completion wording are absent.
3. Closing an automatic slide-out without a linked target selected by Close, Done, backdrop, or Escape unchecks only its initiating source line(s) in the active room and recalculates selected counts/totals. With a linked target selected, both source and target remain included. With two initiating sources, only unsatisfied sources are unchecked; one shared selected target can satisfy both.
4. Closing a manually reopened slide-out never changes line inclusion. Restored or read-only estimates, no-advice sources, stale/error states, room changes, and a failed Select action cannot cause an unrelated rollback or selection. Selection remains scoped to stable IDs in the active room.
5. Focus and announcements make cancellation understandable. Loading, retry/refresh, unavailable, guidance-only, historical, and read-only states remain accurate and non-actionable where appropriate. Focused interaction tests, frontend typecheck/build, rendered desktop and phone checks, accessibility/console checks, `git diff --check`, and dirty-path review pass.

### Open decision for approval

Approval adopts the stated interpretation: automatic dismissal without a linked selected target unchecks the newly checked source, while manual review dismissal preserves existing selections. The right-side Drawer and collapsed Why explanation keep the default panel focused on individual line items.

### Revision outcome

The approved right-side slide-out now lists each eligible target line once, with Required/Optional, Select/Selected, and a per-line Why disclosure. Automatic openings retain the newly checked source identities; closing without an eligible linked selection unchecks only those unsatisfied sources and announces the change. Manual Review never rolls back existing lines. Save or submit initiation and saved-response application cancel a pending automatic opening, preventing a locally rolled-back source from disagreeing with a persisted draft. Current catalogue eligibility also determines whether an included target satisfies advice, so a historical line does not hide an actionable recommendation. The final verification evidence is recorded in the linked task plan.
