## Goal and recommended behavior

When the approved estimate classifies a **Main Basket** as **Standard**, opening that basket in **Procurement → Projects** should show **Sub-vendor** as the suggested mode for each eligible included configured line. Show its saved Configuration base rate and a server-calculated total using the applicable low-quantity rule. The basket can show this useful cost immediately, while clearly marking an unsaved suggestion as provisional. A buyer still explicitly saves a mode decision before preparing a vendor-facing BOQ.

For a Sub-vendor line, the displayed cost is the existing calculator's `adjustedCostPaise`: base quantity cost plus the applicable low-quantity adjustment, with its established paise and UOM rounding. It excludes Lisno's selling margin, discounts, GST, and any vendor bid. Do not show a separate “Low quantity impact” row or column in this Main Basket component.

## Current behavior and evidence

- The approved estimation feature stores `selectedMainBasketClassifications` and configured-line `classification` in the immutable `EstimateClientReviewRound.estimateSnapshot`; missing historical values mean Standard. Basket and line classifications may differ. The classification currently has no procurement effect.
- `approvedProcurementSnapshotFromRows` in `backend/src/services/procurement.service.ts` obtains the immutable approved snapshot through `financeApprovalLineage`, but `ApprovedProcurementSourceLine` and `approvedSnapshotLines` omit basket classification. `buildProjectPurchaseOrderPreparation` therefore cannot carry it to `projectProcurementBaskets` or the basket API.
- `resolvePurchaseOrderModes` batch reads the approved line's pinned Configuration revision, sections, UOM, and saved procurement decisions. Without a saved decision it returns `selection_required` and no preview. `ProcurementBasketModeEditor` initializes its radios from a saved decision only and shows “Mode required” until the buyer chooses, previews, and saves a mode.
- `projectProcurementBaskets` sums ready lines' `preview.baseCostPaise` and `preview.adjustedCostPaise`, but uses `preview.sellingPaise` for `workingTotalPaise`. `ProcurementBasketScopePanel` shows that selling amount for each line and the footer. The selling amount includes margin and does not represent the requested base-plus-low-quantity cost.
- `calculateKnowledgeSubVendorPrice`, reached through `analyzePurchaseOrderModeSettings`, applies the saved low-quantity impact when calculation quantity is **at or below** the saved limit. It rounds the adjusted unit rate in paise before multiplying by the UOM-scaled quantity. Its `baseAmountPaise`, `lowQuantityImpactAmountPaise`, and `revisedAmountPaise` already reconcile; the purchase-mode preview exposes them as `baseCostPaise`, `lowQuantityImpactPaise`, and `adjustedCostPaise`.
- The basket BOQ guard requires a `ready` saved mode. A preview alone cannot make a line orderable. The procurement basket list, detail, mode editor, and BOQ flow already use approved source IDs and an authorization-protected project route.
- The relevant procurement backend and frontend files have existing tracked and untracked changes in a dirty worktree. This specification changes none of them; implementation must preserve those edits and inspect each target diff before writing.

## Calculation and display contract

The established Sub-vendor formula is authoritative. Conceptually, `base cost = quantity × saved Sub-vendor base rate`; when `quantity <= saved lowQuantityLimit`, the saved impact increases the **unit rate**, which is rounded in paise before multiplying by the quantity. The displayed adjusted cost is `baseCostPaise + lowQuantityImpactPaise = adjustedCostPaise`. For example, a whole-unit quantity of 5, a base rate of ₹100, a qualifying 10% impact, and no other adjustment gives ₹550 of adjusted cost. The implementation must use the canonical calculator rather than calculating the percentage in React or applying it again to the subtotal.

The Standard-basket API should expose basket classification and a **separate** display cost/completeness/provisional status, with line-level cost provenance and base rate, in additive fields. Retain `workingTotalPaise` and existing saved-mode `preview.sellingPaise` semantics for current preparation, request, and historical consumers; do not relabel a selling benchmark as cost. The read-only default preview must remain distinct from `mode.decision`, `mode.state === "ready"`, and vendor-payable DTOs. The basket card and detail consume one consistent server projection. Keep OpenAPI and frontend API types aligned with that projection.

Only use the approved source identity, stable Main Basket ID, stable source-line key, pinned revision/digest, saved UOM scale, and saved Sub-vendor settings. Derived suggestions may be calculated in the existing batched mode-resolution read; avoid one database round trip per line. Do not add a read-side audit or persist a suggestion. Do not change an existing tender/preparation digest solely because a read-only suggestion is available; saved decisions and genuine approved-source changes retain the established digest/conflict behavior.

## Material choices and recommendation

| Choice | Effect |
| --- | --- |
| **Recommended: preselect and preview Sub-vendor without saving** | Shows the requested rate and total immediately, keeps existing explicit buyer confirmation and BOQ safety, and leaves an auditable saved decision only when the buyer acts. |
| Automatically persist Sub-vendor decisions on basket read | Would turn a read into financial mutation, create race/audit questions, and make BOQ lines orderable without buyer confirmation. This conflicts with the established decision workflow. |

For totals, add a distinct adjusted-cost presentation value instead of redefining `workingTotalPaise`; existing consumers use the latter as a selling benchmark. This preserves the current contract while changing the visible Standard-basket amount to the requested cost.

## State, permissions, compatibility, and failure handling

- States are: `suggested Sub-vendor cost` (valid read-only preview), `observed, unverified cost` (calculable pinned content with digest mismatch), `saved mode cost` (ready decision), and `unavailable/incomplete` (missing or invalid source). A Special basket keeps the current `selection_required` path. A saved override is never reset on reload.
- Backend project authorization remains authoritative. Only already-authorized internal Procurement/Super Admin views receive internal rates; vendor/client/public BOQ and bid payloads do not. Existing mode save permission and audit remain unchanged.
- Historical approved snapshots without classifications read as Standard without disk rewrites. Historical mode decisions, pending requests, sent enquiries, bid revisions, and issued orders remain immutable and readable. No migration or backfill is included.
- Query invalidation after a mode save refreshes list, detail, and purchase-order preparation, so provisional totals become saved totals. Stale source/version, invalid pin, calculation failure, and missing permissions show specific errors. The existing order guard continues to revalidate mode readiness independently.
- Configuration deletion and draft-copy code preserve active and superseded records; existing saved records are not rewritten. No external email, production mutation, deployment, or vendor communication is included.

## Risks and controls

| Risk | Control |
| --- | --- |
| Treating an unsaved suggestion as an approved financial decision | Explicit suggested status in UI/API; preserve `selection_required` and BOQ guard until versioned save. |
| Displaying selling price instead of requested cost | Use `adjustedCostPaise` and an internal-cost label; keep `sellingPaise` contract separate. |
| Percent arithmetic or UOM rounding drift | Reuse saved pinned Sub-vendor calculator; test fractional quantities and one-paise boundaries. |
| Masking stale or mismatched Configuration with a new suggestion | Never suggest over an existing decision; mark an observed digest mismatch as unverified, show a review warning, and keep BOQ blocked. |
| Basket/line classification mismatch or duplicate names | Resolve basket classification by approved Main Basket ID; join lines by source key, not names. |
| Partial sums presented as final or costs leaking to vendors | Complete/provisional status must be explicit; keep internal projections out of vendor payloads. |
| Existing tender links change from presentation-only data | Keep read-only suggestion out of tender/preparation digests and preserve historical workflows. |
