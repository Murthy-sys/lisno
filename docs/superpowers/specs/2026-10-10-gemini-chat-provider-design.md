# Gemini provider for Ask Lisno and Project messages

Date: 2026-10-10 (Asia/Kolkata)
Status: Approved; implemented, locally verified, and live synthetic greeting/tool checks passed

## Goal

Replace the OpenAI provider used by Lisno AI with Google's Gemini API for both private Ask Lisno and automatic Project-message replies. Preserve the existing agent behavior, user experience, authorization, read tools, server-computed prices and publication safeguards.

This is a provider migration, not a credential-value substitution: the existing implementation sends the OpenAI Responses protocol directly to an OpenAI endpoint. A Gemini key cannot authenticate that request.

## Current behavior and evidence

- `backend/src/server.ts:163` reads `OPENAI_API_KEY` and `OPENAI_PROJECT_CHAT_MODEL`, checks `PROJECT_CHAT_AI_ENABLED`, and constructs `createOpenAiAssistantProvider`. Missing configuration disables generation without preventing human chat startup.
- `backend/src/services/project-assistant-openai.ts` contains the provider/context interfaces, conversational instructions, tool schemas, source-selection checks, transport and generation loop. Its request goes to `https://api.openai.com/v1/responses` with a Bearer key, `store: false`, structured final output and function-call exchanges.
- Both `backend/src/services/ask-lisno.service.ts` and `backend/src/services/project-assistant-runtime.ts` consume the same `AssistantProvider` contract. `app.ts` and the Project-message service also import that contract from the OpenAI-specific module.
- `backend/src/domain/project-chat-assistant.ts` specifies the full 120-second automatic human-response window, bounded context, three tool-result rounds, six tools, four HTTP attempts, timeouts, concurrency and token/admission limits.
- Ask Lisno's authorized project list is generated by the server without a model call. Private project resolution binds a stable authorized project before reads. Project-message publication rechecks source/authority versions and human replies.
- `backend/src/config/env.ts`, `backend/.env.example`, `backend/tests/config.test.ts`, `backend/tests/server.test.ts`, provider tests and `docs/operations/project-messages-ai.md` currently name OpenAI. `render.yaml` does not currently declare assistant-provider variables.
- Existing uncommitted critical-task review changes are a separate completed task. Preserve all of them. No secret environment file has been read or changed during this investigation.

## Scope and non-goals

In scope: a Gemini provider behind the existing contract, narrowly shared provider-independent policy/validation where required, backend environment/startup wiring, equivalent provider regressions, and local/Render environment documentation.

Not in scope: chat redesign, new tools, streaming, attachment analysis, general web search, changing response timing, changing project access, price calculations, notifications, database schema, historical assistant records, migration/backfill, deployment, rotating/revoking an existing key, or other completed requests. Do not add automatic OpenAI fallback or a multi-provider settings screen.

## Proposed approach and alternatives

**Recommended: native Gemini REST adapter using existing `fetch`.** Keep the application contract and business tool execution intact, and replace the transport/message protocol. This matches the current dependency-free provider boundary and supports the existing abort, response-size and usage controls. Native tool history, response parsing and usage mapping require dedicated tests.

Alternative: use Google's official `@google/genai` SDK. It can handle protocol details such as tool-history signatures, but adds a dependency and still requires Lisno's own authorization, validation, bounds and accounting. The current small fetch boundary makes a native adapter reasonable; no dependency is planned.

Use the Gemini Developer API with an AI Studio API key, not Vertex AI service-account credentials. Use its documented `generateContent` REST boundary for the adapter, preserving native tool-call response parts and any required thought signatures in bounded, temporary memory. Google's current documentation describes both structured output and its combination with function calling for `gemini-3.8-flash`; the combined feature is marked Preview. Do not assume every configurable Gemini model supports the same combination. See [structured output and tools](https://ai.google.dev/gemini-api/docs/generate-content/structured-output#structured_outputs_with_tools) and [function calling](https://ai.google.dev/gemini-api/docs/function-calling).

## Configuration contract

| Backend variable | Proposed behavior |
| --- | --- |
| `GEMINI_API_KEY` | Sole credential used by the new provider. Server-only, supplied separately in local backend environment and Render backend environment. |
| `GEMINI_PROJECT_CHAT_MODEL` | Default `gemini-3.8-flash`; an explicit compatible model may override it. No automatic model substitution. |
| `PROJECT_CHAT_AI_ENABLED` | Retain current `false` default and enablement semantics. Applies to both chat entry points. |
| `PROJECT_CHAT_AI_DAILY_TOKEN_LIMIT` | Retain current daily shared allowance and existing accounting receipts. |

Google documents `GEMINI_API_KEY` as an environment credential and `x-goog-api-key` for REST authentication. Send it only in the provider request header, never the URL or a frontend variable. [Gemini API keys](https://ai.google.dev/gemini-api/docs/api-key)

The proposed model is listed in the current official catalogue. Account access, regional availability and live response quality remain unverified until the configured account is evaluated. [Gemini models](https://ai.google.dev/gemini-api/docs/models)

Remove active reliance on `OPENAI_API_KEY` and `OPENAI_PROJECT_CHAT_MODEL` for these features. Old environment entries may remain in a deployment but must not be used, forwarded to Gemini or trigger fallback. Update the example environment and operations guide. Actual secret values are never copied into source, chat, logs, fixtures or screenshots. No live Render settings or `.env` secrets are changed as part of specification/planning.

## Required behavior and invariants

1. Both entry points receive the same Gemini provider through existing dependency injection. Type imports should use a neutral contract module rather than an OpenAI-named implementation. Limit extraction to policy, tool schemas/execution and validation actually shared by the generation boundary; do not build a generic AI framework.
2. Preserve natural, polite conversational instructions: relevant greetings, proportionate acknowledgment of frustration, direct answers and no repetitive bot introductions. Social replies do not require profile/project reads.
3. Preserve the two-minute automatic Project-message window and human-reply suppression. Ask Lisno remains immediate. Existing internal alert routing continues independently of model availability. Authorized project-list requests remain server-generated and do not consume model attempts.
4. Keep all existing read-tool allowlists and argument validation. Gemini may request only tools available to that specific request; project resolution precedes project reads, and profile tools remain private-chat-only. Execute allowed calls deterministically within the existing tool limit. Unknown, malformed or extra tool instructions fail safely.
5. Preserve stable source IDs, source-version witnesses, project/user authorization and publication-time checks. Model prose cannot authorize writes, make commitments, approve work or change estimates.
6. Retain current output semantics and Zod/narrative validation. Only known fact, catalogue and opaque price-preview references may be selected. Financial calculations and amount presentation remain server-owned, with no internal costs or hidden margins added to model context.
7. Keep keys out of frontend bundles. Use a fixed Google endpoint and validate model identifiers so configuration cannot redirect authenticated requests. No arbitrary base URL, hosted tool, public search or attachment retrieval is introduced.
8. Bound request and response size, tool turns, HTTP attempts and cancellation. Safely distinguish rate limits, transient server/network failures, timeouts, content blocking/refusal, incomplete results, malformed JSON and unknown sources. Do not show raw provider bodies/errors or publish partial output.
9. Reserve budget before every provider call and settle once. Map Gemini usage into the existing input/output accounting without omitting thinking tokens or double-counting totals. Missing or invalid usage must retain the conservative reservation, including failed/incomplete responses. Google's response defines separate prompt, candidate and thought counters and a total. [GenerateContent usage metadata](https://ai.google.dev/api/generate-content#UsageMetadata)
10. Preserve the existing overall time and token limits. Configure the selected model's reasoning/output controls explicitly enough to stay within the reserved budget; do not silently increase limits or introduce an extra unaccounted final-formatting request.

## Data, API, UI and compatibility

No frontend response contract, public route, permission, database model or migration is required. Existing persisted assistant answers, runs, result snapshots and usage receipts remain readable. New attempts use the newly configured provider; previously completed answers are not regenerated.

Human chat must start and work when Gemini is disabled, missing a usable key/model or failing. Ask Lisno and Project messages retain their existing safe unavailable/retry states. The Lisno identity and branding remain the same.

An administrator enables the provider using the existing environment flag and the Gemini key/model. Stopping generation still uses `PROJECT_CHAT_AI_ENABLED=false`; rollback preserves records and uses the previous application/configuration version, without deleting receipts or resetting usage. No automatic provider failover.

## Risks and failure handling

- Tool exchange, supported schema keywords, thought signatures and usage accounting differ from OpenAI. Validate the exact outgoing wire format and incoming response cases with synthetic fixtures; preserve required signatures in memory without logging/storing hidden reasoning.
- Structured-output/tool combinations depend on model support. Pin the documented default, fail safely for unsupported models and describe that arbitrary overrides require validation. Recheck official documentation when implementation begins.
- Google data-handling controls differ from OpenAI. Update operations guidance to describe the actual Gemini mode used; never claim that OpenAI's `store: false` automatically transfers, or that the integration has zero provider retention. Only the existing bounded client-visible context is submitted.
- Mocked tests establish protocol and application behavior, not live model quality, credentials, quotas or latency. A live synthetic smoke test requires an available configured Gemini credential and the appropriate live-call authorization; never send real client data as a test.
- Preserve the existing dirty worktree. Any shared target must be compared with its current diff before edits. No unrelated fixes or formatting sweeps.

## Acceptance criteria

1. With Gemini configuration enabled, both Ask Lisno and automatic Project replies use the Gemini endpoint and Gemini key; no active OpenAI requests or credential fallback remain.
2. Local/Render setup is documented using the variables above. Disabled, empty/malformed and provider-rejected credentials produce safe behavior while human chat/alerts remain usable.
3. Social messages, profile help, authorized project-name resolution, project status, execution status, catalogue/recommendations and approximate-addition prices retain their existing contracts and source checks. Listing the user's projects still bypasses the model.
4. Automatic reply timing and human-reply suppression remain unchanged; private answers are not posted to Project messages.
5. Adversarial tool/output cases, different users/projects, blocked content, incomplete output, malformed/oversized responses, aborts, 429/5xx and unknown usage are covered without exposing secrets or bypassing accounting.
6. Existing result history and financial/authorization boundaries remain compatible. No database or frontend contract migration is introduced.
7. Focused Gemini adapter, config/server, runtime, Ask Lisno, Project-message, narrative/source/pricing and authorization regressions pass, along with backend typecheck/build and diff hygiene. Run affected replica-set tests if shared persistence orchestration changes; otherwise retain existing persistence semantics. Frontend verification is limited to any genuinely affected consumers because no visual changes are proposed.
8. Handoff clearly separates mocked verification from any authorized live test, reports remaining account/model constraints, and confirms that deployment, secret rotation and production mutation were not performed.

## Assumptions and open decisions

The request applies to the two existing Lisno AI chat surfaces. Gemini Developer API is the assumed credential type; no Vertex AI requirement has been stated. The default model above is the proposed implementation choice, configurable by environment. The user supplies the Gemini key securely in the backend environment; its value is not needed for specification or mocked implementation tests.

No additional blocking product question is needed at this stage. Task planning and implementation follow the repository's approval gates after this specification is approved.

## Compatibility correction after local feedback

Local Google validation rejected the initially documented `generationConfig.responseFormat.text.mimeType` shape. The approved structured-output behavior is preserved using the compatible `responseMimeType` and identical `responseJsonSchema` fields. Both a live synthetic greeting and a synthetic project-status tool exchange passed through the corrected adapter. This does not establish production-account access or comprehensive model quality. The task plan records the diagnosis, focused verification and transient upstream 503 encountered during testing.
