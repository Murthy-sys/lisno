# Estimator selection of configured baskets and ready items

Date: 2026-10-02  
Status: Revised specification approved by the user on 2026-10-02. The earlier Active-only version was partially implemented locally.  
Related approved work: [Estimator mapping to configured baskets and Main Lines](2026-10-01-estimator-configuration-basket-mapping-design.md). This specification changes that work's exclusion of temporary and direct-parent items, while retaining its pricing, snapshot, and authorization rules.

## Goal

Let Estimator/Sales check the Main Baskets required for an estimate, then select eligible configured items through their actual hierarchy. Ordinary Main Lines appear within their real Sub Baskets. Temporary items appear within a Sub Basket or directly under their Main Basket. Active items with a valid active revision and UOM remain eligible; Draft and Inactive items also appear when their source revision has complete Overview and Mode tabs and a valid UOM.

## Current behavior and evidence

- The first estimator screenshot shows Main Baskets and Sub Baskets, all with `0 Main Lines`; every checkbox is disabled. Later screenshots show `Cove in Gypsum` (temporary, 75%, Rft) and `POP false ceiling` (100%, sq-ft) under POP / Gypsum → NA in Configuration, while the estimator shows NA as empty. Neither Configuration card shows item lifecycle or revision status. The displayed percentage and UOM come from the draft revision first, when one exists.
- `LeadEstimateWorkspace.tsx` disables a basket checkbox when its eligible Main Line count is zero (`!editable || !lineCount`). The continue button already depends on editability, a selected basket, a room, and a loaded catalogue, rather than line count.
- The Configuration index counts all non-archived items on the current page, including Draft, Active, Inactive, and temporary records. Creation starts an item as Draft. The count is broader than the estimator's eligible item count; the screenshots alone do not identify which filter removed these items.
- The current local, uncommitted estimator catalogue implementation reads only Active items and active revisions. The frontend maps returned `mainLines`, grouped `temporaryItems`, and `directTemporaryItems` without dropping them. Its API URL points to production, so a local backend change cannot alter a production response until that backend change is deployed. The page also caches a successful empty catalogue, which is why a manual refresh control has been added locally.
- Configuration computes tab completion from revision section states: Overview is `overview.state === "complete"`; Mode is complete when either `advanced` or `pricing` is complete. Its 100% indicator means all four displayed tabs are complete, so it already satisfies Overview plus Mode. `needs_attention` is not complete.
- Configuration creation permits a temporary item with or without a Sub Basket. Both use the `AiEstimatorKnowledgeMainLine` model with `itemType: "temporary"`. A Draft revision remains mutable under the same revision ID while its version increases on section saves; deactivation retains the active revision.
- Before the approved local temporary-item changes, estimate requests, catalogue DTOs, draft line models, publication checks, client review schemas, workflow descriptions, and procurement lineage assumed every configured estimate line had a nonempty Sub Basket ID and name. Those local changes now carry real nullable parentage through the flow; the new revision concentrates on eligibility and mutable Draft provenance.
- The previously approved Active-only implementation is present as local, uncommitted source changes. This revision changes its estimator eligibility contract and does not authorize deployment or any Configuration data write.

## Scope and non-goals

In scope:

1. Present all active Main Baskets returned by the estimator catalogue in configured order as a vertical checkbox list. A basket is selectable even if it currently has zero eligible items. Keep locked estimates read-only.
2. Include eligible ordinary Main Lines under their real Sub Baskets and eligible temporary items under their real Sub Basket or directly under a Main Basket. Active items use their active revision and valid UOM. Draft and Inactive items must additionally satisfy the canonical Overview and Mode tab completion rule on the chosen revision.
3. Show selected baskets, their Sub Baskets, and direct temporary items in the builder. Display item type and UOM clearly, and use the existing estimator-entered selling rate and quantity flow for both item types.
4. Save, reload, submit, publish, render, and pass eligible ordinary and temporary estimate lines through client review, PDF, design mapping, workflow, procurement, and finance without fabricating a Sub Basket or losing identity, amount, or labels.
5. Explain why a selected basket has no available items and allow the user to refresh available items without losing basket, room, or saved-line state. Make the count label describe estimator-available items, not all Configuration items.

Out of scope: any mutation of existing Configuration data, including creating, editing, activating, deactivating, deleting, seeding, backfilling, or migrating baskets, Sub Baskets, Main Lines, temporary items, revisions, or UOMs. Do not change Configuration management screens or their write services. Isolated disposable test fixtures are permitted only for verification. Also out of scope: admitting archived, unresolved-UOM, missing-revision, wrong-parent, or incomplete Draft/Inactive items; importing Configuration cost/margin as the customer's selling rate; changing GST or approval rules; production data mutation, commit, or deployment.

## Recommended approach and tradeoff

Extend the existing configured-line branch with an explicit item type and an optional Sub Basket for temporary items. Add separate temporary-item arrays to the catalogue response: `directTemporaryItems` on a Main Basket and `temporaryItems` on a Sub Basket. Keep the existing `subBaskets[].mainLines` array for ordinary Main Lines. This additive response lets existing clients continue reading the catalogue and preserves the real parentage of direct temporary items.

For the new Draft/Inactive rule, extend the same server projection and first-save resolver with one shared source-revision selector and eligibility check. Let the updated frontend opt in through `includeReadyNonActive=true` on the catalogue read. Without that flag, the endpoint keeps its Active-only item set so older clients do not display items they cannot save with the required Draft version fields. The current older backend rejects unknown query fields, so an updated frontend released first retries the legacy catalogue URL only when the response specifically rejects `includeReadyNonActive`; other request errors remain errors. The backend remains authoritative on save.

Using the retained Active revision for every Inactive item would avoid mutable Draft checks, but it could quote older content while Configuration displays a newer Draft. The recommended draft-first rule for Inactive items follows the visible Configuration revision and rejects a stale save if that Draft changes. Active items continue using their approved Active revision.

An alternative is to put direct temporary items under a synthetic Sub Basket. That would simplify current UI loops but create a false ID and label that cannot pass parent validation or remain trustworthy in saved estimates, procurement, and audit history. Do not use a synthetic persisted Sub Basket. The builder may use a presentation heading such as **Directly under Main Basket** without storing it as source data.

## Product and UX behavior

1. The configuration step shows a native checkbox per active Main Basket. The full labelled row is clickable, keyboard focus is visible, and checked state is retained across navigation and save/reload. A zero-item basket remains selectable in an editable estimate.
2. The count distinguishes available Main Lines and available temporary items. It must not show `0 Main Lines` as if it meant no Configuration records. When no eligible items exist, explain that availability depends on the selected source revision, completion, parentage, and valid UOM. Loading, empty catalogue, 403, request failure, retry, and stale catalogue states remain distinct. Both Configure and Builder offer a keyboard-accessible refresh action; it preserves the selected room, baskets, entered values, and saved snapshots.
3. With a room and at least one selected basket, **Continue to item selection** opens the builder. Ordinary Main Lines appear under their Sub Baskets. Temporary items with a Sub Basket appear there with a visible **Temporary item** label. Direct temporary items appear in a clearly named group inside their Main Basket without a fictional Sub Basket. Draft and Inactive availability is labelled for the estimator so its source state is clear; this internal state need not appear on customer-facing documents.
4. Each eligible item has its configured name, UOM, include checkbox, quantity, and manually entered selling rate. Blank is distinct from explicit zero. An included blank-rate line may be saved as an incomplete draft but cannot be submitted or published; invalid precision is rejected.
5. If a selected basket has no eligible items, the builder shows an explicit empty explanation. A basket-only draft may be saved. Submission remains unavailable until at least one valid item is included.
6. Saved item snapshots remain visible if Configuration later renames, deactivates, or removes an item. A catalogue refresh must not silently replace the stored label, UOM, item type, parent identity, rate, or amount. Existing legacy estimates retain their current display and editing behavior.
7. Responsive, keyboard, and accessible-name behavior must cover the vertical chooser and the nested builder at mobile and desktop widths. Reuse the existing design language and controls; no new icon or visual dependency is needed.

## Data, API, and validation contract

- `GET /estimation/catalogue` remains an Estimator/Sales and Super Admin read operation with the existing active-actor checks and pagination. `includeReadyNonActive=true` requests the expanded item set; absence of the flag preserves the Active-only set for older clients. It reads existing Configuration records without modifying them and returns active baskets in configured order. `directTemporaryItems` on each basket, `temporaryItems` on each Sub Basket, and `mainLines` on each Sub Basket keep the actual hierarchy. Each eligible item carries stable IDs, item type, actual nullable `subBasketId`, display order, chosen revision ID and version, item lifecycle status and version, and resolved UOM. Fetch item, revision, relevant section, and UOM data in batches. Do not return vendor pricing or administrative payloads.
- Source revision selection is deterministic: an Active item uses its Active revision even when a pending Draft revision exists; a Draft item uses its Draft revision; an Inactive item uses its Draft revision when present, otherwise its retained Active revision. A selected Draft revision that lacks Overview/Mode completeness does not fall back to an older Active revision. Archived items are excluded.
- Eligible item rules: the parent Main Basket is Active; the item type is ordinary Main Line or temporary; the chosen revision belongs to the item and has the status expected above; its Overview supplies a resolvable non-archived UOM with valid code, name, and decimal scale. For Draft and Inactive items, `overview.state === "complete"` and (`advanced.state === "complete"` or `pricing.state === "complete"`) on the chosen revision are required. A 100% displayed item satisfies these two tab conditions but is not the only qualifying percentage. Active items retain the approved active-revision-plus-valid-UOM rule. Ordinary Main Lines require a real matching Sub Basket. Temporary items may have a real matching Sub Basket or `subBasketId: null`.
- A configured estimate-line request identifies `mainBasketId`, `mainLineId`, `revisionId`, `uomId`, `roomId`, `itemType`, and `subBasketId: string | null`, plus item and revision versions from the catalogue for newly selected Draft/Inactive source content. The server re-resolves new lines inside the save transaction and checks current item type, lifecycle, parent, chosen revision ID/status/version, tab readiness where required, UOM, selected basket, ownership, and estimate version before first save. It rejects a stale first save with the existing refreshable catalogue conflict; a Draft edit under the same revision ID cannot silently alter a new quote line. It stamps source lifecycle/revision provenance, item name/type, basket name, optional Sub Basket name, UOM, rate, and amount snapshot. A direct temporary line stores `subBasketId: null` and `subBasketName: null`. Only a temporary line may use null Sub Basket fields. Existing configured lines without `itemType` are interpreted as ordinary Main Lines for compatibility.
- Persist a stable estimate-line ID keyed by room ID plus Main Line ID regardless of item type. Save rates and amounts in integer paise with the existing quantity precision, GST, and total rules. No Configuration cost or guessed rate becomes a quote. Later draft edits use the saved snapshot; publication freezes it. A newly selected item that loses eligibility between catalogue read and save returns the existing refreshable catalogue conflict.
- Add the item type, nullable Sub Basket, and source revision/version provenance to frontend API types, backend request validation, estimate storage, and OpenAPI. Preserve the existing immutable client review snapshots and downstream DTOs. Validate type and parentage rather than treating null as an arbitrary missing field. No stored-data rewrite is planned: preexisting configured lines lacking item type remain ordinary Main Lines with their required Sub Basket, and existing saved lines do not acquire invented source-status values.

## Downstream integrity

- Summary, proposal, client/reviewer/designer views, and PDF show the actual item name and basket path. Direct temporary items show their Main Basket and item, with a **Temporary item** cue where useful; no `null`, `undefined`, or invented Sub Basket label appears.
- Design mapping, task generation, and workflow use the saved stable Main Basket and Main Line IDs. A direct temporary item does not disappear because its Sub Basket is null. The existing generic worker role remains the fallback when no configured specialty mapping exists.
- Procurement source and expense lineage keep the stable approved estimate-line key, exact item type, Main Basket ID, nullable Sub Basket ID, and integer-paise amounts. A direct item is grouped by its real Main Basket. Do not infer or invent a vendor Sub Basket from its name. Project/detail/portfolio finance amounts continue to reconcile from the same approved estimate snapshot.
- Approval and client review history remain immutable. Do not rewrite already published estimates or reinterpret historical ordinary configured lines as temporary items.

## Authorization, compatibility, and failure handling

- Estimator/Sales reads the filtered catalogue and edits only owned lead estimates; Super Admin retains the existing operation-specific read access. Configuration creation/activation remains Super Admin-only. Backend checks remain authoritative. Showing a complete Draft/Inactive item in the estimator does not activate it or change its Configuration lifecycle.
- Coordinate the client and server rollout: older clients omit `includeReadyNonActive` and continue seeing Active-only items; the updated client opts in and sends Draft/Inactive versions when the backend supports them. Against an older strict-query backend, the updated client retries without the opt-in only for a validation error naming that query field; it handles absent arrays and provenance fields and omits newly introduced save fields for ordinary Main Lines in that legacy mode. A temporary line with nullable parentage is not sent to a backend that cannot accept it. The new backend rejects a Draft/Inactive first save without current versions. Existing estimate reads accept missing item type as ordinary Main Line and missing source provenance as historical unknown. No live migration or backfill is needed; rollback is the previous catalogue eligibility implementation because no Configuration data is rewritten.
- A failed catalogue request is shown as an error with retry, never as an empty basket. A stale first-save reference is rejected without writing the invalid line. A successful empty response can be refreshed in place. If production items remain absent, inspect a sanitized estimator response or user-provided status/type/UOM evidence only with appropriate read authority; do not change or directly query production Configuration records. Do not claim a projection bug from the admin page's item count alone or expose private item payloads in logs or screenshots. Local code changes do not fix a production response until the applicable backend is deployed through a separately authorized action.
- Preserve existing ownership, transaction, version/CAS, audit, and publication behavior. No customer email or production write is part of local implementation.

## Risks and verification

- The temporary/direct-parent path touches catalogue projection, save validation, immutable review, workflow, procurement, and finance. Draft/Inactive inclusion adds mutable revision and lifecycle race risk: a Draft revision ID stays stable while its version and sections change. Reusing a saved estimate line must never re-resolve a newer Configuration revision.
- A Configuration card's percentage/UOM is not proof of lifecycle status, selected source revision, or estimator eligibility. Verify with asymmetric fixtures in an isolated, disposable test database only: two baskets, same-named Sub Baskets, Active ordinary/grouped/direct temporary items, Draft and Inactive ordinary/temporary items with complete and incomplete Overview/Mode combinations, 100% items, a mutable Draft revision edited between read and save, an Active item with a pending Draft, an Inactive item with a retained Active revision, archived/wrong-parent/invalid-UOM controls, and saved-line retention after source changes. Do not run tests or scripts against existing Configuration data.
- Run focused backend catalogue/save/submit/publication and replica-set tests, downstream review/PDF/design/workflow/procurement/finance regressions with unequal project amounts, frontend rendered selection/save/reload/refresh/empty/locked states, keyboard and mobile/desktop checks, backend/frontend typechecks and builds, `git diff --check`, and final worktree inspection. Broaden tests if a shared contract exposes another consumer. The independent refresh correction already passed 28 focused rendered tests and frontend typecheck locally; new eligibility verification remains pending approval and implementation.

## Acceptance criteria

1. Every active Main Basket in the estimator catalogue can be checked or unchecked in an editable estimate, including baskets with zero eligible items. Locked estimates remain read-only.
2. An Active ordinary Main Line with a valid active revision, matching Sub Basket, and UOM appears under that real Sub Basket. Active temporary items with the same eligibility appear in their real Sub Basket or directly under the Main Basket. A Draft or Inactive item of either type also appears at its real location when its selected revision has complete Overview and Mode tabs and valid UOM. A 100% complete Draft/Inactive item qualifies; incomplete, archived, wrong-parent, and unresolved-UOM items do not. An Active item uses its Active revision despite a pending Draft; an Inactive item uses its displayed Draft revision when present, otherwise its retained Active revision.
3. The chooser accurately labels available Main Line and temporary-item counts. A selected empty basket has a useful explanation, while API failure or denied access has a distinct state. Refreshing a successful empty catalogue can reveal newly available items without losing the selected room, baskets, entered values, or saved snapshots.
4. An eligible ordinary or temporary item, including a qualifying Draft/Inactive one, can be included in a room, given quantity and a manually entered selling rate, saved, reloaded, and submitted under the existing rate and amount rules. Blank versus zero remains distinct. Wrong-parent, invalid-UOM, no-longer-ready, changed-lifecycle, and stale Draft-version first saves conflict without writing the line.
5. Saved and published lines retain their real `itemType`, IDs, optional Sub Basket, source revision/version provenance where captured, names, UOM, rate, and paise amounts after Configuration changes. Legacy and existing ordinary configured estimates remain readable and correct.
6. Client review, PDF, design mapping, workflow, procurement, and project/portfolio finance handle direct and grouped temporary lines with intelligible labels, correct lineage, and reconciled amounts. No path requires a fabricated Sub Basket.
7. Responsive rendered interactions, keyboard focus, accessible names, authorization checks, focused tests, typechecks, builds, and repository hygiene checks pass on the integrated change. Exact results and any unrun checks are reported at handoff.

## Assumptions and open decisions

- The latest user instruction supersedes the earlier Active-only constraint: items with complete Overview and Mode tabs, including items at 100%, should appear even when their lifecycle is Draft or Inactive. This applies to ordinary Main Lines and temporary items. Preserving the already approved Active-item rule is the narrowest compatible interpretation; Active items still need an Active revision and valid UOM, while Draft/Inactive items have the extra completion gate.
- “Under Main Baskets” includes temporary items directly under a Main Basket and those assigned to a real Sub Basket, because Configuration supports both placements. The individual production items' lifecycle, chosen revision, and eligibility remain unverified from the screenshots. The recommended deterministic revision choice above is based on Configuration's draft-first display for nonactive items and preservation of the approved active source for Active items.
- The user explicitly prohibited touching or editing Configuration data. Implementation may read the existing estimator catalogue, but must not mutate existing Configuration records or management behavior in any environment. Verification may create only isolated disposable fixtures. No direct production Configuration inspection is planned.
