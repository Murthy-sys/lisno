# Configuration-owned estimation prices and tier availability

Date: 2026-11-09
Status: revised specification and task plan approved; Mode A selected. Implementation and verification complete for AC1–AC7. See the [current execution record](../plans/2026-11-09-estimation-priced-main-lines-visibility.md#configuration-owned-pricing-execution-record); older test counts describe prior scopes.

## Goal and confirmed scope

Estimation must use prices set by Super Admin in Configuration. Users can select an available tier, permitted pricing method, quantity and components, but cannot enter or override an estimation price. Show each tier's own configured price; disable a tier when its applicable price is missing, zero, invalid, or otherwise unusable.

The user reconfirmed that a zero Signature base does **not** hide a Main Line when Premium has a positive qualifying base. Eligibility therefore remains an OR across default Mode, Signature, Premium and Functional, rather than requiring every mode to be priced. The price must match the row's pricing method: a PMC-only price does not establish Standard/Sub-vendor eligibility.

Scope includes the existing staff estimation workflow (Sales/Estimator and shared Designer editing), related discovery/recommendation consumers, and backend enforcement of Configuration-owned prices. Preserve the Client quotation workflow's configured-choice behavior and apply consistent eligibility to directly affected choices. No redesign or new pre-Add type/pricing selector is included.

- The running local backend was also older than the edits and omitted the visibility field entirely. The existing local launcher was gracefully restarted without demo seeding; its live public metadata now includes the greater-than-zero field. The source entrypoint is not watched, so future backend edits need a local reload before runtime verification.
- `getEstimationCatalogue` preserves response fields. The normal Sales list rejects explicit false metadata before selected-row handling; no compact-row bypass of a correct false was found. Legacy missing metadata currently preserves visibility.
- `configuredEstimate.ts` creates new choices as Signature/Sub-vendor with Standard classification. Type/pricing controls only appear after inclusion; there is no pre-Add global type selector.

- `ConfiguredEstimateBuilder.tsx` enables the rate input whenever the row is editable, allows manual In-house overrides, and uses the shared tier controls. The estimate route accepts manual rates and only applies Configuration price/version matching to configuration-sourced rates. Disabling an input alone would not enforce price ownership.

## Requirements

1. **Current Configuration is authoritative.** Use the latest saved draft revision, otherwise saved active revision, joined by stable Main Line ID. Keep integer paise, current selling-price formulas, margins, low-quantity effects, component calculations, and CAS/version handling unchanged.
2. **Match the pricing method.** A Standard row uses Sub-vendor eligibility and prices. A Special row uses its selected permitted PMC/Sub-vendor/In-house method. A positive price for another method must not rescue a missing or zero base for the row's method.
3. **Any of the four scopes may qualify.** For the relevant method, one positive valid base across default, Signature, Premium or Functional establishes list eligibility. A zero/missing base in another scope does not negate that positive base. Non-applicable/hidden tier rules remain authoritative for selecting a financial tier.
4. **Strict-positive discovery.** Zero, negative, null, blank, invalid, overflowing or unavailable bases do not qualify. For In-house, reuse existing complete split/component and reference validation: a zero part is valid within a positive complete total; an all-zero or unusable total does not qualify. Keep historical/shared financial zero handling intact.
5. **Discovery follows the method.** Filter ordinary lists, search, Add choices, counts/pagination, temporary paths and new recommendation targets consistently. Fresh staff choices use the existing Standard/Sub-vendor default, so PMC-only or In-house-only sources are not offered as unpriced Standard rows. Existing Special selections are evaluated using their own method and remain reviewable. Do not add an unrelated pre-Add method selector.
6. **Tier-specific availability.** Enable Signature/Premium/Functional only when that tier is applicable and its own saved configuration can provide a valid positive price for the row's method. Disable zero, missing, incomplete, unavailable-reference and unusable-selling-price tiers with an accessible reason. Another tier/method's values cannot enable it. Do not widen the financial tier enum or expose default Mode as a new estimation tier.
7. **Tier-specific prices.** Choosing an enabled tier uses that tier and method's authoritative Configuration selling price, including existing impacts/components. Do not borrow Signature/PMC/default/another tier's price. New choices should start with the first usable applicable financial tier in the established Signature/Premium/Functional order, without persisting anything until explicit Add. If only default Mode qualifies list visibility, keep the item visible but unavailable to Add until a usable financial tier exists; do not invent a default-to-tier fallback.
8. **Estimation price inputs are disabled.** All estimation rate fields, including catalogue previews and selected/review rows, are disabled for entry. Remove manual override affordances and their edit handlers in estimation. Quantity, dimension, permitted type/method/tier and component-selection controls retain their existing permissions. Price updates caused by those explicit selections come only from Configuration calculations.
9. **Super Admin sets prices in Configuration.** Preserve existing Configuration price-management authorization. Estimation is not an alternative price-setting surface, including for a Super Admin viewing an estimate. Backend saves must reject newly supplied manual/forged price overrides and validate the selected configured tier/method/component price rather than trust a disabled frontend input. Do not add a new role or broaden permissions.
10. **Preserve existing data.** Keep full source records and selected/saved IDs, inclusion and amounts; do not label a real source deleted, silently drop a selection, migrate data, or rewrite approved/published history. A saved line whose current tier/method has become unusable stays outside ordinary eligible rows in explicit review. Let the user select another enabled tier when permitted; only that explicit action applies its Configuration price.
11. **Legacy saved manual prices.** Preserve unchanged existing saved rates for compatibility/review without allowing new or changed manual rates. Legacy rows without a current configured replacement must not acquire a new override path. Tier/method/component changes must switch to a valid Configuration price; unchanged historical/manual snapshots are not repriced merely by loading or filtering. Define the bounded unchanged-rate check in the task plan and test against fabricated IDs/revisions.
12. **Required recommendations remain reviewable.** Filtering an unusable target cannot silently satisfy a required rule or auto-close suggestions while review remains. Preserve selected source obligations, Remove/review access and stale-response guards. Client choices must use their own usable configured tier/method and retain existing permissions.
13. **Refresh and failures.** A current Configuration refresh updates eligibility, tier availability and displayed configured prices consistently. Failed/loading/old-version responses must not manufacture eligibility or allow price editing. No per-row requests, background save/submit, selection mutation, or silent financial change may be caused by filtering.
14. **Keep the requested refinements.** Preserve the four independent Configuration editors, Main Line tier selection, hidden default Mode UI in estimation, Sub Basket info/comparison placement, removed Sales footer warning, and recommendation completion behavior. No unrelated style, dependency, route or workflow changes.

## Recommended integration and API impact

Extend the existing catalogue projection with authoritative positive-base availability by Configuration scope and pricing method, using booleans rather than exposing raw private costs. Retain the aggregate `hasConfiguredBasePrice` for compatibility/internal consumers, but do not use an aggregate PMC positive as proof that Standard is priced. Reuse source/configuration readers and batched reference checks; no database collection or persisted financial field is required.

Frontend drafts carry the availability metadata for reconciliation, discovery and disabled-tier reasons. Use one consistent method-aware predicate across the relevant consumers. Keep discovery eligibility separate from selecting a usable financial tier, and raw base eligibility separate from final selling-price calculation. Additive metadata must not be persisted as a user-supplied financial value. A failed or legacy response cannot create proof of a matching positive base; preserve the established loading/error/review states.

Enforce Configuration-owned prices at the existing estimate mutation boundary, without weakening authorization, immutable history, audit, idempotency, version/CAS or downstream task generation. Preserve unchanged saved legacy rate snapshots while rejecting new/altered manual overrides, including forged source identities. Keep existing permission checks for selecting a pricing mode distinct from permission to set its price.

Alternative considered: disable only the frontend rate input and continue using the aggregate flag. This leaves the reported cross-method visibility problem and accepts forged manual-rate requests, so it does not satisfy the request.

## Constraints, risks and non-goals

- No Configuration data edits, price-formula changes, GST changes, new financial tier, default-to-tier fallback, Procurement pricing changes, schema migration, seed, backfill, dependency/lockfile change, production deployment, commit/push or external communication.
- Published/approved snapshots and saved source lineage remain intact. Rollback is a bounded source revert; no data rewrite is planned.
- Preserve unrelated dirty work. Separate the correction delta from the earlier completed implementation when reviewing and verifying.
- Key risks: borrowing another method/tier's price; enabling zero tiers; making PMC-only items appear as Standard; leaking a manual override through another save path; rewriting a saved legacy price; allowing forged legacy exceptions; component/quantity price mismatches; lost recommendation obligations; and testing a new source file while the runtime still serves old code.
- Expected limitation: new staff discovery remains Standard/Sub-vendor by default. Sources priced only for Special methods are not newly offered as Standard. No new selector or automatic classification change is introduced in this scope.

## Acceptance criteria

- **AC1 — Matching-method visibility:** zero/missing Standard bases do not appear as eligible Standard rows even when PMC is positive. Positive relevant-method bases in any of the four scopes qualify; Signature zero with Premium positive remains eligible. Existing Special rows use their selected method.
- **AC2 — Disabled tiers:** only applicable tiers with a usable positive price for the selected method are enabled. Missing/zero/incomplete tiers remain disabled and explain why, independently of another tier's price.
- **AC3 — Correct displayed prices:** asymmetric Signature/Premium/Functional fixtures show the selected tier's exact Configuration selling price and impacts; no cross-method, cross-tier or default fallback. Fresh choices start in a usable tier; default-only visibility does not enable an unpriced financial tier or Add.
- **AC4 — No price editing:** keyboard/mouse cannot edit estimation rate fields or reach an override action. New/altered manual prices are rejected by the backend for otherwise authorized estimate editors; legitimate Configuration choices, quantities, dimensions and components still work within permissions. Configuration price-setting remains Super Admin-managed.
- **AC5 — Data and history preservation:** saved/approved lines keep IDs, inclusion and prices unless an authorized explicit choice applies current Configuration pricing. Unchanged legacy manual snapshots remain reviewable/compatible; fabricated legacy identities cannot bypass the override restriction.
- **AC6 — Consistent discovery and suggestions:** list/search/picker/recommendation/temporary paths and counts agree before paging, required-unavailable targets remain review issues, and filtering/refresh causes no Add/Remove/save/submit side effect.
- **AC7 — Verification and runtime:** focused backend authorization/price/source/replica regressions and frontend rendered tier/rate/discovery tests cover AC1–AC6. Run affected typechecks/builds and desktop/mobile interaction checks. Reload the local non-watching backend and verify the real reported source response and normal estimator path before claiming the issue fixed. Do not reuse the previous 578/638-test counts as new evidence.
